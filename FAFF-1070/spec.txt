## WHY — Problem and Principles

**Load-bearing model.** *(Revised — fixes the review's architectural-major "symmetric two-occupant slot" finding: the prior framing implied a two-peer race, which mischaracterizes how the slot actually behaves.)* Tier 1 of `create.md`'s template-resolution order is one *slot* with room for more than one *occupant*, but the relationship between occupants is **asymmetric, not a peer race**. Every occupant is one of two tiers:

- **Confirmed-tier.** An occupant whose mapping a human onboard-confirmed for a given type (FAFF-1081's onboard step 3b, for the Linear leg). Once populated for a type, a confirmed-tier occupant is **unconditionally authoritative** for that type — it never competes probabilistically with anything else, because a human already resolved any collision once, at onboard time.
- **Heuristic-tier.** An occupant that resolves live, per-fill, with no human confirmation step behind it (this ticket's GitHub leg). A heuristic-tier occupant only ever gets a turn for a type **no confirmed-tier occupant has claimed** — it is a fallback for a gap, never a competitor to a populated confirmed-tier answer.

**"Tracker as source of truth," generalized.** *(New — fixes this round's architectural-major "tier-1's 'tracker is source of truth' framing doesn't fit the GitHub leg" finding.)* `create.md`'s original tier-1 line describes fetching "the tracker's own template body (fetched live), keeping the tracker as source of truth" — written when the slot had exactly one occupant, so "the tracker" and "the occupant's own origin" were the same thing and the line didn't need to distinguish them. The GitHub leg's source is the git working tree, not a tracker call, which can look like a tension in the slot's own stated purpose if that line is read as "only a tracker counts as authoritative." It isn't: the generalized invariant, true of both occupants, is that each tier-1 occupant treats its own native source as authoritative for its own templates — the tracker's persisted template store for the Linear leg, the repo's committed template files for the GitHub leg. "Tracker as source of truth" in `create.md`'s original, single-occupant framing meant "this occupant's origin, not a human override typed at fill time" — a claim both occupants satisfy, each in its own domain, not a claim that a tracker round-trip is what makes an answer authoritative.

FAFF-1083 built the first, confirmed-tier occupant (Linear's `list_templates`/`get_template`, gated on an onboard-confirmed map). This ticket builds the second occupant — the slot's first heuristic-tier member: `.github/ISSUE_TEMPLATE/*.md` / `.github/ISSUE_TEMPLATE.md`, gated on the **repo** carrying that structure — not on which tracker `tracking.tracker` names. Those are two different axes: this very repo pins `tracking.tracker: linear` (`.faffrc.yaml`) while being hosted on GitHub (`tracking.repo: shftwst/faff`), so a `.github/ISSUE_TEMPLATE/` directory could exist here regardless of the configured tracker. Gating the new occupant on the tracker value would silently miss exactly this shape.

**Guidance for a future third occupant** (e.g. GitHub issue-forms YAML, or any other channel this slot might someday grow) — named explicitly so this framing generalizes past today's two-occupant case: declare the new occupant as confirmed-tier or heuristic-tier before wiring it in. A confirmed-tier occupant needs its own onboard-time human-confirm step (mirroring FAFF-1081's) and, once populated for a type, is unconditionally authoritative for it — no scoring, no live disambiguation, because the human already resolved any collision once. A heuristic-tier occupant has no such step; it resolves live, per-fill, and only ever gets a turn for a type no confirmed-tier occupant has claimed. If the slot ever grows more than one heuristic-tier occupant, they stack **below all confirmed-tier occupants**, in an order this ticket leaves **unspecified** (first-built order, or whatever a future ticket sets) — heuristic-tier occupants are peers only among themselves, never with a confirmed-tier occupant.

**Problem statement.** Status quo: a repo whose *issue tracking* runs through Linear (or anything else) but whose *GitHub-hosted issues feature* separately defines `.github/ISSUE_TEMPLATE/*` never gets those templates considered at create time — `create.md` never reads that path, so the fill step is blind to a whole class of maintained, human-authored field structures. Separately, once a repo can expose *multiple* same-type native templates (GitHub's directory form allows any number of files), the ticket's own acceptance criteria require a live disambiguation mechanism across those candidates — a mechanism that doesn't exist yet anywhere in the codebase (no keyword-overlap scorer, no ambiguity-prompt precedent in the fill step). This ticket builds both: the GitHub-file discovery/read occupant, and a **detect-and-defer** scorer — it surfaces a confident single-candidate hit when a genuine lexical anchor exists between a candidate and the ticket, and defers to an operator prompt (interactive) or a logged fall-through (autonomous) on any genuine multiplicity, including the common case where competing same-type templates differ only in boilerplate `name`/`about` captions with no distinguishing signal available. It is deliberately **not** a forced ranked pick — see Design Decision Rationale → **Does the overlap scorer select, or detect-and-defer?**

**Design principles** (each would cause rejection of an otherwise-valid implementation):

- **Repo-gated, not tracker-gated — two independent axes.** `.github/ISSUE_TEMPLATE*` is a property of the git repository, detected by its presence in the working tree the fill step actually runs against — never inferred from `tracking.tracker`. A repo can be GitHub-hosted under any configured tracker (this repo is the live counterexample). **This is not the same claim as "detected regardless of checkout state."** "No tracker connector" (git-only mode) and "no materialized working tree" (a shallow/detached/sparse checkout) are two different conditions; this principle only disclaims dependence on the first. See WHAT → Design decisions → **Working-tree materialization** for what this ticket assumes about the second, and why a repo that legitimately commits `.github/ISSUE_TEMPLATE/` failing this check would be a closed, safe miss rather than an open one.
- **First-match-wins, extended not reordered.** The GitHub leg is a second sub-step *inside* tier 1, tried after the Linear leg and before tier 2. Either leg missing falls through exactly as today; neither leg can suppress the other's hit.
- **Never both fire for one field-set.** A single fill resolves at most one tier-1 hit. When both legs could plausibly hit for the same type (this repo's own shape makes that possible), the confirmed-tier occupant (Linear, once populated for that type) is unconditionally authoritative — never a live comparison between the two, never a second silent overwrite. See WHY → Load-bearing model for the confirmed-vs-heuristic-tier framing this decides from.
- **Untrusted input stays data.** Front matter and body text read from `.github/ISSUE_TEMPLATE/*` are treated exactly like a tracker's returned template body (gateway kernel → **Untrusted input (no-execute floor)**): only the `## <Field>` heading sequence (body) and a fixed set of front-matter scalar fields (`name`/`about`/`labels`, for matching only) are extracted; nothing in either is ever executed or interpreted as a directive, regardless of the fact that these are committed, presumably PR-reviewed files. **This governs the agent/CLI-facing path** — what the no-execute floor already means by "never executed." The **human-facing display** path (the ambiguity prompt) is a separate channel with its own principle, next.
- **The ambiguity prompt neutralizes untrusted display text — it is a picker, not a dialogue.** *(New in round 2, fixing the infosec-minor review objection; the enforcement mechanism below is revised in round 3 — see WHAT → Design decisions → **Sanitization boundary**.)* `name`/`about` text reaching the interactive prompt is sourced from committed `.github/ISSUE_TEMPLATE/*` files — attacker-influenceable via a PR or fork, exactly as the untrusted-input floor above already flags. That floor's "never executed or interpreted as a directive" language was written for agent-side handling and says nothing about the **human-facing display channel**: a crafted `name:` rendered uncritically to an operator is a prompt-injection/social-engineering surface against the human, not the agent. The prompt therefore treats candidate text as **display data only**, and the neutralization is a property of the **CLI verb's own output**, not a separate rendering-layer behaviour left to `prompt_operator`'s discretion: `faff github-templates resolve --json`'s `ambiguous` result already carries each candidate's `name`/`about` truncated to a fixed length, stripped of control/ANSI characters, and wrapped in a fixed `[untrusted template text] "…"` demarcation convention — so the demarcated, sanitized string **is** the CLI's own testable output, and `prompt_operator` renders it exactly as given. The operator is asked only to choose a list index or decline — **never** free-text entry, **never** a "type X to confirm" pattern a spoofed candidate string could imitate. See HOW → `sanitize_for_display` (in `github-templates.js`) and Design Decision Rationale.
- **No mid-run prompt outside interactive invocation.** The ambiguity-resolution prompt this ticket adds is scoped to a **genuinely interactive** create-fill (bare `/faff-jot`, bare `/faff-plot`, or `/faff-plot` without `--autonomous`). It **never** fires under `/faff-plot --autonomous` or any autonomous jot edge-case — `faff/references/autonomous.md`'s no-prompt invariant ("A mid-run interactive gate … is a contract violation … Genuine ambiguity resolves to park or route-out — never to asking") binds here exactly as everywhere else. A forced tie under autonomous invocation resolves the same way every other tier-1 miss does: fall through to tier 2/3, logged.

## WHAT — Vocabulary, Types, and Interfaces

**Vocabulary.**

| Term | Definition |
|---|---|
| Linear leg | Tier 1's existing, shipped sub-step (FAFF-1083): `faff native-map get` + `get_template`. Unmodified by this ticket. |
| GitHub leg | Tier 1's new sub-step (this ticket): a pure, offline scan of `.github/ISSUE_TEMPLATE/*.md` / `.github/ISSUE_TEMPLATE.md`. |
| Candidate | One discovered `.md` file under `.github/ISSUE_TEMPLATE/` (or the bare `.github/ISSUE_TEMPLATE.md`), with its front matter parsed and its inferred faff-type computed. |
| Front matter | The `---`-fenced YAML block at the top of a GitHub issue-template file (`name:`, `about:`, `title:`, `labels:`); used **only** for type-matching and overlap scoring, never as field content. |
| Inferred type | A candidate's best-fit faff type, computed from its front matter (`name`+`about`+`labels` together — a type keyword can live in any of the three) by a fixed keyword heuristic; `UNCLASSIFIED` when no keyword matches anywhere. **A domain-flavored label alone is not a type keyword:** a candidate whose only signal is a domain label (e.g. `labels: security`, generic non-type `name`/`about`) stays `UNCLASSIFIED` — see WHAT → Design decisions → **Labels and the type gate**. **Universal promotion (`EVERY_TYPE`) is gated, not automatic:** only the bare legacy `.github/ISSUE_TEMPLATE.md` file — and only when it is itself `UNCLASSIFIED` — promotes to `EVERY_TYPE`. A directory-form file that comes back `UNCLASSIFIED` stays `UNCLASSIFIED` (matches no type); it never gets the universal fallback. *(Fixed — see build_candidate below and Design Decision Rationale; this closes the review's QA-major "direct contradiction" and architectural-minor "unconditional imposition" findings, which were the same root bug from two lenses.)* |
| Overlap score | A weighted Jaccard similarity: a candidate's `name`+`about` tokens (30% weight) combined with its `labels` tokens (70% weight, when present) against the proposed ticket's title+description tokens. *(Fixed — labels are now part of the signal, not just type-matching; see below.)* It is a lightweight, **opportunistic** signal, and it only ever runs against candidates that already cleared the type gate (WHAT → Design decisions → **Labels and the type gate**): it produces a meaningful score only when such a candidate carries text that lexically anchors to the ticket — most often via curated `labels`. Near-identical same-type templates whose only difference is boilerplate `name`/`about` captions will typically score near zero for every candidate alike — that is the **expected, by-design** case for Ambiguous below, not a scorer defect. |
| Ambiguous | Two or more same-type candidates whose top two overlap scores fail to clear the configured minimum score or margin. This is the **normal** outcome whenever no candidate carries a genuine lexical anchor to the ticket (the common case for boilerplate-only templates) — the mechanism **defers** (prompt on interactive, logged fall-through on autonomous). It never forces a ranked pick among candidates it can't confidently distinguish; see Design Decision Rationale → **Does the overlap scorer select, or detect-and-defer?** |

**The new CLI verb (pure, offline — mirrors `native-map.js`'s discipline exactly).**

```
faff github-templates resolve --type <faff-type> [--min-score N] [--min-margin N] [--json] [--root DIR]
  # stdin: JSON { "title": "<ticket title>", "description": "<ticket description text>" }
  #   (title/description arrive on stdin, not argv — arbitrary ticket text may contain
  #    anything argv can't safely carry, exactly the reasoning `native-map set` used for
  #    template names)
```

- Pure, offline: reads only files under `<root>/.github/ISSUE_TEMPLATE*`. **NO MCP, no network, no git.**
- Imports `FAFF_TYPES`/`FAFF_TYPE_SET` from `native-map.js` rather than redefining the closed taxonomy a second time.
- `--type` outside the closed taxonomy → `usageError`, exit 2 (mirrors `native-map get`'s existing refusal).
- Malformed/absent stdin JSON is **non-fatal**: treated as `{title:"", description:""}` (never throws, mirroring the "never error on absence" posture `native-map get` already established) — this only weakens the overlap score, it never blocks resolution.
- `--min-score` / `--min-margin` default to conservative, overridable values (see **Punt**, below) so the AMBIGUOUS/HIT boundary is unit-testable independent of whatever number product eventually settles on.

```
INTERFACE github-templates resolve:
  # a single same-type candidate, or no candidate needs disambiguation:
  #   --json -> { "result": "hit", "type": <t>, "path": <relpath>, "name": <string>, "fields": [<string>, ...] }   exit 0
  # zero candidates for <t> (no .github/ISSUE_TEMPLATE* at all, or none classify as <t>):
  #   --json -> { "result": "miss", "type": <t> }                                                                  exit 0
  # >=2 same-type candidates whose top-two scores don't clear the margin/minimum:
  #   --json -> { "result": "ambiguous", "type": <t>,
  #               "candidates": [ { "path": <relpath>, "name": <string>, "about": <string>,
  #                                  "score": <number> }, ... ] }                                                   exit 0
  #     `name`/`about` here are ALREADY sanitize_for_display'd -- truncated (80/160 chars), stripped of
  #     control/ANSI characters, and wrapped in the fixed `[untrusted template text] "..."` demarcation
  #     convention. This is the ONE sanitization pass (WHAT -> Design decisions -> Sanitization
  #     boundary); nothing downstream re-derives or re-transforms them, and this makes the
  #     display-neutralization contract directly assertable via --json rather than a
  #     skill-lane-only behaviour with no test oracle.
  # --type outside {bug,feature,spike,chore,epic,default}:
  #   usageError -> exit 2
  # non-json: a short human line carrying the same fact (result + path/candidate count)
```

**Design decisions** (each concluded with a marker; collected in full in Design Decision Rationale):

- **Detection axis.** **Chosen:** repo-gated — a filesystem check for `.github/ISSUE_TEMPLATE/*.md` (≥1 file, excluding `config.yml`/`config.yaml`) or a bare `.github/ISSUE_TEMPLATE.md`, run against the working tree the fill step actually operates in — never gated on `tracking.tracker`'s value. This disclaims dependence on the tracker axis only; the separate working-tree-materialization axis is the next decision. (decides: architecture)
- **Working-tree materialization.** **Assumes:** the fill step's two call sites (`/faff-jot` Step 4, `/faff-plot` Step 5) always run against a real, checked-out local working tree — orthogonal to the git-only/no-tracker-connector axis above. No shipped reference states this as an explicit non-shallow/non-detached-checkout guarantee; the closest available citation, `kernel.md` → **Agent Lanes → Orchestrator** (the lane both skills run in), grants only "codebase (read-oriented)" visibility, which doesn't go that far. Named here as an assumption, not a proven invariant — with a **fails-closed, not open** consequence if it's ever wrong: a non-materialized checkout makes the GitHub leg read as a miss, never a false hit, so this is a missed-detection risk under the seed-never-constrain invariant, never a correctness risk. *Validate before relying on it:* see Open Questions and Assumptions.
- **Slot shape.** **Chosen:** a second sub-step inside the same tier-1 slot (`resolve_native_template`), tried immediately after the Linear leg, before falling through to tier 2. Not a sibling function jot/plot call separately.
- **Cross-leg precedence.** *(Revised — fixes the review's architectural-major "symmetric two-occupant slot" finding.)* **Chosen:** confirmed beats heuristic, always — not a peer race. The Linear leg is this slot's only confirmed-tier occupant today; whenever its onboard-confirmed map is populated for the requested type, it is unconditionally authoritative and the GitHub leg (heuristic-tier) is never even queried — see `resolve_native_template` below, where the Linear-leg block's hit `RETURN`s before the GitHub leg's line is ever reached. The GitHub leg only gets a turn for a type the Linear leg's map has no entry for. See WHY → Load-bearing model for the general confirmed-vs-heuristic-tier framing this generalizes from, and Design Decision Rationale for the specific two-occupant analysis.
- **Lane placement.** **Chosen:** the GitHub leg is a new **pure CLI verb** (no MCP, unlike the Linear leg) — `.github/ISSUE_TEMPLATE/*` are committed repo files, reachable without any tracker call.
- **Front matter vs body.** **Chosen:** front matter (`name`/`about`/`labels`) is the type-matching **and** overlap-scoring signal — `labels` now feeds both `classify_type` and `overlap_score` (previously type-matching only; see **Ambiguity-resolution shape** below) — the body is used **only** for `## <Field>` heading extraction, mirroring the Linear leg's identity-vs-body split.

## HOW — Behaviour

**Architecture and approach.** One new module (`github-templates.js`, mirroring `native-map.js`'s home and purity discipline) exposes the new CLI verb; `create.md`'s `resolve_native_template` gains one new sub-step calling it, plus one new parameter (`invocation_mode`, threaded per the plumbing decision above); jot's and plot's SKILL.md gain at most a one-line pointer plus the explicit parameter-pass at their respective call sites, exactly as they did for FAFF-1083.

**Front-matter parsing (pure, reused across the module).**

```
PROCEDURE parse_front_matter(file_text):
  IF the first non-blank line is not exactly "---": RETURN { front: {}, body: file_text }
  find the next line that is exactly "---" (the closing fence)
  IF no closing fence found: RETURN { front: {}, body: file_text }   # malformed fence -> no front-matter signal
  front_text := the lines strictly between the two fences
  body       := the lines strictly after the closing fence, rejoined
  TRY tree := parseYamlSubset(front_text) CATCH: tree := {}          # never throw on malformed front matter
  RETURN { front: tree, body }
```

**Candidate discovery.** *(Fixed — closes the review's QA-major "direct contradiction" and architectural-minor "unconditional imposition" findings, the same root bug from two lenses: the old `build_candidate(bare, universal: true)` set `inferred := universal ? EVERY_TYPE : classify_type(...)` unconditionally on `universal`, contradicting the DONE criterion's "only with no classifiable front matter." The rewrite below computes classification first and gates the fallback on `UNCLASSIFIED`, and restricts eligibility to the bare-legacy-file path only.)*

```
PROCEDURE discover_candidates(root):
  dir := join(root, ".github/ISSUE_TEMPLATE")
  IF dir exists AND contains >=1 file matching *.md (case-insensitive, excluding config.yml/config.yaml):
     RETURN [ build_candidate(f, universal_eligible: false) for f in those files ]   # directory form: no file
                                                                                       # here ever gets the universal fallback
  # Housekeeping note: the "excluding config.yml/config.yaml" clause above is accurate documentation
  # of intent, not live enforcement -- both names carry a .yml/.yaml extension and already fail the
  # *.md glob on extension alone, so the clause never actually fires. Left in as harmless, readable
  # intent-documentation rather than removed; see Scenarios -> the .yml-extension-vs-config-name
  # scenario for the extension filter's own, independently-exercised test.
  bare := join(root, ".github/ISSUE_TEMPLATE.md")
  IF bare exists: RETURN [ build_candidate(bare, universal_eligible: true) ]   # ONLY the legacy singular file
                                                                                 # is ever eligible for universal
  RETURN []                                                                     # no GitHub template structure at all

PROCEDURE build_candidate(path, universal_eligible):
  { front, body } := parse_front_matter(read(path))
  name       := front.name  OR filename_stem(path)
  about      := front.about OR ""
  labels     := front.labels IS a List ? front.labels : []          # best-effort; see Assumes
  classified := classify_type(name, about, labels)
  # Universal fallback fires ONLY for the eligible legacy file AND only when it has no classifiable
  # front matter at all. A directory-form file that fails to classify stays UNCLASSIFIED (matches no
  # type) -- it never becomes a candidate for every type. This is the literal implementation of the
  # DONE criterion "a candidate for every type only with no classifiable front matter."
  inferred := (universal_eligible AND classified == UNCLASSIFIED) ? EVERY_TYPE : classified
  RETURN { path, name, about, labels, body, inferred_type: inferred }

FUNCTION filename_stem(path):
  # (Fixed -- QA-minor "no test oracle": precise, concrete rule for the `name:` fallback, previously
  # unspecified. The basename of `path`, its `.md` extension stripped (case-insensitive), with every
  # underscore or hyphen replaced by a space.
  #   ".github/ISSUE_TEMPLATE/bug_report.md"      -> "bug report"
  #   ".github/ISSUE_TEMPLATE/feature-request.md" -> "feature request"
  #   ".github/ISSUE_TEMPLATE.md"                 -> "ISSUE_TEMPLATE" is never passed here --
  #     the bare legacy file's stem is never computed, since front.name OR filename_stem(path) only
  #     calls this when front.name is absent, and the bare file's own basename-minus-extension would
  #     be "ISSUE_TEMPLATE" -> "ISSUE TEMPLATE" if it ever were (no scenario relies on this case)
  base := the last path segment of path (the text after the final "/", or the whole path if none)
  stem := base with a trailing ".md" (case-insensitive) removed
  RETURN stem with every "_" or "-" character replaced by " "
```

**Type classification** (a GitHub-leg-specific heuristic inspired by FAFF-1081's onboard-proposal shape — not a verbatim reuse of it; see WHAT → Design decisions → **Type-classification convention**):

```
PROCEDURE classify_type(name, about, labels):
  haystack := lowercase(name + " " + about + " " + join(labels, " "))
  IF haystack matches /\b(bug|defect|broken|crash)\b/:                    RETURN bug
  IF haystack matches /\b(feature|enhancement|request)\b/:                RETURN feature
  IF haystack matches /\b(spike|investigation|research|question|rfc)\b/:  RETURN spike
  IF haystack matches /\b(chore|maintenance|dependency|refactor|cleanup)\b/: RETURN chore
  IF haystack matches /\b(epic|container|parent)\b/:                      RETURN epic
  RETURN UNCLASSIFIED   # never resolves to `default` — no realistic template names itself that
```

**Overlap scoring.** *(Fixed — the "practically dead" architectural-major finding. `labels` now genuinely contributes to the score, weighted above the largely-boilerplate `name`/`about` text, giving the scorer a real — if opportunistic — path to a confident hit.)*

**Behaviour summary:** produces a confident score only when a candidate's text — chiefly its curated `labels` — shares real vocabulary with the ticket; near-identical boilerplate templates correctly score near zero for all candidates alike, which routes to `ambiguous`/defer rather than a wrong pick (see WHAT → Ambiguity-resolution shape).

```
FUNCTION tokenize(text):
  RETURN lowercase(text) stripped of punctuation, split on whitespace,
         minus a small stopword set {a,an,the,and,or,to,of,in,for,is,it,this,that}, as a Set<String>

FUNCTION jaccard(a, b):
  IF a is empty OR b is empty: RETURN 0
  RETURN |a ∩ b| / |a ∪ b|

FUNCTION overlap_score(candidate, title, description):
  target     := tokenize(title + " " + description)
  name_about := tokenize(candidate.name + " " + candidate.about)
  label_toks := tokenize(join(candidate.labels, " "))
  score_na := jaccard(name_about, target)
  IF label_toks is empty: RETURN score_na            # no labels signal available -- name/about is all there is
  score_lb := jaccard(label_toks, target)
  RETURN (0.3 * score_na) + (0.7 * score_lb)          # labels are curated, specific keywords, far more likely
                                                       # to lexically anchor to a ticket than boilerplate
                                                       # name/about caption text; weighted, not replaced, so
                                                       # name/about still contributes when labels are thin
```

**Resolution (the CLI verb's body).**

```
PROCEDURE resolve(type, title, description, min_score, min_margin, root):
  candidates := discover_candidates(root)
  IF candidates is empty: RETURN { result: "miss", type }
  same_type := [ c for c in candidates if c.inferred_type == type OR c.inferred_type == EVERY_TYPE ]
  IF same_type is empty: RETURN { result: "miss", type }
  IF same_type.length == 1:
     f := same_type[0]
     fields := extract_field_headings(f.body)
     # Fixed -- QA-major "no empty-fields guard": mirrors the Linear leg's own
     # `IF fields not empty: RETURN fields` / else REPORT-opaque-and-fall-through guard -- see
     # WHAT -> Design decisions -> Empty-fields guard on the GitHub leg's single-candidate hit.
     IF fields is empty:
        REPORT github_opaque(type, f.path, f.name)   # this leg's own reporting convention,
                                                       # mirroring the Linear leg's REPORT opaque(...)
        RETURN { result: "miss", type }               # no other same-type candidate to fall to here
     RETURN { result: "hit", type, path: f.path, name: f.name, fields: fields }
  scored := [ { c, score: overlap_score(c, title, description) } for c in same_type ]
  sort scored DESCENDING by score
  top := scored[0]; second := scored[1]
  # NOTE: the comparison is strict '<' -- a score/margin exactly AT min_score/min_margin clears the
  # threshold (HIT), it does not trip "ambiguous"; only a value strictly below does. See Scenarios ->
  # the boundary-condition scenario.
  IF top.score < min_score OR (top.score - second.score) < min_margin:
     RETURN { result: "ambiguous", type,
              candidates: [ sanitize_for_display(s.c) merged with {score: s.score} for s in scored ] }
  RETURN { result: "hit", type, path: top.c.path, name: top.c.name, fields: extract_field_headings(top.c.body) }

PROCEDURE extract_field_headings(body):
  RETURN [ heading text for each line in body matching /^##\s+(.+)$/ ]   # the SAME heading-sequence rule tier 2 / the Linear leg apply

FUNCTION sanitize_for_display(candidate):
  # The untrusted-display floor's enforcement point (WHY -> Design principles, prompt-neutralization
  # bullet; fixes the infosec-minor "quoting block not enforced by anything testable" finding and the
  # QA-major "sanitization has no CLI-testable oracle" finding). Demarcation is a property of THIS
  # function's OUTPUT, not a separate, unspecified rendering-layer behaviour prompt_operator might or
  # might not honour. This runs INSIDE the CLI verb, before JSON-encoding -- the ONE sanitization pass
  # -- so its result is directly assertable via `faff github-templates resolve --json`.
  RETURN { path: candidate.path,
           name:  demarcate(truncate(strip_control_chars(candidate.name), 80)),
           about: demarcate(truncate(strip_control_chars(candidate.about), 160)) }

FUNCTION demarcate(text):
  RETURN '[untrusted template text] "' + text + '"'   # the fixed quoting convention -- every
                                                        # candidate's display text carries it, so a
                                                        # plain, undemarcated rendering can no longer
                                                        # satisfy the contract
```

**Integration into `resolve_native_template` (`create.md`'s tier-1 slot — the only control-flow change to shipped code, plus one new parameter).**

```
PROCEDURE resolve_native_template(type, title, description, invocation_mode):   # invocation_mode: interactive | autonomous

  # by reading both blocks (fixes this round's architectural-major "signature carries parameters the
  # Linear leg never uses" finding):
  #   Linear leg: consumes only 'type' (the native-map lookup key).
  #   GitHub leg: consumes all four -- 'type' for classification/matching, 'title'+'description' for
  #     overlap scoring, 'invocation_mode' for the ambiguity-prompt branch below.
  # Not split into two functions for this: one shared call site, one first-match-wins chain (WHAT ->
  # Design decisions -> Slot shape) outweighs the marginal clarity of two narrower signatures.
  # --- Linear leg (FAFF-1083, behaviourally unchanged -- see DONE -> "Linear leg regression bar") ---
  m := run `faff native-map get --type <type> --json`
  IF m has an `id`:
     tmpl := get_template(id = m.id)
     IF tmpl found:
        fields := extract_field_headings(tmpl.content.description)
        IF fields not empty: RETURN fields                       # Linear-leg HIT
        REPORT opaque(type, m.id)
     ELSE:
        REPORT stale(type, m.id, m.name)
     # falls through to the GitHub leg, NOT straight to tier 2 (precedence: Linear wins on a hit only)

  # --- GitHub leg (NEW, this ticket) ---
  r := run `faff github-templates resolve --type <type> --json` with stdin {title, description}
  IF r.result == "hit":  RETURN r.fields                          # GitHub-leg HIT
  IF r.result == "ambiguous":
     IF invocation_mode == "interactive":
        # r.candidates are ALREADY sanitized + demarcated by the CLI itself (github-templates.js's
        # sanitize_for_display, run before JSON-encoding -- see WHAT -> Design decisions ->
        # Sanitization boundary). prompt_operator renders them EXACTLY as given: no re-fetching raw
        # name/about, no re-transformation, index-pick or decline only.
        choice := prompt_operator(r.candidates)
        IF choice is one of r.candidates: RETURN extract_field_headings(fetch(choice.path))
        # human declines / "none of these" -> fall through
     REPORT ambiguous(type, r.candidates)                         # autonomous, or a declined pick -> log + fall through
                                                                   # (see Edge cases for the exact log target)

  RETURN MISS   # -> tier 2 -> tier 3, unchanged
```

**Edge cases and error handling.**

- **No `.github/ISSUE_TEMPLATE*` in the working tree the fill step runs against** (git-only mode with no tracker connector, a tracker-connected repo that just doesn't have the directory, or — per the working-tree-materialization Assumes, WHAT → Design decisions — a non-materialized/shallow/detached checkout, if one is ever a real caller): GitHub leg misses; behaviour identical to pre-ticket in every case. The three causes are distinguishable in principle but not by this mechanism — a miss is a miss, and a miss never blocks, so no cause needs to be distinguished at fill time.
- **`.github/ISSUE_TEMPLATE/config.yml` only, no `.md` files**: treated as "no `.md` candidates" → check the bare-file fallback → miss if that's also absent.
- **A bare `.github/ISSUE_TEMPLATE.md` with classifiable front matter** (e.g. `name: Bug Report`): treated as a single-type candidate for its classified type only — **not** universal (see WHAT → Legacy singular file — universal-candidate gating).
- **A directory-form file whose front matter fails to classify**: stays `UNCLASSIFIED`, matches no requested type — never falls back to `EVERY_TYPE` (universal is bare-file-only).
- **Both legs would hit for the same type**: the Linear leg (confirmed-tier) is unconditionally authoritative; the GitHub leg is never even queried in that case (short-circuit on a Linear-leg hit) — not a scored comparison between the two, see WHY → Load-bearing model.
- **A same-type GitHub-leg candidate whose body carries no `## ` headings at all (opaque body, empty `fields`)**: *(New — QA-major fix, Empty-fields guard.)* not returned as a `hit` — `resolve`'s single-candidate branch reports it (`REPORT github_opaque(type, path, name)`, mirroring the Linear leg's `REPORT opaque` shape, into the same per-invocation narrative log) and returns `miss` for that type instead. This mirrors the Linear leg's own existing opaque-body guard, which the GitHub leg's single-candidate branch previously lacked.
- **Malformed front matter on one candidate among several**: that candidate's `front` degrades to `{}` (name falls back to filename stem, `about`/`labels` empty) — it still participates in classification/scoring on a weaker signal, it is not dropped.
- **Malformed/absent stdin JSON**: treated as empty title/description — weakens overlap scores toward ambiguity, never throws, never blocks.
- **Ambiguous with no interactive pick, or ambiguous under autonomous invocation**: falls through to tier 2/3 exactly like a Linear-leg miss. *(Fixed — was the review's QA-minor "log path/format undecidable" finding.)* Reported into the **same per-invocation narrative log** FAFF-1083's own `REPORT stale mapping`/`REPORT opaque mapping` lines already write to (`create.md:47,51`): the calling skill's `.faff/logs/YYYY-MM-DD/HHMMSS-jot.md` or `HHMMSS-plot.md` (kernel.md → **`.faff/` logging directory**, the "Decisions with reasoning" log-entry bullet — "what was expected, what was observed, what decision was taken, why"). The ambiguity entry names the type and every tied candidate's `path` + `name` + `score`, and the fall-through outcome — no new reporting channel, no new file.
- **`--type` outside the closed taxonomy**: `usageError`, exit 2, mirroring `native-map get`.
- **Error categories**: the `--type` argument error is terminal (exit 2); every miss/ambiguous/malformed-input condition is a non-error fall-through — none is retryable, none blocks creation.

**Failure modes — how the approach falls over, and how you'd notice.**

- **The failure:** `parseYamlSubset` doesn't parse a real-world front-matter `labels:` shape (the confirmed gap: an unquoted flow-list `labels: [bug, triage]` fails `scalar()`'s strict `JSON.parse` and is read as a plain string, not a list). **How you'd know:** the unquoted-flow-form scenario (Scenarios, and DONE → "From HOW (edge cases)") pins this exact degradation as a named, testable case — `labels` reads empty for that candidate; `classify_type` and `overlap_score` then rely on `name`/`about` alone (weaker on both axes now that `labels` also feeds scoring). **What it means:** proceed — `name`/`about` matching still functions (this is a *weaker signal*, not a broken one); narrow by extending `parseYamlSubset`'s flow-sequence handling only if real corpora show `labels` carrying signal `name`/`about` doesn't — a decision this ticket explicitly defers (WHAT → Design decisions → **Labels fixture form**, option (b) rejected for now).
- **The failure — recharacterized, not papered over.** Even with `labels` folded into the scorer, Jaccard overlap over `name`/`about`/`labels` remains an **opportunistic** signal, not a general one: `name`/`about` text is near-constant boilerplate across templates of a given type while ticket title/description is specific and per-ticket, so their token intersection is typically empty regardless of weighting; most real-world same-type template collisions will still have generic or absent `labels`, so the top-two scores will legitimately land at or near zero for every candidate alike. **How you'd know:** a fixture/corpus pass shows the `ambiguous` path firing on the clear majority of genuine same-type multi-candidate cases, with `hit`-via-score reserved for the minority of templates carrying a distinguishing, ticket-relevant label (see Scenarios → the labels-anchored-hit scenario, which demonstrates the minority case working). **What it means:** proceed — this is the mechanism working as designed (detect-and-defer, not forced-pick), not a defect to fix by further threshold tuning: when the top-two scores are both exactly 0 (the common boilerplate-vs-specific-text case), no threshold above 0 changes the outcome, so lowering `min_score` cannot rescue a mechanism with no signal to threshold. If the observed defer rate under real usage proves operationally too high (too many interactive prompts / autonomous fall-throughs), the correct next lever is a **structurally richer signal** — matching the template body's `## <Field>` heading text against ticket content, or an LLM-judged semantic match (see OUT OF SCOPE) — or reopening the onboard-time human-curation extension point, not a stronger heuristic squeezed further out of `name`/`about`/`labels` Jaccard, which this analysis shows has a hard ceiling given what real templates typically contain.

**Anti-patterns.**

- **Anti-pattern:** treating the two legs as symmetric peers, each with independent odds of winning per fill. Why: the confirmed-tier occupant (Linear, once populated for a type) is unconditionally authoritative — the GitHub leg's code path isn't even reached in that case (WHY → Load-bearing model). Framing it as a race would mislead a future third-occupant author into building unnecessary tie-breaking logic between tiers that structurally never compete.
- **Anti-pattern:** returning `hit` from the GitHub leg's single-candidate branch without checking `fields` is non-empty. Why: an opaque, headingless `.md` body would silently violate the seed-never-constrain invariant with a zero-field description — the Linear leg already guards this exact case; the GitHub leg's single-candidate branch must too (WHAT → Design decisions → Empty-fields guard).
- **Anti-pattern:** gating the GitHub leg on `tracking.tracker == "github"`. Why: `.github/ISSUE_TEMPLATE*` is a repo-hosting property, not a tracker-of-record property; this repo is the counter-example.
- **Anti-pattern:** letting the GitHub leg's discovery/scoring make an MCP call. Why: `.github/ISSUE_TEMPLATE/*` are local repo files — there is no tracker round-trip to make, and adding one would be a pointless lane violation.
- **Anti-pattern:** persisting the live ambiguity resolution (e.g., writing a "GitHub native map" file mirroring `.faff-templates/native-templates.yaml`). Why: this ticket's ambiguity is per-ticket (title/description vary every fill); persisting a pick would silently mis-apply it to the next, unrelated ticket of the same type.
- **Anti-pattern:** prompting under `/faff-plot --autonomous` "just this once" because the tie looks obvious. Why: `autonomous.md`'s no-prompt invariant has no severity carve-out; genuine ambiguity under autonomous invocation is a fall-through, not a judgment call for the agent to override.
- **Anti-pattern:** treating front-matter `labels`/`name`/`about` text as anything but data for scoring. Why: kernel's untrusted-input no-execute floor applies to committed template files exactly as it does to tracker free text, per this ticket's own explicit instruction.
- **Anti-pattern:** applying the bare-file's `EVERY_TYPE` universal fallback to a directory-form file that fails to classify. Why: a stray unclassifiable file sitting alongside type-specific siblings most plausibly means "doesn't apply here," not "applies to everything" — universal promotion is a property of the single-legacy-file shape, not of classification failure in general.
- **Anti-pattern:** treating a low overlap-scorer hit-rate as a bug to fix by lowering `min_score` toward zero. Why: when top-two scores are both exactly 0 (the common case), no threshold above 0 changes the outcome — the correct escalation is a richer signal, not a lower number (see Failure modes).
- **Anti-pattern:** rendering unsanitized template `name`/`about` text as prompt copy, or asking the operator to type the template's name back to confirm a pick. Why: both make a committed-but-attacker-influenceable string do double duty as an instruction to a human — exactly the display-channel injection surface the prompt-neutralization principle forecloses. (The CLI itself never emits raw `name`/`about` in an `ambiguous` result — see Sanitization boundary — so there is no raw text left for an implementer to accidentally wire up.)

## Design Decision Rationale

**Repo-gated or tracker-gated?**
- *Tracker-gated* (`tracking.tracker == "github"`) — simpler condition, but misses exactly this repo's own shape (Linear tracker, GitHub host) and any repo like it.
- *Repo-gated* (filesystem presence of `.github/ISSUE_TEMPLATE*`) — matches what the feature actually is: a GitHub-hosting artifact, independent of backlog-tracker choice. **Chosen:** repo-gated. (decides: architecture)
- **Named separately, not conflated:** repo-gated only settles the tracker axis. Whether the filesystem check runs against a fully-materialized working tree is a second, independent axis — this ticket assumes it does (see WHAT → Design decisions → **Working-tree materialization**) rather than claiming the detection is checkout-state-agnostic. Re-reading `faff-jot/SKILL.md` and `faff-plot/SKILL.md` in full found no language guaranteeing a non-shallow/non-detached checkout at the fill step's call sites, so this is named as an **Assumes**, not folded into the "repo-gated" claim as if it were proven.

**Where does the GitHub leg sit relative to the Linear leg?**
- *A sibling function jot/plot call independently* — duplicates the "try tier 1, then tier 2/3" control flow FAFF-1083 already wrote once.
- *A second sub-step inside `resolve_native_template`* — one control-flow home, one first-match-wins chain. **Chosen:** the second sub-step, tried after the Linear leg.

**When both legs could hit the same type, who wins? — and is this actually a competition?** *(Revised — fixes the review's architectural-major "symmetric two-occupant slot" finding: the round-3 framing below answered "who wins" as if it were a live tie-break, which mischaracterizes what actually happens.)*
- *GitHub wins* — no basis: it's discovered fresh, uncurated, at fill time, with no human confirmation behind it.
- *Frame it as two peers racing, tie-broken toward Linear* — the round-3 framing. Produces the identical runtime outcome, but mischaracterizes the invariant: once the Linear leg's map is populated for a type, the GitHub leg was never actually in contention — there is no live comparison happening at all. Look at `resolve_native_template` below: the Linear-leg block either `RETURN`s on a hit or falls through unconditionally; the GitHub leg's line is never even reached in the hit case. Calling that a "race, tie-broken toward Linear" implies a comparison this control flow doesn't perform, and would mislead whoever adds a third occupant into building unnecessary N-way tie-breaking logic between tiers that structurally never compete.
- *Name the real relationship: confirmed beats heuristic, unconditionally, when populated* — the Linear leg's mapping passed a human confirm at onboard time (FAFF-1081 step 3b); that's not "a stronger score in a race," it's a categorically different kind of answer that a live, per-fill heuristic (no human in the loop) was never in a position to outrank. **Chosen:** this framing. The GitHub leg is consulted only for a type the Linear leg's map leaves unpopulated — it is the fallback for a gap, not a contestant. See WHY → Load-bearing model for how this generalizes to a future third occupant (declare confirmed-tier or heuristic-tier; heuristic-tier stacks below all confirmed-tier occupants, in an unspecified order among themselves).

**Where does the GitHub leg's logic live — skill prose (like tier 2) or a CLI verb (like the Linear leg)?**
- *Skill prose*, mirroring tier 2's current style — smallest footprint, but a multi-file scan + type classification + Jaccard scoring is materially more logic than tier 2's single-file Read, and none of it is unit-testable without a real CLI surface.
- *A new pure CLI verb*, mirroring `native-map.js`'s precedent — testable via the same real-CLI black-box harness pattern (`test/native-map.test.mjs`), and there's no MCP dependency forcing it into the skill lane the way the Linear leg's `get_template` call does. **Chosen:** a new pure CLI verb (`github-templates resolve`). (decides: architecture)

**How is a candidate's type inferred, and does it risk drifting from FAFF-1081's onboard heuristic?** *(Revised — fixes the review's architectural-minor "false verbatim claim" finding.)*
- *Reuse FAFF-1081's onboard-proposal heuristic verbatim* — the prior draft's framing. Doesn't hold on inspection: `faff-onboard/SKILL.md` step 3b's actual heuristic (re-read in full for this revision) is a prose-described suggestion with a "no confident match → suggest unmapped" fallback, not a regex keyword table — there is no "verbatim" table to reuse without inventing the regex this ticket needs anyway.
- *Extract FAFF-1081's onboard heuristic into a shared, code-level classifier both legs call* — would genuinely close the drift risk between the two legs, but FAFF-1081's heuristic is shipped, prose-only, human-reviewed logic with no dedicated code module; extracting it is a nontrivial refactor of already-shipped work, not a small addition — scope creep beyond this ticket's narrowed delta.
- *A new, GitHub-leg-specific heuristic, honestly framed as inspired-by-not-identical-to FAFF-1081's proposal shape, with the drift risk named as an accepted tradeoff* — smallest footprint, ships today, and doesn't overstate what it guarantees. **Chosen.** The two legs' classifications are independent and may disagree on an ambiguous template name — an accepted, named tradeoff, not a hidden one. (decides: architecture)

**Should the universal-candidate fallback apply to any file that fails to classify, or only to the bare legacy file?** *(New — fixes the review's QA-major "direct contradiction" and architectural-minor "unconditional imposition," the same root bug from two lenses.)*
- *Apply to any unclassifiable file, directory-form or bare* — simpler rule, one code path — but a stray unclassifiable file sitting alongside type-specific siblings most plausibly means "doesn't apply here," not "applies to everything"; treating it as universal would silently multiply candidates for every type on a parse/classification miss.
- *Restrict to the bare, single-legacy-file shape only, and only when it comes back `UNCLASSIFIED`* — matches the actual design intent (a repo with exactly one legacy template almost always intends it for everything) without over-applying the same logic to a directory that already has type-specific structure. **Chosen:** restrict to the bare-file path, gated on `UNCLASSIFIED`; `discover_candidates` passes `universal_eligible` explicitly so `build_candidate` never has to guess which shape it's in, and the procedure now literally matches the DONE criterion's own wording ("with no classifiable front matter").

**How is ambiguity resolved once GitHub can expose multiple same-type candidates?**
- *(i) Live type-then-keyword-overlap scoring across GitHub's candidates only* — Linear's ambiguity is already structurally closed (FAFF-1081's map stores 0-or-1 per type; there is nothing left to disambiguate there). This narrowed ticket's only genuine multi-candidate case is GitHub's directory form.
- *(ii) Extend `faff-onboard` to add a GitHub-side onboard-time human-curation step*, mirroring step 3b for Linear — would resolve ambiguity once, per repo, at onboard, closing the gap the same way Linear's is closed. Rejected for this ticket: it's a materially larger surface (a new onboard step, a new persisted mapping file, a new writer verb with its own round-trip discipline) than the ticket's narrowed delta calls for, and per-fill scoring is still needed regardless (a repo's `.github/ISSUE_TEMPLATE/` can gain a new file between onboard runs, with no onboard re-run to catch it — onboard's own re-run rule is "never clobbers", not "re-scans").
- **Chosen:** (i), live scoring, this ticket. (ii) is named as an explicit extension point if live scoring proves too imprecise or too defer-heavy in practice — not a rejection of the idea, a sequencing call. (decides: architecture)

**Does a domain label alone (e.g. `security`) satisfy the type gate?** *(New — fixes the review's architectural-major "structurally dead for its own headline case" finding.)*
- *Treat a domain word as an implicit type alias* (e.g. special-case `security` → `bug`) — would let a domain-only-labelled candidate reach the scorer, but silently grows the closed six-type taxonomy's matching surface with product-undecided domain vocabulary — exactly what OUT OF SCOPE → **Replacing faff's six-type taxonomy with GitHub's vocabulary** already forecloses, and it doesn't stop at `security`: any domain word anyone's `labels:` happens to use would need the same special-casing, with no principled stopping point.
- *Leave the mechanism as originally specified and just soften the worked example's language* — doesn't hold: the underlying claim (labels give the scorer "a real path to a confident hit") would remain untrue for the case actually cited, because `classify_type`'s `same_type` gate runs *before* `overlap_score` ever does; no amount of caveat language changes that a domain-only-labelled candidate never reaches the function being described.
- *Recognize that `classify_type`'s haystack already includes `labels` (it does — `lowercase(name + " " + about + " " + join(labels," "))`), and be honest about what that does and doesn't buy* — a type keyword living in a `labels:` entry (e.g. `labels: bug`) satisfies the gate exactly as one in `name`/`about` would; a domain-only label with no type keyword anywhere on the file does not, and cannot, by construction. **Chosen.** Pick a worked example (the labels-anchored-hit scenario) where a type keyword already satisfies the gate — via `name`, as the corrected example does — and let a co-occurring domain label do the real disambiguating work in `overlap_score`. This is honest about the mechanism's actual reach rather than describing a case the code can't produce. (decides: architecture)

**Does the overlap scorer select among same-type candidates, or detect-and-defer?** *(New — fixes the review's architectural-major "practically dead" finding. Genuine analysis, not a caveat bolted on.)*
- *Engineer a stronger selection heuristic* (weight `labels`, lower `min_score`, mine the template body) — this ticket does fold in weighted `labels` (a real, if partial, improvement over `name`+`about` alone), but that cannot close the gap for the common case: `name`/`about` is near-constant boilerplate ("Bug Report", "Describe the bug") while ticket title/description is specific and per-ticket, so their token intersection is typically **exactly** empty, not just below 0.15 — and lowering the threshold below a floor of zero intersection creates no signal that wasn't there. A stronger heuristic squeezed further out of the same three fields (`name`/`about`/`labels`) has a hard ceiling given what real GitHub issue templates typically contain.
- *Recharacterize the mechanism honestly as detect-and-defer* — the scorer's real, achievable job is to catch the minority of cases where a genuine lexical anchor exists (chiefly via curated `labels` that happen to name the ticket's actual domain) and safely default to a human prompt or a logged fall-through otherwise. **Chosen:** detect-and-defer, with the labels-weighted scorer as a genuine (if partial) improvement over `name`+`about` alone — not a claim that the mechanism reliably picks among boilerplate-indistinguishable templates. The acceptance-criteria framing and the DONE items throughout this spec are written to this honest characterization (see WHAT → Ambiguity-resolution shape, and the labels-anchored-hit scenario demonstrating the real minority-case win). **Named as an accepted tradeoff, not glossed over** *(new this round — architectural-minor: "the scoring machinery is largely inert per the spec's own analysis")*: this scorer is deliberately kept simple despite a low expected hit-rate in the common case — it captures the minority of cases where a genuine lexical anchor exists (see Failure modes), and it is the natural extension point once a richer disambiguation signal (see OUT OF SCOPE → **A structurally richer disambiguation signal**) is available; building nothing here would mean re-adding a scoring mechanism later rather than incrementally improving one already in place and already tested. (decides: architecture)

**How does the ambiguity prompt handle untrusted candidate text, and where does the neutralization actually happen?** *(Round 2 fixed the infosec-minor finding; round 3 fixes the follow-on infosec-minor finding that the neutralization wasn't enforced by anything testable.)*
- *Render `name`/`about` as-authored* — simplest, but a crafted `name:`/`about:` (attacker-influenceable via a PR or fork, per the untrusted-input floor) becomes a prompt-injection/social-engineering surface against the human reading it, and the existing floor's "never executed" language was written for agent-side handling, not the display channel.
- *Neutralize the display, restrict the interaction to an index-pick, but leave the demarcation to `prompt_operator`'s own rendering* — the round-2 shape. Doesn't hold up: `sanitize_for_display`'s literal contract (truncate + strip control characters) is satisfiable while still rendering the result in a plain, undemarcated list — `prompt_operator`'s demarcation obligation was unspecified prose with no test oracle.
- *Make the demarcation a property of `sanitize_for_display`'s own output, moved into the CLI verb* — the truncated/stripped text is wrapped in a fixed `[untrusted template text] "…"` convention **before** it ever leaves `faff github-templates resolve --json`, so the sanitized-and-demarcated string is the CLI's own directly-assertable output. **Chosen.** `prompt_operator`'s only remaining obligation is to render that string verbatim and accept an index pick or decline — nothing left to under-specify. See WHAT → Design decisions → **Sanitization boundary**.

**Does the live prompt mirror onboard step 3b's shape?**
- Onboard step 3b's collision resolution is per-repo, once, and its outcome is **persisted** (a durable map entry).
- This ticket's ambiguity is per-ticket, live, and its outcome must **never** be persisted (today's tie between two feature templates says nothing about tomorrow's unrelated feature ticket).
- **Chosen:** borrow the *presentation* shape (a skimmable named-and-scored candidate list, confirm-not-interrogate — now additionally rendered as neutralized display data) but not the *persistence* — these are genuinely different shapes at the storage layer even though the human-facing gesture rhymes.

**Does the prompt ever fire under autonomous invocation?**
- *Fire it anyway when the tie "looks obvious"* — explicitly banned by `autonomous.md`'s no-prompt invariant; there is no severity carve-out for a judgment call that "feels safe."
- *Never fire under autonomous invocation; treat as MISS* — consistent with every other tier-1 fall-through, and with `/faff-plot --autonomous`'s existing create-time fill step, which already tolerates a miss without blocking. **Chosen:** never fire under autonomous invocation.

**How does `invocation_mode` reach `resolve_native_template`?** *(New — fixes the review's architectural-major finding that the "needs no new state" claim cited lines that were never read and don't say what was claimed.)*
- *Assume it's already available with no new plumbing* (the original framing) — doesn't hold on inspection: `create.md` establishes no `invocation_mode` value anywhere today, and the originally-cited `faff-jot/SKILL.md:143-151` spans jot's tracker-less-mode item-keying and the start of its Autonomous-mode section — it describes tracker-presence branching (git-only vs tracker) and jot's own bail-to-`.faff/intake` behaviour, neither of which threads a mode value into a fill-step call.
- *Thread one new parameter from each caller's own already-resolved value* — jot's call site is always `"interactive"` by construction (a genuinely autonomous jot invocation never reaches create/fill at all, per its Autonomous-mode section); plot's call site passes its Ignition-resolved entry mode, since plot's Step 5 ("Write the skeleton") is the one call site genuinely invoked both under interactive `/faff-plot` and `/faff-plot --autonomous`. **Chosen:** the latter — one new parameter through an existing call, added to `create.md`'s fill-step signature and to plot's Step 5 prose; it does not touch the Linear leg's own logic. (decides: architecture)

**Should the GitHub leg's single-candidate branch return `hit` on an empty `fields` list?** *(New — fixes the review's QA-major "no empty-fields guard, unlike the Linear leg" finding.)*
- *Return `hit` unconditionally, as originally specified* — simplest, one fewer branch, but a same-type `.md` file written as plain prose (no `## ` headings) would then produce `fields: []` — a ticket with zero structure, not "thin-but-structured" — silently violating the seed-never-constrain invariant, and inconsistently with the Linear leg, which already guards this exact case.
- *Guard it, mirroring the Linear leg's own `IF fields not empty: RETURN fields` / else `REPORT opaque`-and-fall-through shape* — costs one more branch and one more reporting call (`REPORT github_opaque`), but closes an asymmetry that had no principled reason to exist: there's no basis for the GitHub leg's single-candidate path to be less careful about opaque bodies than the Linear leg is about opaque tracker templates. **Chosen.** See WHAT → Design decisions → **Empty-fields guard on the GitHub leg's single-candidate hit** for the exact mechanism. (decides: architecture)

## Open Questions and Assumptions

**Open Questions.**

- **Punt (decides: product):** the exact `min_score` / `min_margin` values that separate a confident GitHub-leg pick from a forced ambiguity prompt. Carried forward from FAFF-1070's own original open question, narrowed to the one leg where live ambiguity can occur (Linear's is structurally closed by FAFF-1081). Non-blocking: `faff github-templates resolve` ships defensible defaults as overridable flags (suggested: `min_score 0.15`, `min_margin 0.05`, echoing the parent ticket's own suggested default), so the mechanism is buildable and testable today; product tunes the numbers against real template corpora without any further code change. Given the detect-and-defer recharacterization (Design Decision Rationale), the practical effect of these defaults is calibrating **how eager the mechanism is to defer** versus attempt an opportunistic labels-anchored hit — not whether ambiguity resolution "works" at all; a low observed hit-rate under real corpora is expected, not a signal the defaults are broken.

**Assumptions.**

- **Assumes:** `parseYamlSubset` (`shared-infra.js`) parses real-world GitHub issue-template front matter well enough for `name`/`about`/`labels` extraction, including a block-list `labels:` form. *Validation (build agent, before relying on `labels`):* feed `parseYamlSubset` 2-3 real front-matter fixtures (GitHub's own docs examples, or a few popular OSS repos' `.github/ISSUE_TEMPLATE/*.md`) covering `labels: bug` (bare scalar), `labels:\n  - bug\n  - triage` (block list), and `labels: [bug, triage]` (unquoted flow — **known to fail**, per `scalar()`'s strict-`JSON.parse` gate). If the unquoted-flow form shows up often in practice, either extend `parseYamlSubset`'s flow-sequence handling (coordinate — it's shared with `config.js`/`native-map.js`) or accept `labels` as a best-effort, sometimes-empty signal and rely on `name`/`about` as the primary matcher (already the design's fallback; nothing breaks if `labels` stays empty). This assumption is now load-bearing for **both** `classify_type` and `overlap_score` — see WHAT → Front-matter parser. The decidability gap this creates for the spec's own scenarios is resolved separately, not left implicit — see WHAT → Design decisions → **Labels fixture form**: the labels-anchored-hit scenario is pinned to the block-list form, and a second, explicit scenario pins the unquoted-flow form's degraded behaviour.
- **Assumes:** `/faff-jot`'s Step 4 and `/faff-plot`'s Step 5 — the only two `resolve_native_template` call sites — always run against a real, checked-out local working tree when the fill step performs its filesystem check for `.github/ISSUE_TEMPLATE*`. *Validation (build agent, before relying on it):* re-read `faff-jot/SKILL.md` and `faff-plot/SKILL.md` in full at build time to confirm neither documents a shallow, sparse, or detached-HEAD invocation path (this revision's own re-read, and the closest available citation — `kernel.md` → **Agent Lanes → Orchestrator**'s "codebase, read-oriented" visibility grant — found none that goes as far as a guarantee). If a future caller ever adds one, the working-tree check silently reads as absent for that invocation — a **safe, closed failure** (the GitHub leg degrades to a miss, never a false hit, per the seed-never-constrain invariant), not a build-blocking one. This assumption is orthogonal to the git-only-mode axis (WHY → Design principles, **Repo-gated, not tracker-gated**): "no tracker connector" and "no materialized working tree" are two different conditions, and only the first is what repo-gating disclaims dependence on. See WHAT → Design decisions → **Working-tree materialization**.

Verified by the opaque-body scenario and smoke-test step 9.
- [ ] **(New — `filename_stem` test oracle.)** A candidate file with no `name:` front-matter key resolves `name` to the exact `filename_stem(path)` rule: the basename with its `.md` extension stripped and every `_`/`-` replaced with a space (e.g. `bug_report.md` → `bug report`, `needs_triage.md` → `needs triage`) — not the raw filename, not the full path. Verified by the `filename_stem` scenario and smoke-test step 10.

## Methodology critique

Methodology: faffter-dark-methodology-agile-delivery

Critiquing the narrowed spec (GitHub-leg discovery/parsing + live ambiguity resolution + control-flow integration), not the original ticket wording — the split/narrow decisions already happened.

**Right-sized? (principle 4)**

What's there: the narrowed spec still bundles two structurally independent occupants into one ~13-decision, complex-tier build: (1) the GitHub-file discovery/parsing occupant — reading `.github/ISSUE_TEMPLATE/*.md` and `.github/ISSUE_TEMPLATE.md`, parsing frontmatter into candidate structures — and (2) the live ambiguity-scoring mechanism — a new `faff github-templates resolve` CLI verb, Jaccard keyword-overlap scoring, and an interactive-only operator-prompt path on a genuine tie, plus the `create.md` control-flow wiring and the two SKILL.md pointer edits.

Why it's a problem: these two are separable and independently shippable. (1) can be built and selftested against static fixture files with no scoring logic at all (it just needs to produce a candidate list); (2) can be built and tested against synthetic candidate lists with no real GitHub repo needed. The project's own precedent one slice up treated exactly this discovery-vs-apply seam as two tickets — FAFF-1081 (discover the Linear mapping) and FAFF-1083 (fetch/apply it at create time) were split and shipped separately. This ticket re-merges the equivalent seam for the GitHub leg into a single unit, which is how a 1-3 day ticket becomes a multi-day one that sits "in progress" without visible partial progress.

What to do about it: split into (a) GitHub-template discovery/parsing (walk `.github/ISSUE_TEMPLATE*`, parse frontmatter, return typed candidates — no scoring, no CLI verb) and (b) the `github-templates resolve` verb + Jaccard scoring + tie-prompt + `create.md`/SKILL.md wiring, which consumes (a)'s output. (a) can ship and be selftested on its own; (b) becomes a clean, independently reviewable unit that also isolates the interactive-prompt risk (see risk profile below) from the parsing risk.

**Workstream fit? (principles 1+5)**

No issues. FAFF-1060's outcome — "unified repo + tracker convention/template scan feeding onboard + jot's create path" — still covers this delta cleanly: it's the one remaining occupant of the tier-1 native-template slot the epic exists to populate. The scope shrinking doesn't create a cohesion problem, since what's left (GitHub-leg discovery + live resolution) is still squarely "template scan feeding jot's create path," not a drifted theme. One observational note, not a violation: once this ships, FAFF-1060 has no live children left (1068, 1069, 1081, 1083 all Done) — worth closing the epic in the same pass rather than leaving a drained-but-open parent.

**Deps surfaced? (principle 6)**

What's there: checked live tracker state directly. FAFF-1083 is Done (completed 2026-09-22, PR #928). FAFF-1081 is Done (completed 2026-09-22, PR #925/#929). FAFF-1069 is Done (completed 2026-09-21, PR #918). The spec's citations of all three as Done match live state — no discrepancy there. Its Linear description also still reads as the pre-narrowing ticket (it still describes building the Linear `list_templates`/`get_template` leg as part of this ticket's own scope) — it hasn't been updated to reflect that leg now lives in 1083/1081.

Why it's a problem: this ticket's `create.md` control-flow work builds directly on top of the tier-1 resolution order and control flow that FAFF-1083 already wrote and shipped — that's a real code dependency, not just a conceptual one, and it's currently invisible in the graph. What to do about it: add explicit `relatedTo` links from FAFF-1070 to FAFF-1083 and FAFF-1081 (informational, since both are Done — not a blocker in the sequencing sense, but a "builds on this code" signal), and refresh FAFF-1070's description to reflect the narrowed scope so the raw issue doesn't contradict the attached spec.

**Risk profile? (principle 7)**

What's there: the spec's own `**Assumes:**` flags a gap in `parseYamlSubset`'s handling of flow-sequence YAML (`labels: [a, b]`). Direct inspection of `plugin/skills/faff/bin/lib/shared-infra.js`'s `scalar()` (lines 308-324) confirms it: a `[...]` value is only parsed as an array via `JSON.parse`, which requires double-quoted string elements. An unquoted flow sequence like `labels: [bug, needs-triage]` — the near-universal real-world style GitHub issue-template frontmatter uses — fails `JSON.parse` and silently falls through to being returned as the literal string `"[bug, needs-triage]"` rather than throwing.

Why it's a problem: this isn't a rare edge case reachable only by unusual input — it's the common case for exactly the file format this greenfield leg is being built to parse. Because the failure mode is silent (a wrong-shaped string, not an exception), a bug here would corrupt type/keyword matching quietly rather than surfacing — the worst kind of risk to leave as a build-time footnote in decision 12 of 13. It's compounded by this repo's own tracker being Linear (per `.faffrc.yaml`): the GitHub-tracker leg can never be dogfooded live in this repo, so the only validation path is synthetic fixtures/selftest — meaning a quiet parsing bug here has no live usage to catch it before it ships to a consuming repo.

What to do about it: don't fold this into the main build as an assumption. Either (a) fix `parseYamlSubset`'s flow-sequence scalar handling as a small precursor task that gates the GitHub-discovery occupant, or (b) if the resolve/scoring logic genuinely never needs `labels:` (only `name`/`about`/`title`/body for type + keyword matching), state that explicitly as a scoping decision in the spec and add a selftest fixture with an unquoted `labels: [a, b]` frontmatter line that asserts it's ignored/tolerated rather than silently corrupting a used field. Left as-is, "Assumes" undersells a confirmed, common-case, silent-failure gap.

*(Revision-pass note: this critique predates the fix that made `labels` a 70%-weighted input to `overlap_score`, which makes the flow-sequence parsing gap named here strictly more load-bearing than when the critique was written — not less. The Risk profile finding's "don't fold this into the main build as an assumption" recommendation stands, and arguably strengthens, post-revision; it was not one of the review's 8 objections and is left as the methodology lens's own open finding for the human gate to weigh, not resolved by this pass.)*
