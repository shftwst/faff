## 1. WHY — problem and principles

**The load-bearing model: two homes for the same fact, at two different scopes.** A spec-local `(ratified: human)` suffix on a `**Chosen:**` line and a `docs/decisions.md` `ratified_tradeoff` register entry both say "a human settled this," but they answer to different readers. The suffix is read by the spec-review design lenses off the spec body itself, on every round, before any register write completes — it closes the round-to-round gap. The register entry is read by `faff ratified-scope --assemble` and is durable across sessions, re-preps, and future tickets that cite this one. Neither substitutes for the other; this spec adds both, wired to the same triggering event.

**Problem statement.** A `**Chosen:**` marker records that a decision closed, not who closed it. An agent's own inference and a human's live, in-session say-so carry different weight — a reviewer may legitimately re-open the first, never the second — but today's spec text and the spec-review lenses cannot tell them apart. FAFF-1072 paid for this: the adversarial spec-review's architectural lens spent a full round challenging an activation axis the operator had already ratified live, because nothing about the spec or the review inputs distinguished that decision from an ordinary agent-authored `**Chosen:**`. This change adds the missing provenance and wires the one consumer that already has a defer-or-pass-through mechanism (the L4 adversarial spec-review) to use it.

**Design principle: the tag is authored mechanically, in response to an identifiable human utterance — never inferred.** The suffix and the register entry both exist to make a *fact* durable: a human, live, in this session, said "that's settled." Neither is ever added because an agent judges that a human "seems to agree," and neither is ever added on an autonomous dispatch, because no human utterance can occur there. An implementation that lets the `spec` producer decide on its own to add `(ratified: human)` — instead of the orchestrator appending it in direct response to a named human reply — reintroduces exactly the self-grading risk this ticket exists to remove, even if it passes the scenarios below.

**Design principle: deferral is downgrade-to-observation, never suppression, and never for `critical`.** This mirrors the three deferral clauses `faffter-dark-spec-review` already ships (non-goals, ratified goals, tracker-thread resolutions): a design lens that would object anyway records the objection as a cited `observation` instead of a gating finding; a `critical` objection always passes through regardless of any ratification. An implementation that lets a human ratification hard-suppress an objection, or that lets it soften a `critical`, breaks an existing, deliberate safety floor and is rejected even if it converges specs faster.

**Design principle: this is a prose convention, never a contract field.** `faff-contract:spec-readiness`'s `decisions[]` stays `{ marker: "chosen"|"punt"|"assumes"|"none" }`; `faff-contract:spec-review-verdict`'s objection schema is untouched. This mirrors the committed FAFF-356 decision that the existing `(decides: <owner>)` Punt suffix is prose-only display metadata, never a schema field — and it is how FAFF-1072's own out-of-scope note ("do not add a `(ratified: human)` suffix or a new marker field") is honoured: that note rules out a *contract* field, not a *prose* convention identical in kind to one the schema already excludes by design.

## 2. Out of scope

- **A `ratified`/`decides`-style field on `faff-contract:spec-readiness` or `faff-contract:spec-review-verdict`.** Excluded — FAFF-356 already ruled this class of metadata prose-only for `decides:`, and this ticket's own evidence shows the same schemas are `additionalProperties: false` by design. Extension point: `plugin/skills/faff/bin/lib/contract-defs.js` + `plugin/skills/faff/contracts/*.schema.json`, if a future ticket makes the case.
- **Deferral logic in the default `faffter-noon-spec-review` (L1–L3) occupant.** Excluded — that occupant has no `## Ratified scope` machinery at all today (it is not a partial gap this ticket widens, it is a different occupant entirely). Extension point: `plugin/skills/faffter-noon-spec-review/SKILL.md`, a separate ticket.
- **Expiry/staleness of a `ratified_tradeoff` entry.** Excluded — `ratified-scope.js` already documents this as a known v1 gap ("no scope/topology expiry enforcement... v2 owns automatic expiry"), unrelated to who may write the entry. Extension point: the v2 expiry work already named in that file's comments.
- **Widening `faff decisions match --punt` to consult `ratified_tradeoff` entries.** Excluded — `matchDecision` deliberately treats tradeoffs as a distinct consumer path (FAFF-910); this ticket does not reopen that split.
- **A combined single offer that drafts both a cross-ticket precedent and an issue-scoped tradeoff from one event.** Excluded as unnecessary ceremony for v1 — the two shapes serve different purposes (see WHAT) and a human wanting both can accept the offer twice or hand-edit the register. Extension point: the Decisions-register capture step, if demand appears.
- **Retroactively tagging decisions in specs already attached before this change ships.** Excluded — this is a forward-only convention; an absent tag continues to mean "agent-chosen," which is the same reading it has today.

## 3. WHAT — vocabulary, the tag grammar, and the two register shapes

### Vocabulary

| Term | Definition |
|---|---|
| Ratifier tag | The optional `(ratified: human)` suffix on a `**Chosen:**` line — prose-only and schema-absent like `(decides: <owner>)`, but unlike `decides:` it gates a real downstream outcome (spec-review's severity classification), not just a display bucket. |
| Agent-chosen | A `**Chosen:**` with no ratifier tag — today's behaviour, unchanged. |
| In-spec ratification | The spec-local signal: a design lens reads the tag directly off the spec body (`--diff`), no register or context block required. |
| Register-durable ratification | The `docs/decisions.md` `ratified_tradeoff` entry (`Ratified-by: human`), surfaced via `faff ratified-scope --assemble`'s `### Ratified tradeoffs (docs/decisions.md)` subsection to every lens's `--context`. |
| Precedent shape | Today's Decisions-register capture draft: `Chosen`/`Rationale`/`Scope`/`Matches` — a cross-ticket, fuzzy-matched pattern for future punt resolution. |
| Tradeoff shape | The `ratified_tradeoff` draft: `Chosen`/`Rationale`/`Scope`/`Source-issue`/`Ratified-by: human`/`Date` — an issue-scoped citation, never fuzzy-matched, consumed only by `ratified-scope --assemble`. |

### The tag grammar (kernel.md addition)

```
Chosen-line     := "**Chosen:**" prose [ratifier-tag]
ratifier-tag    := "(ratified: human)"
                    # closed vocabulary of exactly one value in v1 — "human".
                    # No "loop"/"agent" value exists: the absence of the tag
                    # already means agent-chosen, so there is nothing a second
                    # value would distinguish.
```

Absent tag → agent-chosen (today's behaviour, fully back-compatible). The tag is never parsed into `faff-contract:spec-readiness` — a tagged `**Chosen:**` still emits `{ "marker": "chosen" }`, identical to an untagged one, exactly as a tagged `**Punt:**` still emits `{ "marker": "punt" }`.

### Who may write the tag, and when

**Chosen:** the orchestrating skill (faff-prep) appends the tag to an already-written `**Chosen:**` line as a mechanical edit, in direct response to one of exactly two named events — never the `spec` producer's own initiative, never *added* on an autonomous dispatch. The two events:

1. **A human closes an open `**Punt:**`/`**Assumes:**`** (today's existing trigger for the Decisions-register capture step, unchanged in when it fires).
2. **A human explicitly overrules a non-`critical` design-lens objection against the *decision itself* (never against the decision's *implementation* — see HOW Decision 2's scope test) that names an already-`**Chosen:**` decision** during the Spec-review gate's round loop (new — see HOW Decision 2).

**"Never added on an autonomous dispatch" governs writing, not carrying.** An autonomous stale-refresh (Path 1) that re-attaches an already-tagged spec preserves every existing `(ratified: human)` tag verbatim — Path 1 is documented as a scoped, annotated refresh of an already-vetted spec, never a whole-cloth redraft, so a tag earned in a prior interactive session is inherited unchanged. Only the *act of adding a new tag* is gated on an interactive human reply; a tag already sitting in the spec text is durable content like any other `**Chosen:**` line, carried forward exactly as the rest of the spec is.

**Audit trail (the human utterance itself, not just its result).** Both trigger events already write a tracker comment today — the resolve-attempt/Punt-closure flow, and (new, per Decision 2 step 3b) the Decisions-register capture offer. Extend both comment sites to quote the human's reply alongside the resulting tag — never just "tag added," always "tag added because the human said: '<quote>'." This makes the tag's provenance independently checkable against the tracker thread rather than resting on trust in the orchestrator's own mechanical-edit claim.

**The quote is neutralised before it is written, never raw — concretely, not just "some treatment."** The human's reply is free text from an interactive turn, so before it is written into the tracker comment it goes through the same structural-neutralisation transformation `faff ratified-scope --fold-resolutions` already applies to tracker values: newline collapse, secret-shaped-value redaction, imperative-sentence scrub (the identical function, reused, not a parallel reimplementation — see `plugin/skills/faff/bin/lib/ratified-scope.js`'s fold-resolutions neutraliser). On top of that shared transform, this site adds one more, specific to itself: extract the shortest sentence that states the decision (never the full multi-paragraph turn), then hard-cap it at 200 characters, truncating with `…` if the sentence itself exceeds that — a concrete, testable number, not an unbounded "shortest sentence." This is the same treatment for the same reason: the quote is later re-read by the Decisions-register reconcile step's in-context LLM judgement, so it must land as inert, bounded DATA there too, not as fresh untreated free text with its own injection surface. Like the scope test (Decision 2) and the tag's own authorship rule, this transform is orchestrator-applied prose discipline, not a mechanically-enforced parser — accepted on the same bounded-risk terms (section 6), not a gap unique to this one site.

**The tag survives every remaining round of the SAME spec-review loop, by construction, not by a re-attach guarantee this spec would otherwise have to newly establish.** Once step 4 appends the tag (Decision 2), the spec-review round loop's only two remaining actions on the spec text are: (a) further `revise` fixes for *other, still-open* objections, or (b) the terminal re-attach on `approve`. A `revise` re-invocation of the `spec` producer is **always instructed to carry every existing `(ratified: human)` tag forward verbatim** — the producer receives the current spec text (tags included) as its base and is never asked to redraft from scratch mid-loop; this is the same narrowing-only-refresh discipline `faffter-noon-spec`'s own self-review exemption already uses for a scoped revision, applied here to one more class of must-not-drop content. This is a same-session, same-loop guarantee only; it says nothing about a *later*, separate prep session's whole-cloth redraft (out of scope — see "Retroactively tagging" above), which is a different event this ticket does not touch.

Rationale in section 6.

### The two register shapes, and which event drafts which

**Chosen:** event 1 (Punt/Assumes closure) keeps drafting the **precedent shape**, unchanged — it answers "is this a reusable cross-ticket pattern," a question orthogonal to ratification. Event 2 (overruling a design-lens objection) drafts the **tradeoff shape** — it answers "don't relitigate this call for *this issue*," which is exactly what `ratified_tradeoff` + `ratified-scope --assemble` already exists to do. Rationale in section 6.

## 4. HOW — behaviour

### Decision 1: kernel.md gains the ratifier-tag bullet, sibling to `decides:`

Add a new bullet to the "Decision markers" list in kernel.md's _Spec readiness (fixed)_ section (~line 455, immediately after the existing "Punt ownership (optional)" bullet), at the same nesting level:

```
- **Ratifier tag (optional).** A `**Chosen:**` may carry a trailing `(ratified:
  human)` suffix, mirroring the `decides:` suffix above — `**Chosen:** X
  (ratified: human)`. Structurally identical to `decides:` in one specific,
  narrow sense: prose-only, never a `faff-contract:spec-readiness` field — a
  tagged Chosen still emits `{ "marker": "chosen" }`, so it never gates the
  spec-readiness/confidence contract. Absent tag = agent-chosen (today's
  behaviour), fully back-compatible.

  **Unlike `decides:`, this tag DOES gate a downstream decision** — it is
  not display metadata. `decides:` only routes a "Needs your call" render
  bucket; it changes no pipeline outcome. `(ratified: human)` changes
  whether a design lens's objection counts as gating or as an `observation`
  in the spec-review aggregate. The analogy to `decides:` is about *contract
  placement* (prose, not schema) — never about *effect* (routing vs.
  gating). This distinction is the reason the tag earns its own bounded-risk
  rationale (see gateway spec-review docs → `faffter-dark-spec-review` →
  Defer to ratified scope) rather than inheriting `decides:`'s "purely
  cosmetic" status wholesale.

  Who may write it: the tag records that a human's own live say-so, given
  in an interactive session (this one, when the tag is newly added; an
  earlier one, when the tag is an inherited carry-forward), settled or
  reaffirmed this exact decision — closing an open `**Punt:**`/`**Assumes:**`,
  or overruling a non-critical,
  decision-level (never implementation-level) spec-review design-lens
  objection to keep a decision as written (see faff-prep's Decisions-register
  capture step). It is appended by the orchestrating skill as a mechanical
  edit to the marker line, never by the `spec` producer's own inference, and
  never *added* on an autonomous dispatch — an autonomous run has no human
  present to supply the say-so a new tag records. A tag already present from
  a prior interactive session is preserved verbatim through an autonomous
  stale-refresh (a scoped annotation, not a redraft) — the "never added
  autonomously" rule governs new tags, not inherited ones. A `critical`
  design-lens objection is never settled this way — only `major`/`minor`
  objections are ratifiable in place.

  The durable, cross-ticket home for a ratified decision is `docs/
  decisions.md`'s `ratified_tradeoff` entry (`Ratified-by: human`); this tag
  is the spec-local echo of the same event, read directly by the spec-review
  design lenses off the spec body itself (see faffter-dark-spec-review →
  Defer to ratified scope).
```

**Anti-pattern:** treating the tag as evidence the producer itself should evaluate ("this reads as settled, I'll add the tag"). Why: the tag's entire value is that it names an event the LLM cannot fabricate — a specific human reply — not a texture the LLM infers.

### Decision 2: faff-prep's Spec-review gate gains a ratify path (interactive only)

Today (faff-prep/SKILL.md ~line 431), a design-lens `revise` or `reject-approach` verdict "loops in place (cap 2)" — the producer is re-invoked with the objection. Add a third path, offered only when the objection is `major`/`minor` **and attacks the decision itself, not its implementation**:

**The decision-vs-implementation scope test (must run before the offer fires).** An objection's `spec_anchor` names a section, not a decision — a design lens can attack *whether X was the right call* (decision-level: "cron is the wrong choice here") or *how X was executed* (implementation-level: "the cron schedule you wrote has an off-by-one" / "a decision correctly identified but badly built," the exact case Decision 4b's implementation carve-out names). Only a **decision-level** objection is ratifiable. Classify from the objection's own `claim`: does it argue against the choice, or against a mechanism/detail of carrying it out? An objection that is ambiguous between the two, or that mixes both, is **not** offered ratify — it routes through `revise` instead, since ratifying it risks silently suppressing the implementation half Decision 4b promises stays critiqued at full severity. This is a stricter gate than "names a `**Chosen:**` line": naming the line is necessary but not sufficient.

**Worked examples (the classification's anchor, not an exhaustive taxonomy).** Like `spec_anchor`'s own worked-examples convention, these three anchor the test's two ends and its fail-safe middle — they do not replace the "argue against the choice vs. a mechanism of carrying it out" test above, they calibrate it:
- *Decision-level (ratifiable):* "Postgres is the wrong store for this — use the file-based register instead" (attacks the choice itself).
- *Implementation-level (never ratifiable):* "The chosen Postgres migration has no rollback path" (accepts the choice, attacks its execution).
- *Ambiguous/mixed (never ratifiable, fail-safe):* "Postgres is fine, but this schema will lock the table under load" (a decision-adjacent implementation critique — the boundary case the fail-safe direction exists for).

**This is a bounded LLM classification, not a deterministic function — accepted, not hidden, and the asymmetry claim is a tested property, not an assertion.** There is no closed-vocabulary parser for "is this objection about the choice or its execution" the way `spec_anchor`'s heading-slug rule is mechanical; natural-language intent classification cannot be fully mechanised without also mechanising the objection-writing itself. The bound is the same shape as the self-attested-tag bound above (section 6): the failure direction is meant to be asymmetric and safety-biased (ambiguous → no ratify, never the reverse) — test-coverage item 5 is what makes that a checked property rather than a naming: it exercises the fail-safe middle worked example itself, not only the clean implementation case item 4 covers, so a scope test that handles unambiguous inputs correctly but defaults an ambiguous one the wrong way fails item 5 rather than shipping unnoticed. The blast radius of a misclassification that slips past both checks is still bounded to one non-critical objection kept in the loop rather than a defect shipping unexamined — the same posture the judge's own discrimination smoke already accepts for a structurally identical problem (classifying prose against no ground-truth oracle beyond a human-curated fixture), now with the boundary case named and tested rather than only asserted.

```
PROCEDURE surface_design_lens_objection(objection, decision_line):
  1. IF objection.severity == "critical":
     present it exactly as today — revise or park, no ratify offer
     (the severity floor is unconditional; see Decision 4)
  2. ELSE IF objection is ambiguous or mixed decision/implementation
     (the scope test above cannot cleanly classify it as decision-level):
     present it exactly as today — revise or park, no ratify offer.
  3. ELSE (major | minor, cleanly decision-level), interactive mode only:
     present three choices, not two:
       - revise    (today's path — loop the producer with the objection)
       - park/needs-human (today's path, on the loop-cap ceiling)
       - ratify    (new) — "keep <decision_line> as chosen; this call is
                    settled, do not revise it"
  4. ON an explicit human "ratify" reply (never inferred from silence
     or from the agent's own read of the conversation):
     a. Append "(ratified: human)" to decision_line's Chosen marker,
        as part of the same re-attach this round already performs.
     b. Log the human's reply verbatim (or its shortest decision-bearing
        sentence) into the tracker comment this re-attach already posts —
        see "Who may write the tag, and when" → Audit trail.
     c. Run the Decisions-register capture step's tradeoff-shaped
        offer (Decision 3 below) on this decision.
     d. Remove this objection from the round's must-fix set; it does
        NOT consume a loop-cap iteration (no revision happened).
     e. Continue the round for any other unresolved objections exactly
        as today.
  5. Autonomous mode: this offer never fires (no human to answer) —
     an autonomous revise/reject-approach proceeds exactly as today,
     unchanged.
```

**Behaviour summary.** A human can now say "no, keep it" to a design-lens objection that attacks the *decision* without either (a) forcing a pointless revision loop or (b) silently losing the fact that a human, not the producer, made that call — while an objection attacking the *implementation* (or one that mixes both) is never eligible, so ratifying a decision can never accidentally suppress a live implementation defect.

**Anti-pattern:** offering "ratify" for a methodology-lens objection. Why: a methodology `reject-approach` is a scope/sizing call routed to `/faff-plot`, never a "loop in place" revision — there is no single named `**Chosen:**` line to ratify against.

**Anti-pattern:** offering "ratify" on the strength of `spec_anchor` alone. Why: `spec_anchor` names the attacked *section*, not whether the attack is decision- or implementation-level — an implementation objection anchored to the same section as its decision would pass a naive "names a Chosen line" test and must not be ratifiable.

### Decision 3: the Decisions-register capture step gains a second draft shape

Extend faff-prep/SKILL.md's existing "Decisions-register capture step" (~line 327). Its trigger (item 1, "Offer... immediately after a human closes out a Punt/Assumes marker") is unchanged and keeps drafting the precedent shape (item 2, unchanged). Add:

```
**A second trigger — ratifying a design-lens objection in place (no punt
involved).** Immediately after Decision 2's ratify path appends the tag,
run this same offer: "Capture this as a ratified tradeoff for FAFF-XX,
so this issue's own spec-review defers to it? (y/n)". On yes, draft the
entry in the TRADEOFF SHAPE (not the precedent shape above):

  Chosen:       <the decision, verbatim from the spec>
  Rationale:    <why, folded from the objection + the human's reply>
  Scope:        <what this decision covers>
  Source-issue: <ISSUE-XX>
  Ratified-by:  human
  Date:         <today>

**Behaviour summary.** This clause is deliberately independent of the `## Ratified scope` context file: it is what closes the round-1→round-2 re-litigation gap even when the register capture (Decision 3) has not yet materialised — the tag lives in the spec text the lens already reads every round, regardless of register timing.

**Anti-pattern:** making this clause conditional on the `## Ratified scope` block being present. Why: that would tie the fast, spec-local signal to the slow, register-materialisation timing it exists specifically to not depend on.

### Failure modes

- **The register capture never lands before round 2 of the same session (no build has run yet, so Step 4c hasn't materialised anything).** How you'd know: `$scratch/ratified-scope.md` in round 2 still lacks a `### Ratified tradeoffs` entry for a decision the human ratified in round 1. What it means: this is expected and non-fatal — Decision 4b's in-spec clause defers on the tag alone, independent of register timing; the register path (4a) is the durable, cross-session backstop, not the round-2 mechanism. Narrow, not abandon.
- **A human says "ratify" meaning something weaker than "never re-open this."** How you'd know: a later round or a later re-prep re-raises the same concern and the human is surprised the tag exists. What it means: the tag is spec-local and reversible — re-prepping is free to drop or re-litigate a tag the same way any `**Chosen:**` can be revised; nothing about this mechanism makes a ratified decision immutable, only non-re-litigated *by an automated design lens* until a human (not the lens) reopens it.
- **The ratify offer is mistakenly wired to fire on a `critical` objection.** How you'd know: a design lens's `critical` finding disappears from a round record after a human reply. What it means: implementation bug, not a design tension — Decision 2 step 1 and Decision 4's severity floor both gate on this explicitly; a scenario below asserts it.

## 6. Design decision rationale

**Q1 (ticket) — Is the prose suffix the right surface, or should ratification live only in the decisions register?**
Options: register-only (one home, simpler); suffix-only (fast, but not durable/cross-ticket); both.
**Chosen:** both, at two deliberately different scopes — the suffix for the immediate, spec-local, round-to-round effect (no register-write latency to wait on), the register for durable, cross-session, cross-ticket citation. Rationale: `ratified-scope --assemble` reads only `docs/decisions.md`, never the spec's own markers (confirmed in `ratified-scope.js`) — a suffix with no register entry is real but invisible to that path (same documented-limitation posture as an unowned `decides:` punt), while a register entry has no round-to-round latency problem but cannot exist before a human has explicitly triggered its capture. Neither alone closes FAFF-1072's actual gap; both together do.

**Q2 (ticket) — Should the suffix auto-suggest a decisions-register capture, reusing faff-prep's existing capture step?**
Options: no auto-suggest (leave it manual); auto-suggest, always drafting the existing precedent shape; auto-suggest, drafting a new tradeoff shape for this event.
**Chosen:** auto-suggest, reusing the existing offer/draft/tracker-comment/materialise mechanics verbatim, but drafting the **tradeoff shape** (Source-issue/Ratified-by: human) for the new ratify-a-design-lens-objection event, while leaving the existing Punt/Assumes-closure trigger's precedent-shaped draft untouched. Rationale: a precedent entry answers "is this reusable across tickets" (`Matches:`-keyed, consumed by `matchDecision` for future punts); a tradeoff answers "don't relitigate this for *this* issue" (`Source-issue`-keyed, consumed only by `ratified-scope --assemble`). These are orthogonal questions — collapsing them (e.g. making every human-touched Chosen become a tradeoff) would either lose today's cross-ticket precedent capture or force every ratification into a shape it wasn't built for.

**Q3 (ticket) — Scope of "defer": hard-suppress a contradicting objection, or just annotate it as pre-settled?**
Options: hard-suppress (never shown at all); annotate as a cited observation, still visible.
**Chosen:** annotate only — a cited `observation`, following exactly the pattern `faffter-dark-spec-review` already ships for non-goals, ratified goals, and tracker resolutions, and never for `critical`. Rationale: this is not a new invariant to invent; it is the existing, working invariant, and the evidence (three near-identical clauses across four files) shows it is already the house answer to "how does this system handle a settled fact colliding with an adversarial reviewer." Diverging from it for this one new source of settledness would be an unjustified inconsistency, not an improvement.

**Who may write the tag: mechanical orchestrator edit, or producer LLM judgement?**
Options: let the `spec` producer decide to add the tag when it judges a decision "sounds ratified"; have the orchestrator (faff-prep) append it mechanically, only in direct response to one of two named, identifiable human replies.
**Chosen:** the orchestrator, mechanically, only on a named human reply. Rationale: the whole point of the tag is that it names a *fact the LLM cannot fabricate* — a specific reply from a specific human, in this session. Letting the producer add it on its own inference reintroduces exactly the self-grading risk the ticket names as the reason this distinction matters, and forecloses the "never on an autonomous dispatch" guarantee (an autonomous producer has no way to distinguish "the human said so" from "this looks settled to me").

**Does closing a Punt/Assumes also earn the tag, given a human answered it live too?**
Options: tag both trigger events identically; tag only the new ratify-an-objection event.
**Chosen:** tag both — closing an open Punt/Assumes is equally a human's live say-so, and giving it the same spec-local marker costs nothing and keeps the prose honest for any reader who never looks at the register. This does not change which register shape that event drafts (still precedent, unchanged).

**Should the in-spec-ratification defer clause require a `## Ratified scope` block?**
Options: require the block (uniform with the other three clauses); make it independent (reads the spec's own `--diff` directly).
**Chosen:** independent. Rationale: the block is assembled once per round from `docs/decisions.md` and a PRD; the spec itself is supplied as `--diff` unconditionally on every round regardless of whether assembly produced anything. Tying the fast signal to the slow one would silently reintroduce the exact round-1→round-2 gap this ticket exists to close whenever the register capture hasn't yet been offered, accepted, and (for a build-attached path) materialised.

**Should the default `faffter-noon-spec-review` (L1–L3) occupant also gain deferral?**
Options: add matching logic there too, for symmetry; leave it untouched.
**Chosen:** leave it untouched — it has no `## Ratified scope` concept at all today (confirmed: it never references the block), so "extend its deferral" is not a small edit, it's building a first version of a mechanism that doesn't exist in that occupant. Out of scope; named as an extension point.

**Should this touch `faff-contract:spec-readiness` or `spec-review-verdict`?**
Options: add a `ratified`/`decides`-shaped field to either schema; keep both closed.
**Chosen:** keep both closed. Rationale: FAFF-356's committed decision already rules exactly this class of metadata prose-only for `decides:`; both schemas are `additionalProperties: false` by design; and FAFF-1072's own out-of-scope note names "a new marker field" as the thing not to add, which this design honours by construction (there is no new field, only new prose read by an existing prompt).

**Is an in-spec, self-attested tag (no independent PR-review-style gate before the lens defers to it) safe to defer to at all?**
Options: require independent corroboration (e.g., only defer once a matching `docs/decisions.md` entry exists, collapsing Decision 4b into 4a and dropping the spec-local-only path); accept the in-spec tag alone, bounded by the existing severity/observation floor.
**Chosen:** accept it alone, bounded — full argument in `## 8. DONE` → "Why an in-spec, self-attested tag is safe to defer to." Requiring corroboration first would silently reintroduce the exact round-to-round latency gap Q1 exists to close (a register entry cannot exist before a human has separately accepted the capture offer); the alternative already-shipped `### Ratified resolutions (tracker thread)` fold defers to the same trust class (a live, same-loop, not-independently-PR-reviewed human utterance) today, so this is not a new risk being introduced, only the existing one relocated for speed, and it is bounded by the same never-defers-`critical` floor and the per-lens transcript's retained audit trail.

**One named trade-off covers every "this is prose, not a parser" objection in this spec — stated once here, not re-litigated per site.** Four separate mechanisms in this spec are LLM-mediated judgement rather than deterministic code: the decision-vs-implementation scope test (Decision 2), the audit-trail quote's sentence-extraction (Decision 2/WHAT), the carry-forward instruction to a `revise` re-invocation (WHAT), and the design lens's own read of the tag (Decision 4b). Round-by-round spec-review has (correctly) found each of these individually. They are one design decision, not four: this whole ticket is a **prose convention** by explicit choice (Q1/section 6, and the "prose-only, never a contract field" principle in WHY) — mechanising any one of the four would mean mechanising natural-language intent recognition generally, which is out of scope by the same reasoning that keeps this off `faff-contract:spec-readiness`. Each site's bound is identical: fail-safe-biased where a direction exists (ambiguous → no ratify, never carry-forward drops a tag silently — a dropped tag reads as agent-chosen, the safe direction), non-`critical`-only blast radius, and the per-lens transcript as the durable audit trail. A finding that a given site "is also just an LLM instruction" restates this accepted trade-off; it is not a new defect unless it names a concrete case where the *direction* of the fail-safe bias is wrong (as test-coverage items 4/5 exist to catch for the scope test specifically) — the general critique of the whole mechanism's non-determinism is closed here, once, rather than requiring one rationale entry per clause.

**How the fixture's `faff-contract:spec-readiness` block is actually extracted (closing the "no extraction method named" gap).** The extraction is the same one faff-prep itself performs at every attach point (see the gateway's Spec-readiness consumer-fold): locate the single fenced ```` ```faff-contract:spec-readiness ```` block in the spec text and `JSON.parse` its body. The fixture check reuses this exact, already-specified mechanism — it is not a new parser this ticket invents, and not a step left to the build agent's invention.

**Test-coverage items 4/5's input and output, named.** Input: the *contents* of the fixture's objection (the same shape as any `refute-*` lens's parsed `claim` string — no new type). Output: a boolean — was the ratify choice offered, yes or no. This is the same input/output shape Decision 2's own procedure already operates on; items 4/5 are not asking for a new interface, only for the existing procedure to be run against the two named fixtures and its boolean output checked.

### Why an in-spec, self-attested tag is safe to defer to (spec-review round 2 raised this; addressed here, not deferred)

The architectural and infosec lenses both pressed the same underlying question in round 2: the `(ratified: human)` tag lives inside the very artifact the lens is scrutinising, is appended by the same pipeline that produced that artifact, and carries no cryptographic or independently-verifiable proof it was earned by a genuine human utterance — unlike `docs/decisions.md` (gated by a PR-reviewed commit) or a PRD (an independently-authored document). Three bounds make this an acceptable, not a novel, risk:

1. **It is not a new trust class.** The `### Ratified resolutions (tracker thread)` fold (FAFF-998) already defers to a *live, same-loop, not-independently-PR-reviewed* human utterance — a tracker comment posted in this same session, folded into context and trusted within the round it lands. Decision 4b's tag is the same trust class relocated from a tracker comment into the spec body, traded for round-to-round speed (Q1's rationale) — not a new kind of authority the lenses did not already extend.
2. **The blast radius is bounded and never total.** A spurious tag can downgrade a non-`critical` objection to an `observation`; it can never suppress a `critical`, and it can never itself produce an `approve` (the confidence gate and the other lenses' independent objections are unaffected). The worst case is one weakened round, not a silently-passed spec.
3. **The full text survives even when the round record drops it.** `aggregate.mjs` drops observations from the round-record JSON (`faff spec-review-churn`/`faff spec-review-convergence`'s input), but the **per-lens transcript** (`$scratch/round-<n>-<lens>.md`, per faffter-dark-spec-review's own "Per-lens transcript" section) retains the lens's full raw output — including a deferred finding — regardless. A human auditing a suspicious deferral reads the transcript, not just the round record.

No design change follows from this — it is the rationale the round-1 fixes did not yet write down, closing the objection by making the existing bound explicit rather than by adding new mechanism.
