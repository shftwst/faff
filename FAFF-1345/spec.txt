# FAFF-1345 — Recognise the DONE section by its leading word, not any mention of "done"

> Spec: faffter-dark-nlspec · 2026-10-26 · autonomous · claude-code/unknown · confidence: high. Full spec on Linear FAFF-1345.
> build-tier: standard

This spec is for the build agent and human reviewers. It fixes the DONE-section recogniser in `plugin/skills/faff/bin/lib/admissibility.js` so `faff dod classify`, `faff admissible`, and `faff dod split` stop mistaking a body heading that merely contains the word "done" for the real DONE checklist, and warn loudly instead of silently returning zero criteria.

## 1. WHY

The whole pipeline reads one predicate to decide where the DONE checklist begins. `isDoneHeading` matches **any** heading that contains the word "done" anywhere in its text, and `parseDoneChecklist` anchors the DONE section on the **first** such heading. A prose body heading like `### The trust shift for prose DONE items` therefore wins over the real `## 7. DONE — Definition of Done`, the parser stops at the wrong place, and `faff dod classify` returns zero DONE criteria with no warning.

The failure is silent and downstream-amplified. Graft Step 8 builds the acceptance-criteria checklist from those criteria, so a spec with this shape ships an empty checklist and the code-blind holdout sees no DONE items to judge or delegate. It is not hypothetical: during the build of FAFF-1291 this hid all 27 DONE items until the offending heading was renamed by hand.

**Design principle — one recogniser, three callers.** The predicate is the single source of truth FAFF-306 established so `faff admissible` (the Scenarios boundary), `faff dod classify`, and `faff dod split` agree on the DONE heading by construction. The fix narrows that one predicate; it never forks a second rule into one caller. Narrowing it in place simultaneously fixes the `dod classify` start-match and the Scenarios over-stop (a body "done" heading could previously end the Scenarios section early too), so the three callers stay in agreement.

**Design principle — a silent empty result is the real defect.** Returning zero DONE criteria is sometimes correct (a spec legitimately has no DONE section). The harm is that the caller cannot tell "no DONE section" from "DONE section hidden by a near-miss heading". The fix must make the hidden-section case **observable** without changing the exit code the caller branches on.

## 3. WHAT

**Vocabulary.**

| Term | Definition |
|---|---|
| DONE heading | An ATX heading whose text, after an optional leading list number (`7.` / `7)`), **begins with** the word "done" — e.g. `## DONE`, `## 7. DONE`, `### 8. DONE`, `## 8. DONE — Definition of Done`. |
| Near-miss heading | A heading that contains the word "done" but is **not** a DONE heading (the word is not the leading token) — e.g. `### The trust shift for prose DONE items`. |
| Checklist item | A line matching the existing `- [ ]` / `- [x]` pattern `^\s*[-*+]\s+\[[ xX]\]\s+`. |

**The recogniser change.** `isDoneHeading(line)` currently returns `headingLevel(line) > 0 && /\bdone\b/i.test(line)` — "done" anywhere. It becomes: a heading whose text, after an optional leading list number, has "done" as its first word.

```
FUNCTION isDoneHeading(line):
  # mirrors SCENARIOS_HEADING_RE: ^\s*#{1,6}\s+(?:\d+[.)]\s+)?scenarios\b , with "done"
  RETURN line matches /^\s*#{1,6}\s+(?:\d+[.)]\s+)?done\b/i
```

The trailing `\b` (not `$`) is load-bearing: real specs almost always write `## N. DONE — Definition of Done`, so the predicate must accept a descriptive suffix after the leading word. Anchoring "done" to the **start** of the heading text (after the optional number) is exactly what excludes a near-miss like `### The trust shift for prose DONE items`, whose first word is "The".

**The ambiguity detector.** A pure helper returns human-readable warning strings; the one I/O caller (`dod classify`) emits them. It mirrors `doneScenariosLevelWarning`, which already returns a `string[]` for a caller to print.

```
FUNCTION doneHeadingWarnings(specText) -> string[]:
  headings := all ATX headings outside code fences, each with {text, level, section_has_checklist_items}
  recognised := headings where isDoneHeading(text)
  warnings := []
  IF recognised.length > 1:
     warnings.push("dod classify: more than one DONE section heading — using the first (" + show(first) + "); also saw " + show(others))
  FOR h in headings where NOT isDoneHeading(h.text)
                      AND h.text contains the word "done" (case-insensitive)
                      AND h.section_has_checklist_items:
     warnings.push("dod classify: checklist items under a heading not recognised as DONE (" + show(h.text) + ") — rename it to a DONE heading (e.g. '## DONE') so its items are classified")
  RETURN warnings

# show(s): the SAME neutralise-before-print transform the file's existing advisories use
# (renderProseDoneWarning / renderCodeSurfaceWarning / renderOracleLessWarning): collapse every
# whitespace run (incl. newlines) to a single space, then truncate to ~60 chars with an ellipsis.
# Reuse that helper verbatim — do not print heading text raw.
```

- "more than one DONE section heading" covers the AC's *more than one heading could be the DONE section*.
- "checklist items under a heading not recognised as DONE" covers the AC's *`- [ ]` items under a heading that is not recognised* — and fires precisely on the FAFF-1291 shape (`### The trust shift for prose DONE items` with checkboxes under it before the real DONE section).
- **Heading text is untrusted.** A heading string is attacker-influenceable spec content, so every interpolated heading (`<first>`, `<others>`, `<h.text>`) is passed through the file's existing whitespace-collapse-and-truncate idiom (`show` above) before it reaches stderr — never printed raw. This matches `renderProseDoneWarning` / `renderCodeSurfaceWarning`, which already neutralise their interpolated spec text, and stops a multi-line or overlong heading from forging extra `dod classify:` log lines or flooding a captured transcript.

**Design decision — leading-word anchor, not whole-text equality. Chosen:** recognise "done" as the leading word of the heading text (after an optional list number). The ticket's wording ("the word done as the whole heading text") reads as strict equality, but the real corpus contradicts a strict reading: committed/produced specs overwhelmingly write `## N. DONE — Definition of Done`, and both default spec producers title the section that way. Whole-text equality would stop recognising nearly every real DONE section — a far worse regression than the bug being fixed. The leading-word anchor satisfies all three stated ACs (`## DONE`, `## 7. DONE`, `### 8. DONE` all pass), matches the sibling `SCENARIOS_HEADING_RE` shape, and excludes the mid-heading near-miss. This is a factual reconciliation of the ticket wording against observable producer output, not a taste call.

**Design decision — keep both pure functions pure; emit the warning from the `cmdDod` command layer. Chosen:** the ambiguity detection lives in a pure `doneHeadingWarnings(specText)` helper (no I/O), and the **`cmdDod` command handler** (the one that implements `dod classify`, ≈L897) emits each warning via `process.stderr.write(...)` after it calls `dodClassify`. This is the load-bearing scoping choice: `dodClassify` is **not** `dod classify`'s private engine — it is reused by `proseDoneAdvisory`, `oracleLessAdvisory`, `codeSurfaceAdvisory`, and `scenariosCodeSurfaceAdvisory` (≈L655–L724), which run under `faff admissible`. Emitting from inside `dodClassify` would print the `dod classify:`-branded warning under `faff admissible` too (up to once per internal call) — exactly the cross-command leak the AC's "scoped to `dod classify`" requirement forbids. Emitting from `cmdDod` scopes the warning to the `dod classify` command alone. Both `parseDoneChecklist` and `dodClassify` stay free of this new I/O (`parseDoneChecklist` is documented "Pure — no I/O" and is reused by `admissible` and `dod split`). `cmdDod` already returns exit 0 on any successful parse (≈L924), so a new stderr line cannot change the exit code.

## 4. HOW

**Approach.** Three edits in `admissibility.js`, all in the recogniser block, plus selftest cases.

1. Narrow `isDoneHeading` to the leading-word regex above. Because it is the shared predicate, this fixes `parseDoneChecklist`'s start-match (`dod classify`, `dod split`) and `scenariosBoundaryStop` (`admissible`) together.
2. Add the pure `doneHeadingWarnings(specText)` helper beside `doneScenariosLevelWarning` (reusing the existing whitespace-collapse-and-truncate idiom for interpolated heading text).
3. In `cmdDod` (the `dod classify` command handler, ≈L897), after it calls `dodClassify`, emit each `doneHeadingWarnings` string via `process.stderr.write(...)`. Do not touch `dodClassify` itself (it is shared with `admissible`), and do not alter any return value, counts, or exit code.

```
PROCEDURE cmd_dod_classify(args):                                  # the `dod classify` command, ≈L897
  1. r := dodClassify(specText, { issue })                         # unchanged — pure, no new I/O here
  2. print JSON(r) to stdout                                       # unchanged
  3. FOR w in doneHeadingWarnings(specText):
        process.stderr.write(w + "\n")                             # NEW — command layer only, not admissible
  4. RETURN 0                                                      # unchanged — warnings never gate
```

**Failure modes.**

- **The failure:** the leading-word anchor mis-recognises — either too tight (a legitimate DONE section titled unusually is missed, so its count drops to zero) or too loose (a body heading that genuinely leads with "done", e.g. `## Done and dusted: the retro`, is wrongly accepted as the DONE section). **How you'd know:** the two sides reveal differently, and only one is caught by the new warning. *Too tight:* the missed heading contains "done" without leading on it, so it falls into the near-miss branch and the new stderr warning fires (the designed-in safety net) — or a selftest over the real heading forms fails. *Too loose:* a heading that leads with "done" **is** recognised, so no near-miss warning fires — this case is caught only by a selftest or by a human noticing the wrong section was read, not by the warning. **What it means:** proceed — the too-tight direction self-surfaces; the too-loose direction is a known, accepted residual (a leading-"done" body heading is rare and the spec corpus does not contain one), narrowed in a follow-up only if a real case appears. The warning is honestly a safety net for the too-tight direction, not for every mis-recognition.
- **The failure:** a spec legitimately has `- [ ]` items under a non-DONE heading (e.g. a WHAT table of checkboxes), triggering a spurious near-miss warning. **How you'd know:** the warning fires on a spec a human considers correct. **What it means:** narrow — gate the near-miss warning on the heading also *containing* the word "done" (done above), so an unrelated checkbox section does not warn.

**Anti-pattern:** adding a second DONE regex inside `parseDoneChecklist` or `scenariosBoundaryStop`. Why: it forks the FAFF-306 single source and re-opens the admissible-vs-classify disagreement this file exists to prevent.

**Anti-pattern:** raising the exit code when a near-miss is detected. Why: the AC fixes the exit code as unchanged; callers branch on it, and the signal is deliberately advisory (stderr only).

## 6. DESIGN DECISION RATIONALE

**How strictly should a DONE heading be matched?**
- *Any mention of "done"* (status quo): over-matches body prose headings — the bug.
- *Whole heading text equals "done"* (ticket's literal wording): would stop recognising `## N. DONE — Definition of Done`, i.e. almost every real spec — a worse regression.
- *Leading word "done" after an optional list number* (mirrors `SCENARIOS_HEADING_RE`): excludes mid-heading near-misses, accepts the real `— Definition of Done` suffix, satisfies every stated AC.
- **Chosen:** leading-word anchor — `/^\s*#{1,6}\s+(?:\d+[.)]\s+)?done\b/i`. At the time of writing, the committed/produced spec corpus and both default spec producers title the section `## N. DONE — Definition of Done`, which a whole-text rule would break; revisit only if the house DONE heading convention changes.

**Where does the ambiguity warning live?**
- *Inside `parseDoneChecklist`*: breaks its documented purity and triple-prints across the three callers that reuse it.
- *Inside `dodClassify` via a pure helper*: keeps the recogniser/parser pure, scopes the warning to `dod classify` (per the AC), and reuses the existing `process.stderr.write` idiom.
- **Chosen:** a pure `doneHeadingWarnings(specText)` helper emitted by `dodClassify`.
