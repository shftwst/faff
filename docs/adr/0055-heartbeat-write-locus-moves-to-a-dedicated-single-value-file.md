# ADR 0055 — Heartbeat write locus moves to a dedicated single-value file

- **Status:** Accepted
- **Date:** 2026-07-11
- **Issue:** FAFF-355
- **Supersedes:** ADR-0015

## Context

ADR 0015 made `faff heartbeat` the single sanctioned write path for `owner.last_heartbeat`, implemented as a field-merge: re-read the run ledger immediately before mutating only that one field and write it back atomically. That closed the false-abandonment hole under the sequential executor, where the orchestrator and its build subagent are never simultaneously active — but ADR 0015's own Consequences named the gap it left open: "concurrent multi-writer safety under the parallel executor is out of scope: with more than one active subagent a field-merge can still interleave with an outcome write," and pointed at the extension point verbatim — "a dedicated single-value heartbeat file decoupled from ledger content." `faffter-dark-concurrency-parallel/SKILL.md` carried that same admission forward as a live blockquote: heartbeat ownership under N concurrent subagents is unresolved, and resolving it is a stated precondition for running the parallel executor in anger. It is also the explicit blocker for FAFF-327 (fleet Sentry supervision), which cannot be admitted while the parallel executor's multi-writer punt stands. A field-merge, however careful, is still a read-modify-write of the whole ledger; two of those (a heartbeat tick and an orchestrator outcome write) can still interleave and the loser's write is lost. The fix has to remove the ledger from the tick's write set entirely, not merely narrow the window.

## Decision

`faff heartbeat`'s only write becomes a dedicated single-value file, `.faff/runs/<run-id>/heartbeat` — one ISO-8601 UTC timestamp plus a trailing newline, written atomically (sibling tmp file + rename, the same idiom ADR 0015 established). The tick still reads the run ledger once, read-only, to evaluate the unchanged running-guard (`owner.status === "running"`); it never writes the ledger back. This is a structural fix, not a sequencing discipline: the race is closed because there is nothing left in the tick path for a concurrent orchestrator outcome write to race against, not because writes are more carefully ordered.

The run ledger's `owner.last_heartbeat` field is demoted from "the heartbeat" to a run-start baseline and legacy-compatibility fallback — it is written once, at mint time, by the owner stamp, and never refreshed by a tick again. Every read seam that used to consult that field directly now overlays the dedicated file over it first: a new pure `effectiveHeartbeatIso(fileIso, fieldIso)` core takes the max by parsed epoch (unparseable or absent input falls back to the other source; both absent is `null`), and a new pure `overlayHeartbeat(ledger, fileIso)` core applies that onto the parsed ledger's `owner.last_heartbeat` in place, reporting which source won. Four call sites overlay before invoking their existing, unchanged liveness predicate: `runcheck --hook`'s `runcheckHookDecision` → `runIsHeld`; the `resolveAppetite` L4 agency-mode pin; `prepIsHeld`'s tier-(a) ledger delegation; and `sentry check`'s `evalWallClock`, whose evidence field is renamed from the now-inaccurate `ledger_field: "owner.last_heartbeat"` to `heartbeat_source: "heartbeat-file" | "owner.last_heartbeat"`, naming whichever source the overlay actually read. `runIsHeld` and the other liveness predicates keep their exact signatures and stay filesystem-free — the overlay is itself a pure, independently-tested core, so the read side changes by one call-site line each rather than a signature ripple through every predicate and both existing selftest tables.

This supersedes ADR 0015's *write-path* decision specifically — the field-merge mechanism it specified is what this change replaces — while leaving ADR 0015's Context intact: `faff heartbeat` remains the single sanctioned entry point every caller invokes unchanged (faff-graft's long sub-steps, both concurrency executors, beep-boop), and the read path / ownership model ADR 0015 also touched is untouched here. `applyHeartbeat`, the field-merge primitive ADR 0015 introduced, is deleted outright — its only callers were `cmdHeartbeat` and its own selftest, both rewritten around the new pure cores.

Two alternatives were rejected. Dual-write (keep writing the field *and* write the new file) does not close the race — the tick still performs a full-ledger read-modify-write, so the exact interleaving ADR 0015 flagged survives; the fix has to make the tick's ledger access read-only, not add a second write. Widening `runIsHeld`'s signature to accept a file-sourced timestamp directly was also rejected in favour of the read-seam overlay: it would have forced a fourth parameter through every liveness predicate and both the `RUNCHECK_SELFTEST_CASES` and `PREPCHECK_HOOK_SELFTEST_CASES` tables, for no benefit the overlay doesn't already provide as its own independently-selftested pure core.

## Consequences

- The run ledger has exactly one class of writer again: orchestrator-lane (outcome recording, the owner stamp/status, sentry abort's resumable mark, the lights-out mint). Build subagents touch only the heartbeat file. N concurrent subagents ticking at once is safe by construction — each tick is an atomic whole-file replace of a single-value file, and last-writer-wins is the correct outcome for a freshness scalar — closing the parallel-executor precondition both `faffter-dark-concurrency-parallel/SKILL.md` and FAFF-327 were blocked on.
- A pre-upgrade run (no heartbeat file yet, or a legacy ledger that never gets one) keeps working with zero migration: `effectiveHeartbeatIso` falls back to the ledger field whenever the file is absent or unparseable, and the run-start owner stamp still seeds that field once at mint time.
- Every diagnostic that names its liveness source must now name the true one — sentry's wall-clock evidence carries `heartbeat_source` rather than a hardcoded field name, and the CLI USAGE / `docs/guide/cli.md` heartbeat and sentry rows describe the file-plus-fallback model rather than the field-merge ADR 0015 documented.
- `RUNCHECK_SELFTEST_CASES` gained a heartbeat-file column (with pre-existing rows unaffected, `heartbeatFile` defaulting to absent) so the fresh-file/stale-field, no-file/fresh-field, both-stale, and unparseable-file/fresh-field interactions are pinned alongside the existing ownership/liveness table; `test/prepcheck.test.mjs` gained the equivalent tier-(a) case; a new `test/heartbeat-concurrency.test.mjs` is the repo's first real concurrency test, spawning real `faff heartbeat` child processes against a scripted, racing outcome write and asserting the no-lost-update invariant directly, rather than only inferring it from the write path no longer touching the ledger.
- A second ledger field ever needing its own dedicated single-value file would follow this same file-plus-overlay shape rather than reopening the field-merge pattern ADR 0015 introduced and this ADR retires.
