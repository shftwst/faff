# ADR 0095 — What bounds a faff run on a CI runner — admission criteria, not a mechanism

- **Status:** Proposed
- **Provenance:** human
- **Date:** 2026-08-03
- **Issue:** FAFF-646

## Context

ADR-0010 delegates the unattended blast-radius boundary to an OS-level host-isolated container: faff owns no sandbox and enforces nothing, it *asserts* the boundary is present via `container-check.js`. That check recognises container **markers** — `/.dockerenv`, `/run/.containerenv`, `KUBERNETES_SERVICE_HOST`, the pid-1 `container=` convention. A self-hosted GitHub Actions runner is a bare user process and produces none of them.

Two sibling tickets built against that reality fail in opposite directions. FAFF-643 runs at L3, where a `not_confirmed` containment reading only *warns* — shipped as-is it would drain a queue unattended on a bare developer host, behind a warning nobody reads. FAFF-606 runs at L4, where the lights-out preflight *hard-blocks* on the same signal — as specified it would refuse at mint on the documented self-hosted rig. Same signal, opposite outcomes, and no ADR saying which is right. The question this record answers: what bounds a faff run on a CI runner, and what does each autonomy level require of it — stated as admission criteria, not as a mechanism.

The evidence is on record, and it is what unblocked this decision. FAFF-654's probe measured four job-surface columns into `docs/spikes/2026-07-26-FAFF-654/RESULTS.md` — hosted-direct and hosted-container (FAFF-657), self-hosted-direct and self-hosted-container (FAFF-656, taken on a fly.io Firecracker microVM). Three findings carry this decision:

1. **The check cannot tell a disposable VM from a laptop.** The self-hosted-direct column shows no container markers at all — `/.dockerenv` absent, cgroups at `/`, pid-1 `comm` is `init` — identical to a bare shell. That the host is a throwaway microVM is invisible to `containerCheck`; nothing in the reading distinguishes it from a developer's own machine.
2. **A contained job can still reach a writable host engine socket.** The self-hosted-container column reads *contained* (`/.dockerenv` present, a `/docker/<id>` cgroup) **and** `attest.canonical_socket_present: yes`, `attest.canonical_socket_writable_by_euid: yes` — the host `/var/run/docker.sock` bind-mounted into the job and writable. A writable host docker socket is root-equivalent control of the host (ADR-0041 decision 3), so containment did not bound the escape. Read from `actions/runner` source (`ContainerInfo.cs:57`), the runner mounts the socket into every Linux job container; FAFF-656's container column is the single *observed* instance of that, and RESULTS.md flags it as having no independent corroboration. The "every job, unconditionally" universal is therefore source-derived, not measured, and this record keeps that distinction. Containment and host-reach are orthogonal axes — which is exactly how `container-check.js` already models them, `containerCheck` for the first and `hostSocketProbe` for the second.
3. **The runner maps its whole `_work` into the job**, not one repository's checkout (`ContainerInfo.cs:54`, confirmed by FAFF-656). On a shared persistent runner that means the job can reach every other checkout on the machine. The single-tenant throwaway Machine held only its own checkout, so the multi-checkout neighbour reach is inferred from the mount, not observed — RESULTS.md records it as a property of a shared runner.

## Decision

**The boundary requirement for a faff run on a CI runner is stated as admission criteria the operator must meet, not as a sandbox faff supplies. There are exactly two, and neither names a product.** The run must be **contained**, and **no host engine socket may be reachable** from the job. faff provides the mechanical check — `faff container-check --gate`, a pass/fail on those two axes, built by FAFF-655 — and the operator brings any cage that passes: claude-box, an Actions `container:` job with the socket removed, a devcontainer, a Kubernetes runner pod, sysbox, or something they wrote. A named cage may appear only in a clearly non-normative illustration. This is not a new stance — the gateway already holds that the container is a substitutable mechanism and claude-box one implementation, recommended rather than required (`SKILL.md:647`); this record fixes the admission criteria that any substitute is measured against.

**"Work scoped to this checkout" is not a third criterion.** It is a real property, but the runner path-maps its whole `_work` into the job (finding 3), and faff has no signal to verify scoping — the worktree-isolation probe proves where faff *writes*, not what the job can *reach*. An unverifiable third criterion sitting beside two verifiable ones is what teaches people to infer safety from the cage they picked. So the criterion is recorded as real-but-not-faff-checkable and excluded from the admission set: it is a guarantee only the cage can make, not one the check can confirm.

**A CI runner is not, by itself, the boundary.** Ephemerality bounds how long the mess survives, not how far it reaches — within the job's life the agent holds the checkout, the runner's credentials and registration token, and on a self-hosted runner the invoking user's home directory. And because the check cannot tell a disposable VM from a laptop (finding 1), no exemption can be scoped to the "safe" disposable case even if one were wanted. This was attacked adversarially during spec-review and held; it is recorded here rather than re-argued. A disposable hosted-runner VM therefore does **not** count as admissible on the strength of being disposable — the default is no, and the check reports `not_confirmed` honestly rather than inferring isolation from a substrate it cannot see.

**The per-level posture: refuse by default when a criterion is absent, at every unattended level, with an explicit recorded opt-out.** L3 and L4 both run unattended once the drain starts, and the check cannot tell a CI runner from a laptop — so strictness keys on the *cage* (detectable) and the *autonomy level* (the unattended proxy), never on substrate.

- `autonomous.require_container` **defaults to refuse**: a missing containment boundary refuses an unattended L3 or L4 run at mint. This closes what is today the system's only fail-open floor — `gates.fallback`, `merge-gate`, the holdout judge, and the L4 preflight all fail closed already; L3 containment was the sole place faff observed a missing safety property and carried on.
- The only escape is an explicit, recorded operator opt-out: `autonomous.require_container: warn`, set deliberately, means "I accept running uncaged." That converts an inherited silent gap into a decision. It is never the default, and an uncaged run is pointed at a cage.
- **No migration window.** The single-operator reference install — this repo's own — already runs contained (`faff container-check` → `contained`, host socket absent on the linuxkit rig), so flipping the default breaks nothing that exists and there is no population to phase. FAFF-643's reference rig is caged from day one by construction.
- **This extends ADR-0010, it does not reverse it.** ADR-0010's headline is "assert, don't enforce" — faff implements no sandbox and never refuses on its own authority. Declining to *start* an unattended run when the asserted boundary is absent is faff refusing to act *without* a cage; it is not faff *implementing* one. faff still owns and builds no sandbox. This narrows ADR-0010's L3 prose to the fail-closed posture `lights-out.js` already applies at L4 on the same signals — a narrowing, not a reversal — and the body says so plainly so a reader does not read it as a corpus contradiction.

**`autonomous.require_branch_protection` gets the same treatment.** It is the same shape — a prose-only `warn` default today with no code branch — on a different axis: it bounds the run's reach into the repository rather than the host blast radius. It defaults to refuse when branch protection on the target branch is absent for an unattended run, with the same explicit `warn` recorded opt-out and no migration. It is a sibling fail-open floor closed by the same principle, not a CI-cage criterion.

**The host-socket route for reading `faff env` in-job is refused, with its reason.** The lights-out preflight already refuses unconditionally on a present host socket unless `autonomous.engine_bounded: true` attests a bounded nested engine (`lights-out.js:346`). That route is recorded as refused rather than left looking like a shortcut. The demonstration is the vanilla Actions `container:` job: it fails the second criterion by default because the runner bind-mounts the host socket (`ContainerInfo.cs:57`) — which is precisely why admission must be *decided by running the check*, not inferred from which cage was chosen. claude-box refuses to mount the socket in its entrypoint; the socket problem is a property of one way of making a cage, not of cages. The in-repo demonstration that the socket is removable and a bounded engine substitutable is the `env-rootless` job in `.github/workflows/validate.yml`: it disables the system docker daemon, removes `/var/run/docker.sock`, and validates against a rootless daemon — the same "no reachable host socket" posture this record's second criterion requires, exercised in CI.

## Consequences

- L3's containment posture stops being the corpus's one fail-open floor. An unattended run with no confirmed cage refuses at mint by default, matching what L4 already does — the two levels now share one direction on the same signal, and FAFF-643 (L3) and FAFF-606 (L4) both have an unambiguous answer for the documented solo-dev rig: caged from day one.
- faff still enforces nothing of its own. The lever operators hold is the cage; the lever this record adds is *admission-refusal when the cage is absent*, which is a decision to not act, not a sandbox. ADR-0010's assert-don't-enforce stance is intact, narrowed at L3, and any future reader should treat the default-refuse as extending it.
- The admission decision is a tool's exit code (`faff container-check --gate`, FAFF-655), not a judgement about which cage was picked. A contained job that still reaches a writable host socket fails, and a marker-less disposable VM fails — both because the check reports what it observes and never infers isolation from substrate. Downstream tickets that adopt the gate (FAFF-643, FAFF-606) inherit this by running the check, not by trusting their runner.
- "Work scoped to this checkout" remains an unmet, unverifiable property on shared runners. This record does not solve it; it names it as the cage's responsibility and refuses to fold it into an admission set faff cannot honestly check. A future signal that *could* verify job-reach scoping would be the thing that promotes it to a third criterion.
- The escape hatches (`require_container: warn`, `require_branch_protection: warn`) are explicit, recorded, per-operator decisions. They leave an audit trail in config rather than a silent inherited gap, which is the property that lets the default be safe without being a wall.
- The worked cages (FAFF-651, FAFF-649) and the reference workflows (FAFF-643, FAFF-606) are downstream of this record, not part of it. They are examples measured against these criteria; none of them is the normative answer, and swapping any of them for another admissible cage changes nothing this ADR requires.
