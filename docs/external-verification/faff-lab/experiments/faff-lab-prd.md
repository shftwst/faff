# PRD — faff-lab

- **Container:** faff-lab
- **Status:** Draft
- **Date:** 2026-07-14
- **Mode:** authored
- **Reference:** github.com/shftwst/faff — explore this repo for faff's current terminology, L4 mechanics, and config shape before implementing

## Problem / objective

faff needs a visible way to demonstrate that its L4 (lights-out) build process is worth using over a raw model one-shotting the same brief. faff-lab is a public gallery, itself generated by faff, that puts a raw one-shot run and a faff L4 run under a given config side by side against the same shared brief — a proving ground for faff, and a test bed for its own model configs. Different kinds of tasks stress different capabilities (a game-building brief is nothing like a brief that requires standing up real infrastructure, e.g. a URL shortener), so the gallery compares runs per task category, each against its own shared brief, rather than forcing every run into one universal brief.

## Goals & success metrics

- A visitor can look at the gallery and tell, per run, what built it, whether a faff config was involved, and which task category it belongs to.
- A faff maintainer can view historical test configs and results, alongside control one-shot frontier models, and can add new runs.
- Support the comparison of a faff config using a cheap/free orchestrator and cheap/free build models against a raw one-shot using those same models — evidence that faff's process, not just model choice, drives the quality difference.
- Support the comparison of a faff config using a capable-but-not-frontier orchestrator (e.g. Opus or Sonnet) directing cheap/free build models against a raw one-shot from a bleeding-edge frontier model/harness (e.g. Fable) — evidence that the faff run can land on par with the frontier one-shot at a fraction of the cost, while also producing a better-governed codebase than the frontier one-shot has.

## Non-goals

- A prescribed data model, filter mechanism, or run-adding mechanism — implementation's to decide.
- Requiring anything of other, independently-hosted run repositories (e.g. their own `.faff/` handling) — out of faff-lab's control.
- Visual design decisions beyond the direction stated under Requirements — subsequent PRDR.
- Run content decisions beyond the seedable fixtures direction stated under Requirements — subsequent PRDR.

## Users

Visitors evaluating faff's L4 capability; faff maintainers using the gallery as a live test bed for comparing configs.

## Requirements

- Runs are filterable and searchable by the visitor.
- Runs are ordered most recent first by default.
- Each run is shown as a card with a thumbnail, its name, the model(s) used, the harness used, and what the run cost to produce (unknown cost is stated as unknown, never silently omitted).
- Each run links to its run repository — how a visitor inspects the codebase the run produced, its commit history, and any committed `.faff/` trail — and to its live built artifact where one is deployed.
- Each run records its results — pass/fail per acceptance criterion of its tab's brief — viewable from its card.
- Where a run used a faff config, the config is revealable and copyable from its card, and faff version used must be stated.
- The site is organized into tabs, one per task category (e.g. a game-building task, a URL-shortener task requiring infrastructure); each tab has its own shared brief and shows only the runs built against that brief.
- Tab briefs are versioned; each run records the brief version it was built against.
- Runs that answer the same comparison — a faff run and its one-shot control, built against the same brief version — are explicitly paired, and a visitor can view a pair side by side; runs without a counterpart stand alone.
- Links to the main faff repository and to the faff-lab repository are prominent.
- Design is dark/light mode, modern, clean, content-first; "faff" is always written lowercase.
- GitHub, Netlify, Fly.io, Turso, and R2 exist and are available for use — availability only, not a decision on what's used; no paid service beyond what's already available is allowed.
- Releases/deployments of the site are automated.
- A maintainer adds a run as data — the mechanism is implementation's choice, but it must not require changing the site's code.
- Seeded with plausible fixtures for tabs, briefs, runs and results, every fixture visibly marked as illustrative so seeded data cannot be mistaken for a real run.

## Acceptance criteria

- The site MUST let a visitor filter the set of displayed runs.
- The site MUST let a visitor search the set of displayed runs.
- The site MUST order displayed runs most recent first by default.
- Given a run, When it is displayed, Then its card MUST show a thumbnail, its name, the model(s) used, the harness used, and its cost (or an explicit statement that cost is unknown).
- Given a run, When its card is displayed, Then it MUST link to the run's repository, and to the live built artifact where one exists.
- Given a run, When its results are displayed, Then they MUST show pass/fail per acceptance criterion of its tab's brief, at the version the run was built against.
- Given a run that used a faff config, When its card is displayed, Then the config MUST be revealable and copyable from that card, and the faff version used MUST be stated.
- Given a run that did not use a faff config, When its card is displayed, Then no faff-config affordance is shown on it.
- The site MUST present runs grouped into tabs, one per task category.
- Given a tab, When it is displayed, Then it MUST show its shared brief, and each run in it MUST state the brief version it was built against.
- Given a run, When its results are evaluated, Then evaluation MUST be against its own tab's brief, at the version the run was built against.
- Given a run with a paired counterpart, When its card is displayed, Then the pairing MUST be visible and a side-by-side view of the pair MUST be reachable from it.
- Given two runs, When they are presented as a pair, Then both MUST have been built against the same version of the same brief.
- The site MUST NOT provide any visitor-facing control to add a run or trigger a build.
- Adding a new run MUST NOT require changes to the site's code.
- Given a fixture run, When it is displayed, Then it MUST be visibly marked as illustrative rather than a real result.
- The site MUST prominently link to the main faff repository and to the faff-lab repository.
- The faff-lab repository MUST commit its `.faff/` directory rather than gitignoring it.
- The site MUST support both dark mode and light mode.
- Written references to faff MUST use lowercase.
- Releases/deployments of the site MUST be automated, with no manual deploy step.

## Evaluator note

Most Acceptance criteria above are objective — a card field is present, a link resolves, a pairing exists, a mode toggle works — and can be checked without judgement. Three requirements are subjective: "modern, clean, content-first" design, the prominence of the repository links, and whether the side-by-side view actually makes the comparison legible. Treat those as directional context for a human reviewer, not pass/fail gates — a build can pass every objective criterion and still fail to communicate.
