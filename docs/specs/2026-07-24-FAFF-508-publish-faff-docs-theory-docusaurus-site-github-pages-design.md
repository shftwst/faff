# Publish faff docs + theory as a Docusaurus site on GitHub Pages

> Spec: faffter-dark-nlspec · 2026-07-24 · autonomous · confidence: high. Full spec on Linear FAFF-508.

This spec is for the build agent (and human reviewers) of FAFF-508. It stands up a Docusaurus static site, in the faff repo, that publishes two reading surfaces — the existing `docs/guide` content and a new "theory & concept" section — and deploys it to GitHub Pages on merge to `main`. It is deliberately the first slice: enough to give the docs and the theory a browsable home, and nothing past that.

## 1. WHY — Problem and Principles

**The load-bearing idea:** the canonical Markdown under `docs/` stays the single source of truth, and Docusaurus reads it *in place*. The site is a rendering surface over the repo's own files, not a second copy of them. Everything else in this spec follows from that one rule.

**Problem.** faff's docs are rich but repo-only — adopters read raw Markdown on GitHub, and the theory (the levels model, the governing principles, the "why faff" story) has no browsable home at all; it lives scattered across the README and the gateway skill. A published site gives the project a shareable front door and puts the *Understandable, not unapproachable* tenet on show.

**Design principles.**

- **No fork.** The site must never duplicate `docs/guide`. If a build step copies guide Markdown into a site folder, that is the wrong approach — the canonical files must remain the ones Docusaurus reads.
- **The site copy is public positioning.** The theory pages are the first thing an adopter reads about what faff is. They follow the repo writing style (`.agents/STYLE.md`): the core idea is "safe to stop watching"; the levels are trust earned per rung, not convenience gained; the governance layer is a product in its own right. No convenience-tool framing.
- **First slice, held.** The exclusions in section 2 are load-bearing, not aspirational. Resist pulling ADRs, versioning, or theme work forward.

**Reference context.**

| System | Language | Relevance |
|---|---|---|
| `docs/guide/*.md` | Markdown | The guide surface — read in place, unchanged, as the source of truth |
| `README.md` | Markdown | Source material the theory pages distil (the pitch, the levels table) |
| `plugin/skills/faff/SKILL.md` | Markdown | Source material the theory pages distil (the gateway's "What faff is", the four governing principles) |
| `.github/workflows/*.yml` | GitHub Actions | The existing CI workflows the deploy workflow sits alongside |
| bundled `faff` CLI | Node (dependency-free) | The repo's only existing Node code — the site's Node tooling stays isolated from it |

**Scope.** A new, self-contained documentation site living under `website/` in the repo, plus a Pages deploy workflow. It touches no CLI code and no existing guide content beyond two link rewrites (section 4).

## 2. OUT OF SCOPE

- **ADRs and architecture docs as published surfaces** — Why: the slice publishes guide + theory only; the `docs/adr` and `docs/architecture` trees stay unpublished for now. Extension point: a third docs plugin instance in `website/docusaurus.config.js`, pointed at `../docs/adr`.
- **Doc versioning** — Why: one live version is enough for a first slice. Extension point: Docusaurus's `versions` config on the guide docs instance.
- **Custom domain** — Why: deferred by the ticket. Extension point: a `website/static/CNAME` file plus the `url`/`baseUrl` swap in the config (section 3).
- **Search and theme polish** — Why: the default classic theme is sufficient to browse. Extension point: `themeConfig.algolia` for search, and `website/src/css/custom.css` for styling.
- **Drift-guard between the theory pages and README/gateway** — Why: the three surfaces are allowed to say the same thing in their own length for now (section 3, Decision on theory source of truth). Extension point: a follow-up ticket for a lint that flags divergence. This is a known consequence, tracked, not solved here.

## 3. WHAT — Structure, Config, and the Two Surfaces

**Vocabulary.**

| Term | Definition |
|---|---|
| Guide surface | The existing `docs/guide` content, published as one navigable section |
| Theory surface | The new `docs/concept` content (levels, principles, why-faff), published as a distinct section |
| Site root | `website/` — the self-contained Docusaurus project (its own `package.json`, config, and `src/`) |

**Site layout.**

```
website/
  package.json            # Docusaurus deps; scripts: start, build, serve
  docusaurus.config.js    # site metadata, two docs instances, navbar, onBrokenLinks
  sidebars.js             # autogenerated sidebars, one per docs instance
  src/pages/index.*       # the landing page (section 4)
  src/css/custom.css      # minimal; no theme polish this slice
docs/
  guide/                  # UNCHANGED source of truth — read in place
  concept/                # NEW canonical theory Markdown — read in place
    intro.md
    what-is-faff.md
    levels.md
    governing-principles.md
```

**How Docusaurus consumes `docs/` without forking.** Docusaurus's docs content plugin accepts a `path` that points outside the site directory. The site is configured with **two** `@docusaurus/plugin-content-docs` instances, each pointing at a repo-`docs/` subtree by relative path — no copy step, no restructure of the canonical files.

- Guide instance: `id: 'guide'`, `path: '../docs/guide'`, `routeBasePath: 'guide'`, autogenerated sidebar.
- Theory instance: `id: 'concept'`, `path: '../docs/concept'`, `routeBasePath: 'concept'`, autogenerated sidebar.

**Chosen:** point two docs-plugin instances at `../docs/guide` and `../docs/concept` in place. Rationale: it is the only option of the three the ticket named (point / copy / restructure) that keeps the canonical Markdown authoritative. Copying forks; restructuring moves the source of truth into the site. Pointing reads the repo's own files, so a `docs/guide` edit is live with no sync step.

**The theory page set, and where each piece's source of truth lives.** The theory currently has no home under `docs/` — it lives in `README.md` and the gateway `plugin/skills/faff/SKILL.md`. This slice gives it one: four new canonical pages under `docs/concept/`, distilled from those two sources.

| Page | Distilled from | Covers |
|---|---|---|
| `intro.md` | README opening + gateway "What faff is" | Section landing: what "theory & concept" means here, links onward |
| `what-is-faff.md` | README "What faff is" + gateway "What faff is" | The harness definition, tracker-as-control-plane, the "safe to stop watching" thesis |
| `levels.md` | README "The levels" + gateway levels tables | The L1–L4 model, per-workload eligibility, mechanical vs model-compliance |
| `governing-principles.md` | Gateway "Governing principles" | The four tenets, each as *X, not Y* with its embodying mechanism |

**Chosen:** author these four pages as new canonical Markdown under `docs/concept/`, and treat `docs/concept/` as the site's source of truth for theory. Rationale: the ticket's Why is "the theory has no browsable home" — the fix is to give it one under `docs/`, which is exactly where the no-fork rule wants canonical content to live. The README keeps its condensed pitch and levels table (a front door is not a fork of the concept pages — it is a shorter thing for a different reader), and the gateway keeps its runtime routing copy. **Consequence:** three surfaces now describe the levels in their own length, so they can drift; that is accepted for this slice and left to the follow-up named in section 2, not gold-plated here.

baseUrl: "/faff/"
organizationName: "shftwst"

**Navbar.** Two items — **Guide** (→ `/guide`) and **Concept** (→ `/concept`) — so the two surfaces browse as distinct sections, plus a GitHub repo link. That is the whole nav for the slice.

## 4. HOW — Build, Landing Page, and Deploy

**Local build.** `website/package.json` carries the standard Docusaurus scripts. `npm --prefix website ci` then `npm --prefix website run build` produces static HTML in `website/build`. `npm --prefix website start` serves a dev server for local authoring.

**The landing page.** A minimal custom homepage at `website/src/pages/index` (the classic-template homepage, trimmed), carrying:

- The faff one-liner and the "safe to stop watching" line (from the README pitch, per the writing style).
- Two calls to action — **Read the guide** (→ `/guide`) and **The theory** (→ `/concept`).

No hero illustration, no feature grid, no theme work — that is section 2's excluded polish. Just the pitch line and the two doors.

**Chosen:** a minimal custom `src/pages/index` landing rather than redirecting `/` straight into the guide docs. Rationale: the site's front page is the first public positioning surface; a one-screen landing that states the thesis and offers the two sections is worth the few lines, and it is where a later slice hangs polish. It stays within the excluded-theme-polish boundary by using the default theme unstyled.

**Broken links from the guide tree.** Two guide pages — `docs/guide/governance-check.md` and `docs/guide/releasing.md` — link to files outside the `docs/` tree via `../../.github/workflows/*.yml`. Those relative links resolve on GitHub but fall outside what Docusaurus can render, so they would raise broken-link errors.

```
PROCEDURE handle_out_of_tree_links:
  1. Rewrite the two `../../.github/workflows/*.yml` links in docs/guide/*.md
     to absolute https://github.com/shftwst/faff/blob/main/.github/workflows/<file> URLs.
     (Absolute links also resolve correctly when the same file is read on GitHub.)
  2. Set onBrokenLinks: "warn" in docusaurus.config.js so any remaining
     unforeseen link surfaces as a build warning, not a hard CI failure.
```

**Chosen:** rewrite the two known out-of-tree links to absolute GitHub URLs **and** set `onBrokenLinks: 'warn'` for this slice. Rationale: "site builds in CI" is an acceptance criterion, so a single unforeseen link must not turn the build red on the first slice; the rewrite fixes the known cases cleanly (and keeps them valid on GitHub too), while `warn` keeps the build green and logs anything missed. A follow-up can tighten to `throw` once the guide tree is link-clean.

**Anti-pattern:** copying or symlinking guide Markdown into `website/docs`. Why: it forks the source of truth — the whole point of section 3 is that Docusaurus reads the canonical files in place.

**The deploy workflow.** A new `.github/workflows/deploy-docs.yml`, using the GitHub-recommended Pages-via-Actions pattern.

```
PROCEDURE deploy-docs (on push to main; also buildable on PR):
  build job:
    1. checkout
    2. setup-node (Node 20+, cache npm against website/package-lock.json)
    3. npm --prefix website ci
    4. npm --prefix website run build
    5. upload-pages-artifact from website/build
  deploy job (only on push to main; needs: build):
    6. permissions: pages: write, id-token: write
    7. deploy-pages  ->  environment: github-pages
```

Run the build step (steps 1–4) on pull requests too, so a docs PR proves the site builds before merge; gate the deploy job to `push` on `main` only.

**Failure modes.**

- **The failure:** GitHub Pages is not set to build from GitHub Actions, so the workflow succeeds but nothing serves. **How you'd know:** the deploy job is green but the Pages URL 404s. **What it means:** proceed — this is the `**Assumes:**` in section 7; the human enables the Pages source once.
- **The failure:** the `../docs/guide` relative path breaks under the Pages build working directory. **How you'd know:** `npm run build` fails locally with a missing-path error before CI ever runs. **What it means:** proceed — caught at local build (a DONE item), not a runtime surprise.

## 6. Design Decision Rationale

**How does Docusaurus consume `docs/` without forking?** Options: (a) point plugin `path` at the repo `docs/` subtrees, (b) copy guide Markdown into `website/docs` at build time, (c) restructure the canonical files under `website/`. **Chosen:** (a) point in place — the only option that keeps `docs/` authoritative; (b) forks, (c) moves the source of truth.

**Where does theory content live, and what is its source of truth?** Options: (a) author new canonical pages under `docs/concept/`, (b) point a docs instance at `README.md`/gateway files directly, (c) leave theory in README only and link out. **Chosen:** (a) — (b) can't cleanly include scattered repo-root files without a fork/symlink, and (c) fails the ticket's "no browsable home" problem. New `docs/concept/` pages give theory a canonical home under `docs/`, consistent with the no-fork rule.

**Default github.io URL vs custom domain?** **Chosen:** default `https://shftwst.github.io/faff/` with `baseUrl: '/faff/'`. The custom domain is deferred by the ticket; the extension point is recorded in section 2.

**What does the landing page contain?** **Chosen:** a minimal custom homepage — the pitch line plus two section links — over an auto-redirect into the guide. It is the first positioning surface and the hook for later polish, and stays within the excluded-theme boundary by using the default theme unstyled.

**Where does the site live in the repo?** Options: repo root vs a `website/` subdirectory. **Chosen:** `website/`. The repo's existing Node code (the `faff` CLI) is deliberately dependency-free with no root `package.json`; isolating the site's `node_modules` and deps under `website/` keeps that posture and keeps the site tooling self-contained.

- **Assumes:** the repo's default branch is `main` (confirmed) and the workflow's `main`-only deploy gate matches it.
