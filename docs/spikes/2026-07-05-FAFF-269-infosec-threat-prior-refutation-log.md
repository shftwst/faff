# FAFF-269 — Refutation log: infosec spec-review lens repo-specific threat context (a learned per-repo threat prior)

Design-settle spike per `docs/specs/2026-07-05-faff-269-infosec-threat-prior-spike-design.md`. Method: for each question, state an evidence-anchored hypothesis, attempt ≥2 distinct refutations (invariant-contradiction / threat-case / owner-boundary / YAGNI) against the invariant set, and close as survived / amended / narrowed. The invariant set: ADR-0010 (faff implements no sandbox; assert-not-launch; the no-execute floor), ADR-0013 (`.faff/` machine-acquired ⊕ `.faffrc.yaml` human-override storage split), ADR-0039 (inside the container the build subagent shares uid+filesystem, so on-disk orchestrator artifacts are forgeable pre-FAFF-325), ADR-0040 (fetched/grounded claims are untrusted data under the no-execute floor; no persisted evidence store at v1 because it would be forgeable), and design-register E's Logged / Explainable / Reversible guardrail + the cross-project meta-only firewall.

Ground truth re-verified at spike start (2026-07-05): `faff adr next-number` → 0046; ADR-0010/0013/0039/0040 all live and unsuperseded (`faff adr live-decisions`); `refute-infosec.md` is still the five generic items (authn/authz · secrets · input surface · blast radius · failure-as-bypass) headed "this v1 has no learned per-repo threat prior"; FAFF-267's committed spec still reserves "the infosec lens's `--system` prompt file + an optional grounding input, swappable later without touching the aggregation"; the eval `refutation-spec` KIND scores set-equality of objecting lenses (`env.objections` filtered to severity ∈ {blocker, major}) against `oracle.closed_set`; `mineRepo` (`bin/faff:7746`) is deterministic / read-only / no-LLM; `design/self-learning.md`, `design/future-directions.md`, `design/spec-stage.md` read in full.

**A premise the spike carries, not settles (recorded up front).** The ticket's third open question — "does a threat prior leak code context into the *code-blind* lane?" — is misspecified against the as-built code and is re-cast, not answered as posed. The **evaluator** (`faffter-noon-evaluate`) is the code-blind lane (its `holdout-verdict` asserts `code_blind:true` and it never reads the codebase). The **spec reviewer is not that lane** — prep already hands it the gateway + the files the spec names + `docs/adr/`, so the reviewer is not code-blind and a threat-model doc is one more `--context` input alongside inputs it already takes. The real infosec concern with a *stored* prior is data-sensitivity/integrity — a `.faff/` prior is build-lane-forgeable (ADR-0039), the same shape FAFF-325 addresses — and that concern drives SQ1/SQ2 below.

## SQ1 — What produces the prior?

The ticket's candidates: mined from repo surfaces (a `faff profile mine` extension, or an LLM synthesizer), a maintained config, or intake-time Q&A. And: is it an extension of the infra-profile acquirer or a distinct artifact?

**Hypothesis:** a per-repo threat prior is best produced as a **human-curated, version-controlled threat-model document**, not an autonomously-mined artifact — because faff's threats are *semantic* (properties of the trust architecture, not file-presence patterns) and a self-mined *persisted* prior is forgeable by the very lane the lens exists to catch.

- **Attempt 1 (invariant-contradiction — the deterministic-miner fit, ADR-0013) → AMENDS.** Can Candidate A — extend `faff profile mine` — produce the prior? The miner is deterministic, read-only, no-LLM, matching file *presence* (CI workflows, Dockerfiles, compose, Terraform, PaaS/language manifests). faff's real threats are semantic: "a new on-disk orchestrator artifact sits on the shared-uid+fs forge surface" (ADR-0039); "a trust flag the judged party sets about itself is circular"; "a persisted ledger field read without a liveness gate grants stale authority." None of these is a file-presence pattern. A deterministic miner can emit that `run-ledger.json` exists or that a `spec_review` slot is configured, but not the threat *content* that would prime the lens. So Candidate A cannot produce the prior's substance — at most coarse signals that are not the prior. The miner-as-producer is refuted.

- **Attempt 2 (threat-case — the forge concern applied to an LLM-mined persisted prior, ADR-0039/0040) → NARROWS.** Can Candidate B — an LLM synthesizer that reads the ADR log + audit history and writes a persisted `.faff/threat-prior.json` — produce it autonomously? Its output is a persisted `.faff/` artifact on the shared container filesystem, which the build subagent shares uid+fs with — build-lane-forgeable (ADR-0039), exactly the caveat ADR-0040 applied forward to a persisted grounding-evidence store. This is worse than a benign integrity gap: an adversarial (or drifting) build lane could *forge the threat prior to suppress a true objection* — delete the "self-attestation is circular" entry so the infosec lens waves through a self-attesting spec (refutation-spec-009's exact shape). A self-mined, persisted prior is therefore not merely ill-fitting; it is a new attack surface on the very lens meant to catch attacks. So any autonomously-produced prior must either not persist (ADR-0040 fetch-and-consume in-memory per invocation — heavy, still LLM-authored/untrusted, and it needs a live acquirer every review) or live in a source the build lane cannot forge at review time.

**Close: AMENDED-NARROWED-SURVIVES.** The ticket's "autonomous mining" framing is the weakest candidate on both axes — semantic content does not mine deterministically (Attempt 1), and a persisted mined prior is forgeable (Attempt 2). The surviving producer is the ticket's **"a maintained config"** option, sharpened: a **human-curated, git-committed threat-model document**. It carries the semantic content a human security-reviewer already holds; it lives in version control, so it is not build-lane-forgeable *at review time* (a worktree tamper shows in the diff review); and it satisfies design-E's Logged/Explainable/Reversible by construction (a git-tracked human artifact is inherently logged, explainable, and revertible). The autonomy is *relocated*, not lost: **acquisition** is a one-time human curation; **consumption** is fully autonomous — the lens reads the doc at every review with no human in the loop. That is the honest answer to the ticket's "without a human in the room": the human is out of the *review* loop, present only at the one-time authoring, because a self-authored prior is either ill-fitting or forgeable. (Intake-time Q&A is a UX variant of the same human-curation producer and is not separately load-bearing.)

## SQ2 — Where is it stored and how does the infosec lens consume it?

**Hypothesis:** store the prior as a version-controlled document (a committed `docs/threat-model.md`, or a path named by an `infosec_prior:` key in `.faffrc.yaml`), consumed by the infosec refuter as an additional `--context` file via the FAFF-267-named seam — no change to lens aggregation or the verdict contract.

- **Attempt 1 (invariant-contradiction — the forge/integrity concern, ADR-0039/0013) → AMENDS.** Does storage in `.faff/` — the ADR-0013 machine-acquired store — survive? No: a `.faff/` prior is build-lane-forgeable (SQ1 Attempt 2). But ADR-0013 splits storage by authorship: the machine-acquired half (`.faff/`, gitignored, regenerable) *and* a human-override half (`infra:` in `.faffrc.yaml`, version-controlled, human-authoritative, wins field-by-field). The threat prior is human-authored (SQ1), so it belongs in the human-override lane — version control — never the forgeable machine store. The storage question amends to: the prior lives in git (a committed doc, or a `.faffrc.yaml`-pointed committed path), consistent with SQ1's producer.

- **Attempt 2 (owner-boundary — the FAFF-267 aggregation seam) → SURVIVES.** Does consumption via `--context` avoid touching the fixed aggregation? The L4 refuter is invoked `--system refute-infosec.md --context <files> --diff <spec>` (`review-call.mjs`); the per-lens objections roll up in `aggregate.mjs`, which never sees the context files — it sees only each lens's emitted objection. Adding the threat-model doc as one more `--context` file is precisely the seam FAFF-267's committed spec reserved ("swappable later without touching the aggregation"). No aggregation change, no `spec-review-verdict` contract change, no new lens. The same holds at L1–L3 (the single-pass reviewer takes repo context the same way). Staleness folds into ordinary doc maintenance — the doc is re-read every review; a drifted threat-model doc is a docs-never-go-stale concern, not a new mechanism.

**Close: AMENDED-SURVIVES.** Storage = version control — a committed `docs/threat-model.md` (or a `.faffrc.yaml`-named committed path), the human-override lane of ADR-0013, never the forgeable `.faff/` machine store. Consumption = one additional `--context` file to the infosec refuter, the FAFF-267 seam, with no aggregation or contract change. The forge/integrity concern is dodged *by construction*: a git-tracked doc is not build-lane-forgeable at review time, and any worktree tamper is visible in the diff review. Staleness is ordinary doc maintenance.

## SQ3 — Is the value worth building over the generic checklist?

**Hypothesis:** a threat-model-primed infosec lens catches faff-specific threats — the forge surface (refutation-spec-007), stale-ledger authority (008), self-attestation (009) — that the generic five-item checklist plausibly misses, without over-firing on a sound same-surface spec (010); the lift is real and the wiring cost is tiny. **But the lift must be measured, not asserted.**

- **Attempt 1 (YAGNI — does the generic checklist already catch these?) → the genuine uncertainty.** The generic checklist carries two broad items — "blast radius" ("if abused, what is the worst it can do?") and "failure-as-bypass" ("can an error path silently skip a check?"). A *strong* frontier reviewer, reasoning hard on refutation-spec-007, might reach "the build lane can write this file → it can forge its own corrective input" from blast-radius alone, without any faff prior; on refutation-spec-009 it might spot the self-attestation circularity from first principles. So the lift is not guaranteed — on a strong-enough base reviewer the generic checklist may already sit near its ceiling on these fixtures, and a prior would add little. Whether the prior adds catches the base reviewer misses is an *empirical* question about the base reviewer's ceiling, not one refutation can settle by reasoning. The fixtures (007–010) exist precisely to measure it: three faff-specific catches (oracle `["infosec"]`) plus one same-surface near-miss (010, oracle `[]`) that catches the opposite failure — a prior that makes the lens over-fire on a spec that touches the forge surface but handles it correctly.

- **Attempt 2 (invariant-contradiction — can the experiment run in-session? the frontier-nesting constraint) → NARROWS the deliverable.** The primed-vs-generic run scores both arms through `node eval/run-evals.mjs` on the `refutation-spec` grader, which drives `claude -p` (frontier) or a Tailscale ollama (local). The frontier driver spawns a nested `claude -p` on the same account quota — the documented "never nest the frontier eval in a session" hazard (the `eval/` dir is excluded from CI for exactly this reason: real `claude -p` calls + the `~/.claude.json` config race). Confirmed empirically this session: invoking the runner on a single case (`--only refutation-spec-007`) hung past a two-minute wall with no output. So the measured run is structurally a **human-supervised** step — a plain terminal, or the local-ollama driver over Tailscale — not something the spike executes in-session. This is not a spike failure; it is the spec's own boundary ("accepting/recording any baseline is a separate human-supervised step") and the overrun-valve prescription ("do not force a binary the evidence does not support").

**Close: NARROWS.** The *design* is settled (SQ1 curated-committed-doc producer; SQ2 version-control storage + `--context` consumption, no aggregation change). The *value* is genuinely empirical — whether the prior beats a strong base reviewer's ceiling on the faff-specific fixtures — and the fixtures (007–010) are committed and runnable to answer it. But the measured run requires the live eval harness, which cannot run nested in-session; it is the named human-supervised gating step. SQ3 therefore closes as **GO-conditional**: build the (tiny) threat-model doc + one `--context` wiring line *iff* the measured run shows a positive, non-artefactual catch-rate lift on refutation-spec-007..009 with no near-miss regression on 010; record a **null** (closing design-register-E's infosec sub-question) if the lift is ≈0. The build is cheap either way, so the go/no-go rests entirely on the measured lift, never on implementation cost.
