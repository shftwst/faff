# Persistent short-code mint via POST /shorten

> Spec: faffter-dark-nlspec · 2026-08-20 · autonomous · claude-code/unknown · confidence: high.

This is the build spec for the second-slice epic gk-20260819-weudrt of the link-shortener service (project P1, "Core shorten-and-redirect service"). It is written for the build agent that implements the mint route, and for human reviewers gating it. This epic inherits the runnable stack shipped by its blocker gk-20260819-wng8an (a Go 1.23 stdlib net/http api plus a PostgreSQL 16 datastore under docker-compose, with golang-migrate migrations applied at startup and a two-role least-privilege split). It adds the first product route, `POST /shorten`, and the first real schema migration: a table that persists minted codes. It stores codes but does not read them back; the read path (`GET /{code}` redirect) is the next epic.

## 1. WHY — Problem and Principles

**The mechanism this epic turns on: a `POST /shorten` request mints a fresh, opaque 7-character code, writes a `code → url` row durably under the least-privilege runtime role, and returns the code.** The code is generated, not derived from the URL, so the same URL shortened twice yields two different codes with no deduplication. Persistence is a real datastore row created through a versioned migration, so the code the downstream redirect epic will resolve already survives an api restart the moment it is written.

**Problem statement.** The shipped skeleton stands up a healthy stack but serves no product route and stores nothing, so no code can be minted or persisted. This epic adds `POST /shorten`, which validates an absolute http(s) URL, mints a 7-character base62 code, and persists the `code → url` mapping through a new schema migration, returning 201 with the code.

**Design principles** (constraints that would cause an otherwise-valid implementation to be rejected):

**The code is minted, never derived from the URL, and is not deduplicated.** Each successful `POST /shorten` produces a fresh code, so two shortenings of the same URL return different codes (a PRD non-goal is URL deduplication). A scheme that hashes the URL into the code, or returns an existing code for a repeat URL, is out of bounds — it would collapse two shortenings to one code and fail the distinct-codes acceptance criterion.

**The mapping is persisted in the datastore through a versioned migration, applied under the migration role, not in process memory.** The storage table is created by a new golang-migrate migration file under the DDL-holding migration role, applied at startup by the existing machinery. An in-memory map, a process-local cache, or a table created ad hoc by the request path is out of bounds: persistence through the migration seam is what lets the code survive the api restart the downstream redirect epic must prove, and DDL from the request path would violate the least-privilege split.

**The request path holds no DDL, writes under the least-privilege runtime role, and never trusts request input into SQL.** The mint handler writes through the least-privilege runtime role (`app`, no DDL), which the shipped role split already grants DML on migrator-created tables. The URL is always bound as a query parameter, never concatenated into SQL text. This bounds the blast radius of any injection on this route to data access and keeps the untrusted URL out of the SQL grammar.

**A minted code is opaque and unguessable-by-construction, not a sequence.** The code is drawn from a cryptographic random source, not an incrementing counter, so it leaks neither the total number of codes minted nor their order. A counter encoded to base62 is out of bounds: it would leak volume and let a caller enumerate every stored URL by counting up, and it would need left-padding to reach a fixed 7-character width.

**Scope statement.** This epic is the write half of the core loop: it mints and persists codes. It does not read them back, redirect, expire them, or run the consolidated acceptance suite.

## 2. OUT OF SCOPE

- **`GET /{code}` redirect and unknown-code handling.** Why excluded: it is the next epic, gk-20260819-1ckwj6, which reads the row this epic writes. Extension point: a `GET /{code}` handler registered on the same router, reading `short_links` by primary key under the runtime role.
- **Time-to-live expiry (`ttl_seconds`).** Why excluded: project P2, epic gk-20260819-8td0lv. Extension point: an `expires_at` column added by that epic's own migration, plus a read-path expiry check; this epic accepts and ignores an unknown `ttl_seconds` field in the request body (see the unknown-fields decision) so the TTL epic adds behaviour without breaking the wire shape.
- **Authentication, authorization, and identity-based per-caller quotas.** Why excluded: authentication and authorization are explicit PRD non-goals for v1. **Per-source rate limiting — the volume-based storage-DoS mitigation — is now IN scope for this epic** (see the rate-limit constant in WHAT, the middleware in HOW, and the born-verifiable scenario in Scenarios); it bounds the rate at which any single unauthenticated source can grow `short_links`. What stays out of scope is *identity-based* per-caller quotas, which are impossible without authentication (a PRD non-goal); distributed multi-source abuse therefore remains bounded only by the per-source rate limit and the finite code space, an accepted residual tied to the auth non-goal rather than an unmitigated hole. Extension point: an auth middleware enabling per-caller quotas, added when a deployment target requires authenticated writes.
- **The consolidated acceptance test suite.** Why excluded: project P3, epic gk-20260819-xqkaty. Extension point: a suite exercising the full stack. A per-epic mint smoke test still rides inside this epic.
- **Deduplication of identical URLs, caller-chosen aliases, analytics or click counting, and a user interface.** Why excluded: all are PRD non-goals for v1. Extension point: none planned; explicit non-goals.

## 3. WHAT — Vocabulary, Types, and Interfaces

**Vocabulary.**

| Term | Definition |
|---|---|
| short code | A 7-character base62 string (`^[0-9A-Za-z]{7}$`) that identifies one stored URL. |
| mint | Generate a fresh short code and persist its mapping to a URL. |
| base62 | The 62-character alphabet `0-9`, `A-Z`, `a-z`; each character is one of 62 values. |
| runtime role | The least-privilege datastore role (`app`) the api serves requests under; it has DML on migrator-created tables but no DDL (shipped by gk-20260819-wng8an). |
| migration role | The DDL-holding role (`migrator`) that applies schema migrations at startup and owns the tables it creates (shipped by gk-20260819-wng8an). |

**Reference context.** This epic extends the shipped skeleton; the build agent should read these before starting.

| System | Language | Relevance |
|---|---|---|
| `api/main.go` | Go | Startup sequence; opens the runtime `*pgxpool.Pool` from `RUNTIME_DATABASE_URL` and builds the router via `httpapi.NewRouter()`; `main.go` registers the mint route with the store here (see HOW), leaving `NewRouter()` zero-arg and `/healthz` store-free. |
| `api/internal/httpapi/healthz.go` | Go | `NewRouter()` registering `GET /healthz` on a `http.ServeMux`; the mint handler registers `POST /shorten` alongside it. |
| `api/internal/migrations/*.sql` | SQL | Embedded, versioned migrations applied at startup; this epic adds `000002_*`. `000001_baseline` is an empty no-op. |
| `db/init/10-roles.sh` | SQL/shell | Role provisioning; its `ALTER DEFAULT PRIVILEGES FOR ROLE migrator ... GRANT SELECT, INSERT, UPDATE, DELETE ... TO app` is why the `app` role can write a table the `migrator` role creates, with no extra grant. |
| `docker-compose.yml` | YAML | Wires `MIGRATION_DATABASE_URL` as the `migrator` DSN and `RUNTIME_DATABASE_URL` as the `app` DSN — the fact that makes the ownership invariant below hold. |
| `api/internal/config/config.go` | Go | 12-factor config; `RUNTIME_DATABASE_URL` is the runtime-role DSN the mint path writes under. |

**Ownership invariant (why the runtime role can write the new table).** The shipped `ALTER DEFAULT PRIVILEGES FOR ROLE migrator ... TO app` grants `app` DML only on tables **owned by `migrator`**. This holds here because the shipped `docker-compose.yml` sets `MIGRATION_DATABASE_URL` to `postgres://migrator:...@datastore/...`, so `db.ApplyMigrations` authenticates as `migrator` and `migrator` owns the `000002` table. If a future change pointed the migration DSN at a different role (superuser, bootstrap `POSTGRES_USER`), that role would own the table, the default-privileges grant would not fire, and the first runtime `INSERT` would fail with a permission error (SQLSTATE 42501). The build must keep the migration connection authenticating as `migrator`; the `000002` migration adds no explicit grant because the default-privileges grant already covers a migrator-owned table.

**Storage schema (new migration `000002`).**

```
TABLE short_links:
  code        text         # PRIMARY KEY; the 7-char base62 short code
  url         text NOT NULL # the stored absolute http(s) URL, verbatim
  created_at  timestamptz NOT NULL DEFAULT now()  # mint time (audit/ordering)

  CONSTRAINT code is PRIMARY KEY   # uniqueness is enforced here, and is the
                                   # collision signal the mint path retries on
```

Created by the migration role (`migrator`), which owns it, so the shipped default-privileges grant lets `app` `INSERT` and (for the downstream read epic) `SELECT` with no further grant. The down migration drops the table.

**Tunable constants (compile-time, not environment-sourced).** These are fixed constants in the api binary, not 12-factor environment variables — they are invariants of the wire contract and storage shape, not per-deployment settings, so they do not flow through `config.Config`:

| Constant | Value | Meaning |
|---|---|---|
| `CODE_LEN` | 7 | short-code length in base62 characters |
| `MAX_URL_LEN` | 2048 | maximum accepted `url` byte length |
| `MAX_BODY_BYTES` | 8192 | maximum accepted request-body byte length (bounds decode cost) |
| `MAX_MINT_ATTEMPTS` | 5 | bound on collision-retry regeneration attempts |
| `RATE_LIMIT_MAX` | 60 | max `POST /shorten` requests per window per client source IP before 429 |
| `RATE_LIMIT_WINDOW_SECONDS` | 60 | fixed-window length (seconds) for the per-source rate limit |

**`POST /shorten` contract.**

```
ENDPOINT POST /shorten
  Request:  Content-Type application/json; body length <= MAX_BODY_BYTES
            body: { "url": "<absolute http(s) URL>" }
            - unknown fields (e.g. a future "ttl_seconds") are ignored, not rejected
  Response on success: status 201 Created
            Content-Type application/json
            body: exactly { "code": "<7 base62 chars>" }, matching ^[0-9A-Za-z]{7}$
  Response on invalid request: status 400
            body: { "error": "invalid_request", "message": "<human text>" }
  Response on wrong method (GET/PUT/... on /shorten): status 405
            (http.ServeMux method-pattern default for a POST-only path)
  Response on rate-limit exceeded: status 429 Too Many Requests
            body: { "error": "rate_limited", "message": "<human text>" }
            (> RATE_LIMIT_MAX requests within RATE_LIMIT_WINDOW_SECONDS from one client source IP;
             no code is minted for a rejected request)
  Response on collision-retry exhaustion or any datastore fault: status 500
            body: { "error": "internal", "message": "..." }
  Semantics: each success mints a NEW code; the same URL posted twice yields two
             different codes (no deduplication).
```

**Error catalog.** Every 4xx/5xx carries a structured JSON body `{ "error": "<token>", "message": "<text>" }`. The token is a stable machine string; the message carries no DSN, password, SQL text, or stack detail.

| Status | `error` token | When |
|---|---|---|
| 400 | `invalid_request` | body too large, non-JSON, missing/empty/non-string `url`, or a `url` that fails a validation rule |
| 405 | `method_not_allowed` | a non-POST method on `/shorten` (ServeMux default body may be plain; the token is used if a custom handler is added) |
| 429 | `rate_limited` | more than `RATE_LIMIT_MAX` requests within `RATE_LIMIT_WINDOW_SECONDS` from one client source IP; no code is minted |
| 500 | `internal` | datastore unreachable, any non-collision SQL error, or collision-retry exhaustion (astronomically unlikely) |

**Validation rules for the `url` field** (all failures return 400 with `error: "invalid_request"`):

| Rule | Reject when |
|---|---|
| Present and non-empty | `url` missing, null, empty, or not a string |
| Parseable | `net/url` cannot parse it |
| Absolute with a host | no scheme, or no host component |
| Scheme is http or https | scheme (lowercased) is anything else (`ftp`, `mailto`, `javascript`, `file`, …) |
| Bounded length | byte length exceeds `MAX_URL_LEN` (2048) |

## 4. HOW — Behavior

**Architecture and approach.** `POST /shorten` is a new handler on the existing `http.ServeMux`. Startup is unchanged except that `main.go` now constructs a thin store from the already-opened runtime `*pgxpool.Pool` and registers the mint route with it. `NewRouter()` stays zero-arg and registers `GET /healthz` only, so the liveness route keeps no datastore dependency and the shipped router seam is preserved; `main.go` registers the mint route separately via a small `httpapi.RegisterShorten(mux, store)` helper (or by `mux.Handle("POST /shorten", httpapi.Shorten(store))` directly). The store carries the runtime pool, so the mint route's least-privilege wiring stays explicit without coupling the datastore into the shared router constructor. The store owns the SQL (`INSERT INTO short_links (code, url) VALUES ($1, $2)`); the handler owns validation, code generation, and the collision-retry loop. The new `000002` migration creates `short_links`; the existing embedded-FS + golang-migrate machinery discovers and applies it at startup with no change to the startup code.

**Rate limiting (volume-abuse mitigation).** The mint route is wrapped by an in-process fixed-window rate-limit middleware, registered on `POST /shorten` only (never on `GET /healthz`, which must stay dependency-free). The middleware keys on the **connecting client's source IP** — the host portion of the request `RemoteAddr` — and **deliberately does not trust `X-Forwarded-For`** (an attacker who could set that header could rotate the key to evade the limit; in the single-instance compose deployment there is no trusted proxy to populate it). It maintains a per-key request count within a `RATE_LIMIT_WINDOW_SECONDS` fixed window (a small in-process map with lazy per-key window reset — no external store, sufficient for the single-instance v1); when a key's count within the current window exceeds `RATE_LIMIT_MAX`, the request is rejected with **429 `rate_limited` before the body is read, before any code is generated, and before any row is written** (so a rejected request mints nothing and touches the datastore not at all). This bounds the rate at which any single unauthenticated source can grow `short_links` — the storage-DoS vector. A shared/distributed limiter is an extension point for a future multi-instance deployment; the in-process limiter is correct for the single-api-container compose stack this epic ships.

**Mint procedure (the ambiguity point):**

```
PROCEDURE handle_shorten(request):
  1. IF method is not POST: 405 (ServeMux path-method default).
  2. Cap the body at MAX_BODY_BYTES (e.g. http.MaxBytesReader) BEFORE decoding.
     a. IF the body exceeds the cap: 400 { error: "invalid_request" }.
  3. Decode the JSON body into { url string, ...ignored }.
     a. IF the body is not valid JSON, or url is absent/empty/not-a-string:
        400 { error: "invalid_request" }.
  4. Validate url per the validation-rules table (parse, absolute, http/https
     scheme, host present, length <= MAX_URL_LEN).
     a. IF any rule fails: 400 { error: "invalid_request" }.
  5. Mint-and-persist with bounded collision retry:
     FOR attempt in 1..MAX_MINT_ATTEMPTS (5):
       a. code := generate_code()            # 7 base62 chars, see below
       b. err := store.Insert(ctx, code, url)
       c. IF err is nil: 201 { code }.        # success, return the minted code
       d. IF err is a unique-violation (SQLSTATE 23505) on the primary key:
            continue                          # rare collision; mint a new code
       e. ELSE: log non-secret metadata, 500 { error: "internal" }.  # real fault
     AFTER the loop without success:
       log, 500 { error: "internal" }.  # collision space exhausted (astronomically unlikely)

PROCEDURE generate_code() -> string:
  # 7 characters from the 62-char base62 alphabet, cryptographic source,
  # WITHOUT modulo bias.
  1. alphabet := "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz"  # len 62
  2. out := ""
  3. WHILE len(out) < 7:
       b := one cryptographically-random byte (crypto/rand)
       IF b >= 248:  continue        # reject the top 8 of 256 values so the
                                      # remaining 248 map evenly (248 = 4*62)
       out += alphabet[b % 62]
  4. RETURN out
```

**Behaviour summary.** A valid request mints a random 7-character code, inserts it under the runtime role, and returns it; a duplicate code (caught by the primary-key constraint) is retried with a fresh code; anything else is a 400 (bad input) or 500 (datastore fault / exhaustion) with a structured body.

**Edge cases and error handling.**

- Request body larger than `MAX_BODY_BYTES` → 400 `invalid_request`, decode never attempted (bounds memory/decode cost, closes the large-payload OOM vector).
- Empty or non-JSON body, missing/empty/non-string `url` → 400 `invalid_request`. Terminal for the request.
- `url` that parses but is relative, schemeless, hostless, or a non-http(s) scheme → 400 `invalid_request`.
- `url` longer than `MAX_URL_LEN` → 400 `invalid_request` (bounds stored row size).
- Unknown JSON fields (e.g. `ttl_seconds`) → ignored, request still succeeds (forward-compatible with the TTL epic).
- Primary-key collision on insert → retried up to `MAX_MINT_ATTEMPTS` with a fresh code; exhaustion is a 500 `internal`.
- Datastore unreachable / any non-collision SQL error (including a permission error if the ownership invariant is broken) → 500 `internal`; the response and logs carry no DSN, password, SQL text, or stack detail (reuse the shipped `dsn.SafeMetadata` for any connection-level log line).

**Failure modes — how the approach falls over, and how you would notice.**

- **The failure:** the code generator has modulo bias (naive `randomByte % 62` over the full 0–255 range), so early-alphabet characters are over-represented. **How you would know:** a unit test over a large in-process sample of `generate_code()` shows a skewed character-frequency distribution rather than roughly uniform. **What it means:** use rejection sampling (reject bytes ≥ 248) as in the pseudocode. This is a code-quality/opacity property proven by a unit test, not a black-box HTTP scenario (a biased generator still emits 7-char base62 codes, so the HTTP oracles cannot see it) — see the note in Scenarios.
- **The failure:** the mint store is opened from `MIGRATION_DATABASE_URL` (the `migrator` DSN) instead of `RUNTIME_DATABASE_URL`, silently bypassing the least-privilege split — every data oracle still passes because `migrator` also has DML on `short_links`. **How you would know:** the Postgres statement-log role oracle (Scenario: run the datastore with `log_statement = all` and a `log_line_prefix` carrying `%u`, then confirm the mint `INSERT` is logged as user `app`, not `migrator`); the negative-DDL scenario proves the `app` role itself is DDL-denied (a necessary companion); and code review of which config field the store pool is built from. **What it means:** the store must be built from the runtime pool `main.go` opens from `RUNTIME_DATABASE_URL`.
- **The failure:** the `000002` table is owned by a role other than `migrator` (migration DSN re-pointed), so the default-privileges grant does not fire and the runtime `INSERT` fails 42501. **How you would know:** the mint scenario returns 500 `internal` instead of 201; the datastore log shows a permission-denied on `short_links`. **What it means:** keep the migration DSN authenticating as `migrator` (the ownership invariant in WHAT).

**Anti-pattern:** deriving the code from the URL (hashing) or returning an existing code for a repeat URL. Why: it deduplicates, so two shortenings of one URL collapse to one code and the distinct-codes criterion fails.

**Anti-pattern:** creating the `short_links` table from the request path (or an ORM auto-migrate on first write). Why: it puts DDL on the runtime role, breaking the least-privilege split; the table must come from the `000002` migration under the migration role.

**Anti-pattern:** string-concatenating the URL into the INSERT. Why: it is an injection surface on untrusted input; always bind the URL as a parameter.

**Anti-pattern:** decoding the request body before capping its size. Why: an unbounded JSON body with a valid `url` plus megabytes of ignored fields is an OOM vector; cap with `MAX_BODY_BYTES` first.

**Not black-box verifiable (proven by unit test, not an HTTP scenario).** Two DONE properties cannot be forced black-box against the live stack and are covered by in-process unit tests instead of scenarios, so the spec does not pretend an HTTP oracle exists for them:

- **No modulo bias in code generation.** A biased generator still emits 7-char base62 codes, so the HTTP oracles above cannot distinguish it. A unit test over a large sample (e.g. 100,000 codes ≈ 700,000 characters) asserts every one of the 62 alphabet characters appears and the character-frequency distribution is uniform against a stated threshold — a chi-squared goodness-of-fit over the 62 buckets that does not reject uniformity at p > 0.01 (equivalently, each character's count within roughly ±5% of the expected 1/62 at that sample size).
- **Collision-retry exhaustion path.** Forcing five consecutive primary-key collisions black-box is not feasible (62^7 ≈ 3.5×10^12 space). The retry loop and its exhaustion result are covered by a unit test that injects a store stub returning a unique-violation, asserting the loop retries and surfaces 500 `internal` on exhaustion.

- No datastore credential, DSN, SQL text, or stack trace appears in any `POST /shorten` response body or in the api logs for a failed request (non-functional constraint; the datastore-stopped scenario forces a 500 and inspects for leakage).

## 6. DESIGN DECISION RATIONALE

**How is the short code generated?** Options: (a) cryptographic random 7-char base62 with rejection sampling; (b) an incrementing counter (or Postgres sequence) encoded to base62; (c) a hash of the URL truncated to 7 chars. **Chosen:** (a) cryptographic random base62. Rationale: it satisfies distinct-codes-for-the-same-URL trivially (no dedup), leaks neither volume nor order, and needs no padding to reach a fixed 7-character width. A counter (b) leaks total volume and lets a caller enumerate stored URLs, and needs left-padding early on. A hash (c) deduplicates identical URLs to one code, failing the distinct-codes criterion. The 62^7 ≈ 3.5 × 10^12 space makes collisions astronomically rare, and the primary-key constraint plus bounded retry handles the rare case correctly.

**How are code collisions handled?** Options: ignore (rely on improbability); a `SELECT` existence check before insert; insert and retry on the unique-violation. **Chosen:** insert under a primary-key constraint and, on SQLSTATE 23505, regenerate and retry up to `MAX_MINT_ATTEMPTS` (5), surfacing exhaustion as 500 `internal`. Rationale: the database is the single source of uniqueness truth (no check-then-insert race), and the retry is bounded so it cannot loop forever. A pre-insert `SELECT` has a time-of-check/time-of-use race and costs an extra round trip. (Whether exhaustion warrants a distinct wire token is decided separately below.)

**How is collision-retry exhaustion reported?** Options: a distinct token (e.g. `code_unavailable`); reuse the generic `internal` 500. **Chosen:** reuse `internal`. Rationale: exhaustion is reachable only at a table scale this v1 does not address (roughly 10^11 rows against a 62^7 ≈ 3.5×10^12 space), so a distinct wire token would be effectively dead — a client would never observe it, and if it ever did, "retry the whole request" would be the wrong advice because the code space is genuinely filling. Reusing `internal` keeps the wire contract to tokens a caller can actually see. The retry loop still exists (a single spurious collision is retried transparently); only its astronomically-unlikely exhaustion collapses into the generic fault token.

**What is the storage schema?** Options: `(code, url, created_at)`; add an `id` surrogate key; add `expires_at` now. **Chosen:** `short_links(code text primary key, url text not null, created_at timestamptz not null default now())`. Rationale: `code` is the natural key the redirect epic looks up by, so it is the primary key and the uniqueness constraint in one; `created_at` gives cheap audit/ordering. `expires_at` is deliberately omitted — it belongs to the TTL epic's own migration, keeping this slice minimal. A surrogate `id` adds nothing the code key does not already provide.

**Are unknown JSON request fields rejected or ignored?** Options: strict decode (reject unknown fields); lenient decode (ignore them). **Chosen:** ignore unknown fields. Rationale: the TTL epic adds `ttl_seconds` to the same body; ignoring unknown fields now means that epic adds behaviour without a breaking wire change, and an unexpected field is not a client error worth a 400 here. The trade-off (a typo'd field name is silently ignored) is acceptable for a v1 with a single required field.

**How is request-body size bounded?** Options: rely on the JSON decoder; cap the body before decoding. **Chosen:** cap at `MAX_BODY_BYTES` (8192) with `http.MaxBytesReader` before any decode. Rationale: without a cap, a valid `url` plus megabytes of ignored fields is an OOM vector, precisely because unknown fields are tolerated. 8 KiB comfortably fits a single `url` up to `MAX_URL_LEN` plus JSON framing and a small `ttl_seconds`.

**Where does the datastore access live, which role, and how is the route wired?** Options: SQL inline in the handler vs a thin store type; and threading the store through `NewRouter` vs registering the mint route separately. **Chosen:** a thin store type (e.g. `internal/links`, `links.Store`) holding the runtime `*pgxpool.Pool`, with the handler calling `store.Insert(ctx, code, url)`; and `NewRouter()` stays zero-arg (healthz only) while `main.go` registers the mint route with the store via `httpapi.RegisterShorten(mux, store)`. Rationale: the store keeps the handler testable and the SQL in one place and makes explicit that the mint path uses the runtime pool from `RUNTIME_DATABASE_URL`, never the migration DSN. Keeping `NewRouter()` zero-arg preserves the shipped router seam and keeps `GET /healthz` free of any datastore dependency — making the store a required router-constructor argument would couple the liveness route to the pool, which the skeleton deliberately avoided.

**Are the size/length/retry bounds environment-configurable?** Options: 12-factor env vars via `config.Config`; compile-time constants. **Chosen:** compile-time constants. Rationale: `CODE_LEN`, `MAX_URL_LEN`, `MAX_BODY_BYTES`, and `MAX_MINT_ATTEMPTS` are invariants of the wire contract and storage shape (a 7-char code is the acceptance criterion itself), not per-deployment knobs; keeping them out of the environment avoids a config surface whose only effect would be to break the contract if tuned. `RATE_LIMIT_MAX` / `RATE_LIMIT_WINDOW_SECONDS` are kept compile-time for v1 for the same consistency and to keep this slice minimal — but note these are the one pair a real deployment would most plausibly want to env-source (a genuine per-deployment tuning knob, unlike the wire-shape constants); env-sourcing them via `config.Config` is a clean, contract-preserving extension point, deliberately deferred here rather than expanded into this slice.

**How are errors reported?** Options: bare status codes; a structured JSON error body. **Chosen:** a structured JSON body `{ "error": "<token>", "message": "<text>" }` on every 4xx/5xx, per the error catalog, matching the PRD's "structured JSON error responses" P1 requirement. Rationale: a stable machine token lets a client branch without string-matching prose, and the message never carries datastore internals.

**How is volume-based storage abuse bounded?** Options: (a) accept unbounded growth (a documented tradeoff, no mitigation); (b) a per-source in-process fixed-window rate limit returning 429; (c) a global row-count cap; (d) require authentication for writes. **Chosen:** (b) a per-source fixed-window rate limit. Rationale: it bounds the rate at which any single unauthenticated source can grow `short_links` — the realistic single-abuser storage-DoS vector — with a born-verifiable 429, needing neither authentication (a PRD non-goal) nor external state (the v1 stack runs a single api container). (a) leaves the DoS entirely unmitigated. (c) a global cap turns a full table into a service-wide denial of service for *all* callers (a legitimate fill locks everyone out), which is worse than the unbounded-growth problem it addresses. (d) auth-based per-caller quotas need authentication, an explicit v1 non-goal. Keying on the connecting `RemoteAddr` rather than the spoofable `X-Forwarded-For` prevents trivial key-rotation evasion; distributed multi-source abuse remains bounded only by the per-source rate and the finite 62^7 code space, an accepted residual tied to the auth non-goal (see OUT OF SCOPE), not an unmitigated hole.

## 8. DONE — Definition of Done

### From WHY
- [ ] `POST /shorten` mints a fresh code per success; the same URL posted twice returns two different codes (no deduplication).
- [ ] The `code → url` mapping is persisted through the new `000002` migration (a migrator-owned table), not in process memory.
- [ ] The code is drawn from a cryptographic random source, not a counter/sequence.

### From WHAT (types and interfaces)
- [ ] Migration `000002` creates `short_links(code text primary key, url text not null, created_at timestamptz not null default now())` under the `migrator` role; the down migration drops it.
- [ ] `POST /shorten` returns 201 with body exactly `{ "code": "<7 base62>" }` matching `^[0-9A-Za-z]{7}$` on a valid request.
- [ ] Errors follow the catalog: 400 `invalid_request`, 405 wrong-method, 500 `internal` on datastore fault or collision-retry exhaustion; every error body is `{ "error", "message" }`.
- [ ] Error bodies and failed-request logs carry no DSN, password, SQL text, or stack detail.

### From HOW (behaviour)
- [ ] `main.go` builds a `links.Store` from the runtime `*pgxpool.Pool` (opened from `RUNTIME_DATABASE_URL`) and registers the mint route with it; `NewRouter()` stays zero-arg and registers `GET /healthz` only (healthz keeps no store dependency).
- [ ] The mint handler writes through the runtime role, never the migration DSN — verified by the Postgres-statement-log role oracle and at code review (see the least-privilege failure mode).
- [ ] The URL is bound as a query parameter in the INSERT, never concatenated into SQL.
- [ ] Code generation produces 7 base62 characters without modulo bias (rejection sampling) — proven by a unit test over a large sample against the stated uniformity threshold.
- [ ] The request body is capped at `MAX_BODY_BYTES` before decoding.

### From HOW (edge cases)
- [ ] Body over `MAX_BODY_BYTES`, missing/empty/non-string `url`, non-JSON body, relative/schemeless/hostless URL, non-http(s) scheme, and over-length URL each return 400 `invalid_request`; no code is minted.
- [ ] A non-POST method on `/shorten` returns 405.
- [ ] Unknown JSON fields (e.g. `ttl_seconds`) are ignored and the request still succeeds.
- [ ] A primary-key collision is retried with a fresh code up to `MAX_MINT_ATTEMPTS`; exhaustion returns 500 `internal` (retry loop + exhaustion proven by a unit test injecting a unique-violation).

### Security
- [ ] The runtime `app` role holds no DDL (negative-DDL scenario), and the mint `INSERT` is performed by the `app` role (Postgres-statement-log oracle), not the migration DSN.
- [ ] A forced datastore fault returns 500 with a structured body and leaks no DSN, password, SQL fragment, or stack trace in the body or the api logs.
- [ ] `POST /shorten` enforces a per-source-IP fixed-window rate limit: more than `RATE_LIMIT_MAX` requests within `RATE_LIMIT_WINDOW_SECONDS` from one source returns 429 `rate_limited` and mints no code (the `short_links` row count is unchanged by a rejected request), bounding the volume-based storage-DoS vector; the limiter keys on the `RemoteAddr` source IP and does not trust `X-Forwarded-For`, and wraps `POST /shorten` only (not `GET /healthz`).

### Acceptance (the epic's headline)
- [ ] A valid absolute http(s) URL to `POST /shorten` returns 201 and a `^[0-9A-Za-z]{7}$` code; two shortenings of the same URL return different codes; the minted mapping is present as a `short_links` row in the datastore.
