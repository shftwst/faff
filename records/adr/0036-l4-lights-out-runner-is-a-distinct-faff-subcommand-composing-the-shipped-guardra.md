# ADR 0036 — L4 lights-out runner is a distinct faff subcommand composing the shipped guardrail contracts

- **Status:** Accepted
- **Date:** 2026-06-29
- **Issue:** FAFF-225

## Context

The gateway levels table names L4's entry point `lights-out (frontier)`, but there has been no command or mode for it: an unattended L4 run was a manual assembly of `/faff-beep-boop` flags with no enforced floor, where a single missing precondition (no budget ceiling, a bare host, an unreachable review slot) silently degrades the run. L4 is "leave the building entirely" — correctness held up by adversarial machinery (a second-opinion model, a code-blind holdout) rather than by a human reviewing parks in the morning. That only earns trust if "go lights-out" is one self-checking action that *refuses to start* unless the guardrails it names are actually live.

By the time this slice was built, the two keystone guardrails the L4 floor turns on had shipped — the Sentry live derailment kill-switch (`faff sentry check|abort`) and the code-blind holdout verdict (`faff holdout verdicts`, rolled into `faff prdr coverage --dod-verdicts`) — alongside the already-shipped admissibility, terminating, budget, observability, spec-review-verdict, and container-check contracts. Each guardrail is its own ticket exposing a deterministic CLI contract. So the runner's job is **composition, not mechanism**: mint an L4 run with strict defaults, probe each guardrail's contract at launch, refuse on any unsafe precondition, and print a banner naming exactly which guardrails are live this run. The blast radius itself is out of scope — host isolation and `--dangerously-skip-permissions` are the container's responsibility (the containerisation ADR), not faff's; the runner detects and refuses, it never weakens the host.

Two questions had to settle before building. **Command surface:** a distinct `faff` subcommand, a `/faff-beep-boop --lights-out` flag, or a level-recipe preset? The CLI's command set is governed by the subcommand registry as its single source of truth (ADR-0014). **Guardrail disposition:** with both keystones now live, does a v1 ever ship as a degraded "reduced mode", or is a lights-out run always fully armed? This ADR records the runner's command-surface and compose-over-live-contracts decision; the adversarial advisory→merge-gating promotion and the richer dial-coherence preflight were split out to their own tickets and are explicitly *not* part of this slice.

## Decision

**The L4 lights-out entry point is a distinct `faff` subcommand (`faff lights-out`), registered in the subcommand registry per ADR-0014, that runs a fail-closed basic preflight, then on pass mints a strict-defaults L4 run-ledger and renders + persists a run banner.** It is **not** a `/faff-beep-boop --lights-out` flag and **not** a level-recipe preset.

- **A subcommand, not a flag or a recipe.** A flag re-introduces the manual-flag-assembly problem the runner exists to remove — one forgotten flag silently degrades the run. A recipe preset couples v1 to an as-yet-unbuilt recipe schema. A subcommand gives a clean strict-defaults entry, a natural home for the banner, and the registry-governed surface ADR-0014 mandates. The exact verb is a minor naming detail; *subcommand, not flag, not recipe* is the fixed shape.
- **Compose the shipped contracts; re-implement none.** The runner probes and calls `faff admissible --lights-out`, the `spec-review-verdict` contract, `faff run-done`, `faff budget check`, `faff events`, `faff sentry`, `faff holdout`/`faff prdr coverage`, and `faff container-check`. Every guardrail decision traces to a CLI-contract call — the runner owns no copy of any guardrail's logic. Its `armed: Map<Guardrail, State>` derives from a genuine reachability probe, never from config presence alone, and the persisted banner is derivable one-to-one from `armed`.
- **Fully armed or refuse — no reduced mode.** Because both keystones are live and reachable, a lights-out run is fully armed (all eight guardrails `live`) or it refuses. A keystone probe failure is a reachability fault to refuse on, not a designed keystone-absent path. The preflight is fail-closed everywhere: a non-contained host, an unreachable `review`/`spec_review` slot (configured-but-unreachable counts as absent, never pass+skip), an unset budget ceiling, any non-live guardrail, or a failed floor assertion (no-execute, worktree isolation, the Autonomous Mode Contract) refuses to go lights-out and mints nothing.
- **faff owns the discipline, not the cage.** The runner never self-grants `--dangerously-skip-permissions` and never weakens the host; on a non-contained host it refuses and points at the containerisation ADR. On the lights-out path `container-check` is promoted from its L1–L3 warn to a hard block; L1–L3 behaviour is unchanged (the surface is additive).

## Consequences

- **The entry-point shape is fixed for every later lights-out slice.** Future L4 work — promoting the adversarial review advisory to a merge-gating `critical → needs-human` signal, and the richer dial-coherence preflight that rejects reckless level+appetite+slots+gates combinations — extends this subcommand and its run-ledger rather than re-litigating the surface. They are separate, independently reviewable tickets that build on this slice.
- **Adding or moving a guardrail is a contract-probe change, not a logic change.** Because the runner composes contracts behind reachability probes, a guardrail's policy change lands in its own CLI and the runner tracks it automatically. The failure mode to watch is the runner drifting into re-implementing a guardrail (its own budget arithmetic, its own derailment thresholds) — that is an anti-pattern to abandon: resolve every guardrail through its CLI contract at dispatch.
- **The banner is the human's trust contract.** A morning (or in-flight) reader can tell a fully-armed L4 run from a degraded one by reading the persisted banner, without re-deriving config. The risk to guard is false-arming — reporting `live` for a configured-but-unreachable guardrail; `armed` state must come from a reachability probe, enforced by the selftest table.
- **Consistent with the surrounding decisions.** The surface registers per ADR-0014 (subcommand registry = SSOT); the blast-radius boundary defers to the containerisation ADR; the merge fail-safe relies on the machine-DoD-verification posture (ADR-0029: born-verifiable criteria trusted unattended, prose forced to needs-human) so an unverified DoD drives `prd_satisfied=false` and the run escalates rather than merging un-verified work.
