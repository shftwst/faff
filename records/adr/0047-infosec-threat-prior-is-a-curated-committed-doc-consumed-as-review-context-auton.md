# ADR 0047 — Infosec threat-prior is a curated committed doc consumed as review context; autonomous mining refuted

- **Status:** Accepted
- **Date:** 2026-07-05
- **Issue:** FAFF-269

## Context

The spec-stage reviewer's infosec lens (single-pass at L1–L3, adversarial per-lens refuter at L4) runs a **generic** threat checklist — authn/authz, secrets, input surface, blast radius, failure-as-bypass — self-annotated in `refute-infosec.md` as having "no learned per-repo threat prior". `design/spec-stage.md` §A left one question open: *how does the infosec lens get repo-specific threat context without a human?* — tied to design-register E (self-learning). FAFF-267's committed spec reserved the seat: "the infosec lens's `--system` prompt file + an optional grounding input, swappable later without touching the aggregation."

FAFF-269 was the design-settle spike for that seat. It asked three questions: **SQ1** what produces a learned per-repo threat prior (mined? a maintained config? intake Q&A?); **SQ2** where it is stored and how the lens consumes it; **SQ3** whether the value beats the generic checklist enough to build it — with a null result (generic is sufficient) an explicitly valid outcome. Refutation log: `records/spikes/2026-07-05-FAFF-269-infosec-threat-prior-refutation-log.md`.

A premise correction the spike carried, not answered: the ticket's "does a threat prior leak code into the code-blind lane?" is misspecified against the as-built code. The **evaluator** is the code-blind lane (`holdout-verdict` asserts `code_blind:true`); the **spec reviewer is not** — prep already hands it the gateway, the files the spec names, and `records/adr/`. So a threat-model doc is one more `--context` input alongside inputs the reviewer already takes. The real infosec concern with a *stored* prior is data-sensitivity/integrity: a `.faff/` artifact is build-lane-forgeable (ADR-0039), the same shape FAFF-325 addresses.

Invariant set the refutation ran against: ADR-0010 (faff implements no sandbox; the no-execute floor), ADR-0013 (`.faff/` machine-acquired ⊕ `.faffrc.yaml` human-override storage split), ADR-0039 (the build subagent shares uid+filesystem inside the container, so on-disk orchestrator artifacts are forgeable pre-FAFF-325), ADR-0040 (fetched/grounded claims are untrusted data; no persisted evidence store because it would be forgeable), and design-register E's Logged/Explainable/Reversible guardrail + the cross-project meta-only firewall.

## Decision

**A per-repo infosec threat prior, if built, is a human-curated, version-controlled threat-model document consumed by the infosec refuter as one additional `--context` file — never an autonomously-mined, persisted `.faff/` artifact. The GO/NO-GO on building it is gated on a measured primed-vs-generic catch-rate run against committed fixtures, which is a human-supervised step.**

- **SQ1 — producer: a curated, git-committed threat-model doc (autonomous mining refuted).** A deterministic `faff profile mine` extension cannot produce it — faff's threats are *semantic* (a new on-disk orchestrator artifact on the shared-uid+fs forge surface; a self-attested trust flag; a stale-ledger authority read without a liveness gate), not file-presence patterns the read-only/no-LLM miner matches. An LLM synthesizer that persists a `.faff/threat-prior.json` is worse than ill-fitting: the persisted artifact is build-lane-forgeable (ADR-0039), so an adversarial or drifting build lane could **forge the prior to suppress a true infosec objection** — a new attack surface on the very lens meant to catch attacks. The surviving producer is the ticket's "maintained config" option, sharpened to a **human-authored, git-tracked threat-model doc**. Autonomy is relocated, not lost: **acquisition** is a one-time human curation; **consumption** is fully autonomous (the lens reads the doc at every review, no human in the loop). That is the honest reading of "without a human in the room" — the human is out of the *review* loop, present only at the one-time authoring, because a self-authored prior is either ill-fitting or forgeable.
- **SQ2 — storage in version control; consumption via the FAFF-267 `--context` seam.** The prior lives where ADR-0013 puts human-authored config — the version-controlled override lane (a committed `docs/threat-model.md`, or a `.faffrc.yaml`-named committed path) — **never** the forgeable `.faff/` machine-acquired store. The infosec refuter consumes it as one more `--context` file (`review-call.mjs --context …`), the exact seam FAFF-267 reserved: no change to lens aggregation, no `spec-review-verdict` contract change, no new lens. The forge/integrity concern is dodged **by construction** — a git-tracked doc is not build-lane-forgeable at review time, and a worktree tamper is visible in the diff review. Staleness folds into ordinary docs-never-go-stale maintenance (the doc is re-read every review).
- **SQ3 — value is empirical; GO/NO-GO gated on a measured run (design settled, measurement pending).** Whether the prior beats a *strong* base reviewer's ceiling is genuinely uncertain: the generic checklist's broad "blast radius" and "failure-as-bypass" items may already near-ceiling on the faff-specific fixtures without any prior. This is measured, not reasoned: four fixtures ship (`eval/cases/refutation-spec-007..010` — three faff-specific catches on the ADR-0039 forge surface, the FAFF-378 stale-ledger escalation, and the self-attestation/code-blindness circularity; plus one same-surface **near-miss**, 010, that catches the opposite failure of a prior making the lens over-fire). The primed-vs-generic run scores both arms through the existing `refutation-spec` grader. **It is a human-supervised step**: the frontier eval driver spawns `claude -p`, the documented "never nest the frontier eval in a session" hazard (confirmed this session — a single-case run hung), so the measured run happens in a plain terminal or via the local-ollama driver. GO-narrow (build the doc + one `--context` line) iff the run shows a positive, non-artefactual catch-rate lift on 007–009 with no near-miss regression on 010; NULL (close design-register-E's infosec sub-question) if the lift is ≈0.

Rejected: (a) a deterministic-miner-produced prior (semantic content doesn't mine); (b) an LLM-synthesized persisted `.faff/` prior (forgeable — new attack surface on the lens); (c) settling SQ3 by assertion rather than the measured run (the spec forbids forcing a binary the evidence doesn't support); (d) building the doc + wiring now, ahead of the measured lift (the build is cheap, so the go/no-go rests entirely on the measurement, not on saving implementation cost).

## Consequences

- **What ships now (this spike):** four eval fixtures (`refutation-spec-007..010`), the refutation log, and this ADR. **No** shippable miner, `--system` prompt, config schema, or grounding artifact — the design is settled, the occupant is not built (per the spike's anti-pattern rules).
- **The infosec lens is unchanged this ADR.** `refute-infosec.md` keeps its generic checklist and its "no learned per-repo threat prior" heading until a GO-narrow build lands the `--context` wiring.
- **Costed follow-ups (to file on the measured run's outcome, not pre-filed):**
  - The measured primed-vs-generic run on `refutation-spec-007..010` (`node eval/run-evals.mjs`, local-ollama or a plain-terminal frontier run) — the human-supervised gating step. Its catch-rate delta + near-miss false-positive count decide GO vs NULL.
  - **On GO-narrow:** a build ticket — author `docs/threat-model.md` (or the `.faffrc.yaml`-named committed path) + add it as one `--context` file to the infosec refuter invocation; update `refute-infosec.md`'s "no learned prior" heading. Small, dependency-free.
  - **On NULL:** record on the design-register-E thread (FAFF-13) that the infosec sub-question is closed — generic is sufficient at the measured fixture strength — with the corpus + numbers for a future re-open.
- **The forge/integrity residual is pinned, not solved.** This ADR *avoids* the forge surface by keeping the prior in version control; it does not build FAFF-325. Any future variant that persists a machine-acquired prior in `.faff/` inherits FAFF-325's integrity precondition (read-only mount / orchestrator-verified signatures) exactly as the run-ledger and any grounding evidence store do (ADR-0040).
- **Cross-project scope is out.** A per-repo threat prior is project-private and legitimate; a `~/.faff/` cross-project threat store is barred from carrying code/secrets/business-specifics by design-E's meta-only firewall and is not in scope here.
- **Revisit triggers:** the measured run shows a material lift on a stronger corpus than 007–010; or the base reviewer's ceiling drops (a weaker default model) such that a prior that added no lift at frontier strength starts to; or FAFF-325 ships and makes a machine-acquired persisted prior integrity-safe, reopening the deterministic/LLM-acquirer options refuted here.
- **FAFF-267 seam honoured.** Consuming the prior as `--context` leaves the L4 aggregation and the fixed `spec-review-verdict` contract untouched, as that ticket's spec reserved.
