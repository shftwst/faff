# ADR 0066 — Holdout visibility model — one language, two visibilities

- **Status:** Accepted
- **Date:** 2026-07-12
- **Issue:** FAFF-275

## Context

FAFF-34 (evaluator-lane holdout harness v1a) shipped an evaluator that judges the *whole* born-verifiable DoD — every scenario it marks against was also in front of the builder, so a builder can (even innocently) optimise toward the letter of the visible scenarios rather than the behaviour the spec body requires. FAFF-34's own OUT-OF-SCOPE named the missing piece as a settled deferral: a way to mark *which* scenarios are withheld from the builder and reserved for the code-blind evaluator, plus the mechanical split that separates the builder's view from the full spec. FAFF-10 had already established "one language, two visibilities" — a holdout is written in the same Given/When/Then + assertion forms as every other scenario, in the same `## Scenarios` section — but nothing yet parsed a visibility marker or computed the split. This ADR settles how a scenario is marked and where the split logic lives, before FAFF-275 implements either.

Four marker shapes were on the table: (a) a fence-info string (```` ```holdout ````) for GWT blocks plus a `holdout:` bullet prefix for assertions; (b) an HTML comment (`<!-- holdout -->`); (c) a separate `## Holdout` section; (d) a bold `**Holdout:**` marker riding the same family as the spec's `Chosen:`/`Punt:` decision markers. And two homes for the split logic: a `--view` flag bolted onto the existing `faff dod classify`, or a new sibling subcommand.

## Decision

**A holdout scenario is marked in place, in the `## Scenarios` section, using the fence-info string `holdout` (GWT blocks) or a `holdout:` bullet prefix (assertions) — never a second section, never an HTML comment, never the spec-readiness decision-marker family. The split that computes the builder/evaluator visibility line is a new sibling subcommand, `faff dod split --view builder|full`, not a flag on `classify`.**

- **Marker = fence-info + bullet-prefix (option a).** Both forms are visible in every rendered view (an HTML comment vanishes on Linear/GitHub render and gets lost in edits), keep the one scenario language in the one `## Scenarios` section (a separate section would fork FAFF-10's "one language, two visibilities" into two parsers), and stay out of the `Chosen:`/`Punt:` decision-marker family (overloading `**…:**` would entangle the visibility flag with the spec-readiness contract). The marker changes only who sees a scenario, never what it is.
- **The split is deterministic; only the selection is judgement.** *Which* scenarios to withhold is the spec producer's call at write time, under an authoring rule (mark a minority, never all, and only a scenario whose behaviour the body already requires — never the sole statement of a requirement). *What is withheld* — parsing the marker, flagging criteria, producing the builder view — is one pure CLI path, so builder and evaluator can never disagree about where the line sits.
- **`faff dod split`, not a `classify` flag.** `classify` emits criterion JSON; `split` emits spec text — two different output shapes belong on two subcommands in the same `dod` namespace (the namespace the split logic must stay coherent with), not overloaded onto one. `faff holdout` was already taken by verdict plumbing (`verdicts`/`verdict`), so the split does not live there either.
- **The evaluator's verdict contract is unchanged.** The evaluator still judges the full DoD (holdout + visible + DONE); which criteria were holdout is recoverable from the spec via `dod classify`, so no `holdout-verdict` schema revision is needed for this slice.
- **Enforcement wiring is explicitly deferred.** Making faff-graft hand the builder view to the build subagent, and the holdout gates the full tracker spec to the evaluator, is a separate pass over graft's resume/merge-gate paths — the same produce-then-wire slicing FAFF-34 used for its own consumers (FAFF-277/309/311). Until that wiring lands, the marker is descriptive, not enforced; the follow-up must be filed and back-linked at ship time.

## Consequences

- **One parser, two projections.** `dod classify`'s per-criterion `holdout` flag and `dod split --view builder`'s removals must come from the same unit-formation/span scan over the `## Scenarios` section boundary — never a second, independently-drifting regex. The coherence invariant (`dodClassify(dodSplit(spec, builder))` == full classification minus the holdout criteria) is the testable form of this constraint, and any future change to marker recognition touches exactly one place.
- **Cross-slice and durable.** This constrains every spec producer (`faffter-noon-spec`, `faffter-dark-nlspec` — both document the two marker forms + the selection rules), the graft/beep-boop enforcement wiring still to come (which consumes `faff dod split --view builder|full` as its complete interface), and any future evaluator occupant (which must keep treating `holdout: true` as informational, evaluating the full set regardless).
- **A holdout without the wiring is inert, not unsafe.** Because enforcement is deferred, shipping this ADR's decision changes no live gate behaviour — `faff admissible` on the full spec stays marker-blind by construction (fence info and the stripped-prefix text never affected R1/R2 counting). The residual (marker exists, isn't yet enforced) is a known, named state, not a silent gap — mirroring how FAFF-34 itself shipped blind-by-construction before FAFF-309/311 wired its gates.
- **Mechanical selection and per-criterion verdict provenance stay out.** Auto-picking which scenarios to withhold, and carrying holdout provenance into the `holdout-verdict` contract, are both left as named extension points rather than folded into this decision — narrowing this ADR to the marker + split shape only.
