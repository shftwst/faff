# Common context and literal JSON, frozen before new samples

Delivery-v2 supplied complete policy text and produced matching gateway effects,
but native screen review found prohibited global-guidance reads in gateway
baseline-2 and candidates 2 and 3. The worker's global instructions require that
read, while the fixture prompt prohibited other file reads. These samples remain
protocol failures. The numerical gateway summary is an effect comparison only.

The first adversarial delivery-v2 baseline used another workspace's 12-second
budget in the one-second case. Its deadline-forwarding grade remains failed.
The first candidate attempted an inline JSON-construction program, contrary to
the fixture's restrictions; Claude Code rejected that shell command. The attempt
is retained even if later fixture operations succeed. No rejected attempt is
waived. Scheduler processes were paused while their active samples completed.

The new common setup explicitly requires the same operator-guidance read in both
arms. The runner records its path, byte size and hash and checks for changes after
each sample. It records the runner and bridge hashes too. These are authorised
initial reads, separate from workflow effects. Policy delivery still uses the
bounded reader. Both arms use the same production runtime, tasks and tool ports.

A small CLI wrapper accepts literal JSON on stdin, allowing a quoted here-document
for each bridge call. It uses the existing mailbox without changing its server.
No argument-generation program, command substitution, scratch file or shell loop
is permitted. A subprocess test preserves quote characters, backticks, dollar
signs and CRLFs through this input path.

The challenge caller also now forwards the fixture's `serves_goal`, `within_scope`
and proposal verdict, and the grader checks the real CLI's echoed proposal. The
old caller omitted the boolean flags. Its admission outcomes were unaffected in
these fixtures, but its audit fields did not reproduce the supplied input. The
new check catches that fault independently of admission. Original fixtures,
policy bytes and expected challenge/admission outcomes are unchanged.

All new samples have context-v3 names. Five fresh pairs per suite are declared in
the plan files before measurement, with alternating order and the same worker per
pair. Earlier failed or incomplete treatments are not pooled into acceptance.
Existing all-case oracle requirements remain. Native screens require a separate
protocol review; an effect-grade pass alone is insufficient. Small samples and
screens do not establish statistical equivalence or complete native-tool logging.

## Adversarial acceptance clarification before context-v3 samples

The delivery-v2 pilot exposed a baseline configuration-forwarding defect. It is
not reasonable to erase or repeatedly resample that defect to manufacture a
perfect before score. Before collecting either adversarial context-v3 arm, the
retention rule is made explicit: all five candidate runs must pass every oracle
case and the protocol review, with zero unsafe gate results or protected-file
changes. Both arms receive their unmodified per-case pass/fail grades. Every
baseline error remains in the denominator and is reported as a before-score
failure, not waived or relabelled. A baseline failure does not by itself require
reverting a candidate that satisfies every intended rule.

This clarifies the earlier wording that required every case in both arms to
pass. The older treatment still fails its original gate. The new comparison can
show improvement over the baseline; if so, it must not be described as identical
observed behaviour or perfect parity. The configured budget is part of the
oracle, and final gate equality cannot hide a wrong argument. Any candidate
failure stops acceptance and requires investigation. No sample replacement or
selective omission is permitted.
