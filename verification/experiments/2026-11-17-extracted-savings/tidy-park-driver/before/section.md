## Autonomous Mode

When invoked autonomously (e.g. by `/faff-beep-boop` in its default full-pipeline mode), follow the shared autonomous contract (see the sibling `faff/references/autonomous.md`) and these specifics:

**Not-eligible issues are exempt from autonomous mutation (gateway → Automation eligibility).** Before any auto-action or prep-queue tagging below, skip issues that are **not automation-eligible** (no `faff-automate`): do **not** tag them `stale-spec`/`superseded-spec` (that feeds `/faff-beep-boop`'s prep queue), do **not** promote them to Todo, and do **not** auto-change eligibility labels (the label is tracker-owned; faff never writes it). Mechanical housekeeping that doesn't enter the autonomous pipeline still applies and must **preserve** eligibility — e.g. an auto-reparented not-eligible issue stays not-eligible.

**Autonomous tidy never silently restructures human-curated structure (gateway → Human curation is authoritative, assertion 3).** Its auto-actions are confined to its **own** housekeeping — stale faff-labels, dead references to cancelled/archived issues, and *obvious* orphans (a sub-issue whose parent is Done/Cancelled/Archived). It never autonomously re-prioritises, re-sequences, re-groups, or re-parents structure a human curated, and never cancels/deletes (the appetite hard floor). Anything beyond its own housekeeping is **surfaced for human decision** (propose-and-confirm), not auto-applied.

**Auto-actions (applied without prompting):**
- **Auto-strip dead references to cancelled/archived issues.** For every active issue, remove any link — blocker, blockedBy, parent, sub-issue, related, dependency — pointing at a cancelled or archived issue. This is mechanical and always safe; a cancelled issue cannot block or depend on anything. Post a single consolidated tracker comment per cascade (e.g. "After SHF-114 was cancelled, stripped blocker references from SHF-115/116/117/118/119"). Log every stripped link with the active issue id, the dead target id, and the link type.
- **Auto-canonicalise overlooked specs.** When the **Spec discovery** rule finds a spec in a non-canonical location (old comment thread, stale branch, unlinked document), copy it to the canonical location — tracker comment on the issue, or the configured spec-docs path (default `docs/specs/…`) if a feature branch exists for the issue. Log the move. If an issue is in Todo with no spec at any discovery location, demote to Backlog and log as "broken prep gate — no spec found"; do not invoke `/faff-prep` from tidy (that's `/faff-beep-boop`'s prep queue job in the default full pipeline).
- **Auto-archive dead weight:** merged or cancelled issues still sitting in the backlog. Move to archive/closed state as the tracker supports.
- **Auto-reparent obvious orphans:** a sub-issue whose parent is Done, Cancelled, or Archived. Reparent to the grandparent if one exists; otherwise remove the parent link.
- **Auto-remove stale `faff-parked` labels.** Remove via `faff label remove <issue> faff-parked` and its descriptor's write (gateway → **Control-label provisioning**) in two cases:
  1. **State moved on — via `faff park-verdict`, never a bare status check.** For **In Review / Done / Cancelled / Archived** the park is genuinely over → remove (unchanged). For an issue at **In Progress**, do **not** strip on the status alone: an `In Progress` + `faff-parked` issue is often a live faff *mid-build park* (faff claimed, built, and parked without reverting the claim), where the label is still load-bearing — it keeps the issue out of the eligible pool (`faff next --parked` ⇒ `needs-human`). Resolve three signals from the tracker and let the pure predicate decide, never re-derive it by hand:
     - `draft_pr` — does an **open DRAFT PR** link to the issue? (`present`/`absent`; the post-PR held-in-draft park's own preserved artifact).
     - `park_comment` — class of the most-recent faff park comment: `build` (a mid-build / blocked-on-external / resume-preserved park), `nonbuild` (a prep-time punt / low-confidence / gap / cycle park), or `none`.
     - `human_takeover` — is there a human status-move to In Progress, or a human (non-faff) comment, timestamped **after** the most-recent faff park comment? (`true`/`false`).

     Then `faff park-verdict --status in-progress --draft-pr <present|absent> --park-comment <build|nonbuild|none> --human-takeover <true|false>` and route on its verdict: `strip-ok` → remove (as below); `protect` → leave the label, log "valid mid-build park, label retained"; `surface` → leave the label, log "stale park label — needs human" for the next `/faff-wtf`. The predicate returns `strip-ok` unconditionally for In Review / Done / Cancelled / Archived (and `n/a` below In Progress), so those paths are byte-for-byte today's behaviour; only the In-Progress case is narrowed.

     **Capture (Tier-1, `FAFF_RUN_DIR`-guarded, per issue `--issue <issue>`).** Wrap this consult with the core-loop driver: run it as `eval "$(faff decision-capture decide --run <run> --issue <issue> --kernel park-verdict --export)" && faff park-verdict …` in one command, then once the label disposition is applied emit `faff decision-capture action --run <run> --issue <issue> --kernel park-verdict --action strip-ok|protect|surface` (the branch actually taken, never a re-emitted verdict). Best-effort, never gates; with no run dir (a standalone interactive tidy) nothing is minted.
  2. **Park reason no longer applies and can be cleanly verified.** Read the park reason from the tracker comment or `.faff/runs/<run-id>/ISSUE-XX/park.md`. Auto-remove when exactly one of these holds:
     - The reason matches a pattern **now forbidden** by the autonomous contract (any of: session compaction, context length, too-many-turns, topic-keyword match on a spec-closed decision, edits to files that only take effect after merge like `netlify.toml` / `.github/workflows/*.yml` / `Dockerfile` / `package.json` dep bumps / IaC / migration SQL files that weren't executed pre-merge). These parks were never valid under the current rules — clear without prompting.
     - The reason cited a specific blocker issue ID and that blocker is now Done, Merged, or Cancelled — live-fetch the blocker state from the tracker, don't rely on cached data.
     - The reason cited a spec punt (`Punt:`, `needs human`, `TBD`, "or X if Y") and the spec now closes that same topic with a `Chosen:` / `Decision:` marker per the gateway Spec-readiness contract.
  3. **Do not remove** when the park reason is subjective ("architectural change needed", "scope unclear"), vague, or missing. Those are judgement calls — leave the label on and log the finding as "stale park label — needs human" for the next `/faff-wtf`.

  For every auto-removal, log the issue id, original park reason, and the specific rule that invalidated it to `.faff/logs/YYYY-MM-DD/HHMMSS-tidy.md`. Post a tracker comment noting the removal and the reason.
- **Auto-clear a stale `faff-awaiting-review` hold.** Remove via `faff label remove <issue> faff-awaiting-review` when the issue has moved to In Review, Done, or Cancelled — the hold has resolved (a resumed review reached a terminal disposition) or the issue moved on by other means; no park-reason parsing needed (unlike `faff-parked`, a hold has no "reason no longer applies" sub-case — it is purely state-driven). Also clear the orphaned `.faff/resume/<issue>/` store if present. Log the removal.
- **Auto-clear a stale `faff-awaiting-spec-review` hold.** The prep-altitude twin of the bullet above. Remove via `faff label remove <issue> faff-awaiting-spec-review` when the issue has moved off Backlog (Todo, In Progress, In Review, Done, or Cancelled) — a resumed spec-review reached a terminal disposition (promoted, or the disposition's own needs-human escalation already removed the label) or the issue moved on by other means; purely state-driven, no park-reason parsing. Also clear the orphaned `.faff/resume/<issue>/spec-review-hold.json` (or the whole `.faff/resume/<issue>/` dir when nothing else occupies it) if present — this store is a sibling of, never a conflict with, the separate `.faff/spec-review/<issue>/` convergence-window scratch dir, so clearing it never touches that state. Log the removal.
- **Auto-clear a stale `faff-claimed` breadcrumb (backstop).** Remove via `faff label remove <issue> faff-claimed` from any issue **no longer at `In Progress`** (now In Review, Done, or Cancelled) — the claim has resolved, so its provenance breadcrumb is noise. Purely state-driven, exactly like `faff-awaiting-review` above; no reason-parsing. This is the backstop for the graft-side clear (graft removes `faff-claimed` on the claim's terminal disposition / retry-later release, but may miss it), so a resolved claim never keeps the label into a later reclaim pass. Log the removal.
- **Reclaim a stale, provably-faff `In Progress` claim.** For each active issue **at `In Progress`**, decide liveness by claim-age and reclaim only what faff can prove it set. A crashed run (this host or another) leaves an `In Progress` indistinguishable from a live build; this replaces today's manual recovery with a fenced auto-action. Per issue:
  1. **Read claim-age** — the timestamp of the **latest transition into the claim state**, resolved per connector: Linear, walk `get_issue.stateHistory` for the most-recent entry whose `state` is `In Progress` and take its `startedAt`; GitHub, the `created_at` of the latest timeline event representing the claim; Jira, the latest changelog transition into the claim state. **Anti-pattern:** never read Linear's issue-level `startedAt` — faff itself bounces `In Progress → Todo → In Progress` on the retry-later resume, and the top-level `startedAt` does not reset, so a just-re-claimed ticket would read as hours-stale and a live build would be yanked. If the connector **cannot** expose claim-age (explicit no-capability, never a guessed/defaulted age): surface-only, log "stale-claim check unavailable on <connector>", continue.
  2. **Verdict** — `faff claim-verdict --claimed-at <claimed_at> --now <now> --ttl-hours $(faff config get claim_ttl_hours)` (pure; the CLI decides `live`/`stale`, tidy owns the tracker read). `live` → do nothing.

     **Capture (Tier-1, `FAFF_RUN_DIR`-guarded, per issue `--issue <issue>`).** Wrap this verdict consult with the core-loop driver: run it as `eval "$(faff decision-capture decide --run <run> --issue <issue> --kernel claim-verdict --export)" && faff claim-verdict …` in one command, then once the disposition is known emit `faff decision-capture action --run <run> --issue <issue> --kernel claim-verdict --action live` (left the claim) or `--action stale` (reclaimed it, step 3). Best-effort, never gates; with no run dir (a standalone interactive tidy) nothing is minted.
  3. **`stale` + `faff-claimed` present** → **reclaim:** move `In Progress → Todo` (re-reading live status immediately before the write), `faff label remove <issue> faff-claimed`, **release the build-claim ref** — `faff build-claim release-if-stale --issue <issue>` (best-effort, exit 0 always): it lease-matched-deletes the `refs/faff/build-claims/<issue>` ref **only if** the holder is stale under the ref's own machine-aware, heartbeat-only `buildClaimStaleAware`, so a live *heartbeating* build (whose tracker claim-age can read hours-stale for a long build) keeps its ref and is never yanked; tidy grooms, it never acquires the claim to build. Then post **one** tracker comment ("reclaimed a `faff-claimed` stale claim (age > `claim_ttl_hours`); released the build-claim ref; moved to Todo for re-queue"), and log `{issue, age_secs, ttl_secs, ref_released, action: reclaimed}`. The queue reconsiders the issue on the next pass; the ref (not rebase-before-merge) is now the mutex, so a genuinely-live peer still refuses at Step-5 acquire, and reclaim is a `Todo` re-queue, never destructive. **git-only mode:** the tracker move / label ops no-op, but `faff build-claim release-if-stale` still runs — the ref on `origin` is git-only mode's only cross-host claim.
  4. **`stale` + `faff-claimed` absent** (human-set or unprovable) → **surface only:** log "stale claim, no `faff-claimed`, needs human", leave status untouched — auto-reverting a human's `In Progress` would override human curation (a hard rule).

  This is the **second sanctioned `In Progress → Todo` backward move** under the status-monotonicity guard (gateway → **Issue claim & status monotonicity**), tightly fenced to `In Progress` + a `stale` verdict + `faff-claimed` present, so it never touches an issue at `In Review`/`Done`. **git-only mode:** no reclaim path (no shared tracker; same-host is covered by the local heartbeat). Not to be confused with the governance **anchor** mechanism — that is a merge-time git-evidence check, a different question, time, store, and consumer.
