# Prioritised skill-to-CLI extraction plan

Audited all 32 installed skill prompts and nine shared references. The source inventory ties 55 candidate operations to exact ranges in the repository. The ranking groups them into 34 work items, including two policy holds and one implementation already in review. The cited ranges total 599,084 distinct bytes. They include instructions that must stay with the caller. [Pinned source tree](https://github.com/shftwst/faff/tree/a0e84c3cb28213367523ad825cabb6919c572185/plugin/skills) · [Source inventory, reuse and proposed tests](sources.json)

## Where to start

Start with **build dispatch**. The sequential and parallel executors both choose a model, log the configured effort and assemble issue context for a build worker. A shared preparer can be checked by comparing the actual argv and payload each executor sends today. The next independent change normalizes supplied issue snapshots. Queue partitioning can then consume those facts.

Put **L4 spec-review** in the first delivery batch. It is the largest individual opportunity found, with 29,055 bytes of round mechanics in scope. Existing helpers already build requests, fan out, aggregate, capture transcripts and pin backend identity. Begin with request preparation. Take result recording as a separate PR after testing retries, unavailable lenses and captured backend identity. Editorial review of the spec remains in the reviewer.

These are planning ranges for net prompt text removed after replacement instructions. Each kB means 1,000 bytes. Estimates use about four bytes per token. Actual landed figures use the existing per-file estimate of one token per four UTF-16 code units, rounded up. The 31-item sum is a scenario before rebasing overlapping draft work and checking production fidelity. The two holds, the current graft PR and possible read-on-demand savings contribute zero to it. The first six are the delivery forecast. The longer range is sensitive to shared helpers, policy decisions and the instructions that trials show must remain.

The campaign started at 1,372,081 bytes. A 25% reduction takes 343,021 bytes. If all measured open cuts land, the total saved reaches 184,777 bytes. That leaves **158,244 more bytes** to reach 25%, near the upper end of the 31-item estimate. [Measured savings ledger](../2026-11-17-extracted-savings/README.md)

## Evidence behind the order

- **Frequency.** The checked-in anchors contain 490 event files from 338 distinct runs dated July 22 to November 16, 2026. Identical archived records were counted once per run and sequence. Two sequence positions had distinct historical records, which were retained. There were 209 build starts, 334 admissions, 165 issue outcomes, 87 prep starts, 135 prep completions, 79 parks and 1,011 ledger writes. Many anchors were taken mid-run. Three recorded tidy completions and seven run ends illustrate the incomplete sampling. These are activity counts, with no universal skill-load denominator. [Archived events](https://github.com/shftwst/faff/tree/a0e84c3cb28213367523ad825cabb6919c572185/.faff/anchors)
- **Determinism.** High means the proposed code can reproduce a decision, identity, ordering, effect ownership or durable state from explicit facts. Medium means it can reproduce the preparation or rendering around a decision that still needs judgement.
- **Ordering.** Give preference to repeatedly executed decisions and to reusable work other rows need. Use estimated net bytes to distinguish comparable candidates. Move an item down when it has limited reach, an unresolved policy, uncertain output costs or a side effect that is difficult to exercise safely. Frequency in each row describes the actual calling rule. The number of calls in a loop and the number of times a skill is loaded can differ.
- **Runtime cost.** A CLI can add local code, tool calls and JSON output while removing prompt bytes. Measure the new invocation and output on the affected path. A short prompt that prints the deleted prose back to the agent puts those tokens back into the session. Existing tracker MCPs retain discovery, reads, writes and acknowledgement. A local command may accept their normalized results.

## Delivery and acceptance

1. Use the first ready row in ranked order. The first dispatch PR takes the two executor prompts and one shared argument preparation function. Capture their existing outputs for single and mixed tiers, inherited settings, an unusable config and a verified corrective run. Compare against the candidate through both executor entry points. Capture the exact model field, including its omission on inherit, and verify that effort appears only in the log. Preserve sequential foreground blocking and parallel background dispatch with await-all. On correction, the sequential caller explicitly supplies its custody manifest. Keep the existing corrective check in each caller until those distinct inputs and dispositions have independent test cases. Count generated worker-instruction tokens as runtime cost. Keep live dispatch in the original harness. The four existing dispatch and adaptor test files passed all 71 baseline cases on 7d593627. These cover the existing resolver and caller contracts. The extraction still needs paired handoff evidence for both executors.
2. Ship a small implementation PR with TypeScript and committed emit where applicable, a direct executable test for the new surface, and the skill and size ratchets. Keep raw evidence and the model driver on the evidence branch. Test malformed input and a real downstream consumer. Any new writer also needs retry, partial-failure and concurrent-write coverage.
3. Compare the old and new callers at the exact handoff. Use a bounded Claude Code pair when skill routing or interpretation changes. Use direct equivalence and CLI tests for pure computation. Report the observed cases, failures and coverage limits alongside bytes and tokens.
4. Reconcile merge status, competing drafts and the measured result after each PR. Start the next ready row as soon as its inputs are available. A held item keeps its reason and zero booked bytes. It cannot block unrelated work.
5. At the end of the first three items, compare actual yield, emitted tokens and failures against the 8.3–15.3 kB forecast. Reorder the remaining queue if delivery evidence changes the trade-off.
