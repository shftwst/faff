# Hard briefs — comparison rationale

Faff-side companion to the harder briefs added beyond the original seven — first wave `quorum`, `tandem`, `relay`, `bookend`, `sealed`; second wave `keel`; third wave `stall`, `plinth`, `recall`. Like the one-shot control runbook, this document is **never** included in what a run sees — a control gets its brief plus the fixed wrapper, nothing else (FAFF-547). It records why each brief was added, what it tests on each side of the comparison, and the expected result going in, so outcomes can be scored against stated predictions rather than narrated after the fact.

These five sit above the existing seven in difficulty. The existing set tops out at grocer (two services, broker, outbox, kill-recovery); each new brief either deepens one axis past that ceiling or opens an axis the set doesn't cover. Ordering below is by evidence value: how much a result — either result — would tell us about the process-versus-one-shot question.

Predictions use "one-shot control" and "faff run" throughout. A prediction is a falsifiable statement, not an endorsement; several of these are expected to be close, and one is expected to favour the control. That spread is deliberate — a testbed where every brief is predicted to favour the faff run isn't a testbed.

## 1. quorum — replicated key-value store

**Why it's the most valuable test.** Correctness is invisible: a cluster that silently loses writes demos identically to one that doesn't, and no amount of reading the code settles it. The entire comparison collapses into one question — does a working fault injector and history checker exist, and does the system survive it? That makes quorum the purest measurement of the thing faff claims to sell (verification discipline as process output) against the thing a one-shot sells (getting hard code right in one pass). Either outcome is decisive evidence; no other brief has that property.

**What it tests in the one-shot control.** Consensus is well-represented in training data, so a fluent, plausible implementation is likely. The pressure point is everything around it: real container kills, network-level partitions in a compose topology, client-side history recording, and a checker that provably rejects a bad history. Each of those is a place where a single session can produce something that runs and passes — vacuously. The checker self-test criterion exists precisely so a hollow harness scores as a fail, not a pass.

**What it tests in the faff run.** Consensus resists decomposition — the invariants cut across election, replication, and recovery, so they can't be sliced into independent tickets and verified locally. If faff's process forces premature decomposition, quorum is where that failure shows up as a cluster whose parts each pass and whose whole diverges. It also stresses whether cheaper build models can implement genuinely hard algorithmic code when the spec and tests are strong.

**Expected result.** The faff run is expected to produce the more defensible artifact — not because the control writes worse consensus code, but because the criteria are decided by the harness, and building a real nemesis-plus-checker is a sustained, multi-stage discipline that single sessions historically shortcut. The stated counter-possibility: if the one-shot control ships a working checker and passes it, that is strong evidence that process adds little at even this difficulty, and it should be reported exactly that way.

## 2. tandem — collaborative text editor

**Why it's second.** Convergence is a sharp, binary property that only surfaces under interleavings no human demo produces — the same "looks right, isn't" cliff as quorum, but on a different axis: client-side distributed state, browser integration, and offline merge rather than server consensus. Together with quorum it brackets the distributed-correctness space; a process that wins both is winning on the class, not on a lucky brief.

**What it tests in the one-shot control.** CRDT/OT libraries and blog-post implementations are abundant, so the control may assemble a convergent editor quickly. The differentiators are adversarial delivery (reordering and duplication injected in the delivery path, not pre-sorted away), the offline-merge path, restart durability, and a harness whose divergence assertion demonstrably fires. Intent preservation — both concurrent inserts surviving — is where naive last-write-wins shortcuts get caught.

**What it tests in the faff run.** Emergent properties are hard to specify: "converges under any interleaving" doesn't reduce to per-ticket acceptance checks the way CRUD does. Tandem tests whether faff's spec and review layers can hold a global property through decomposed implementation, and whether the harness ticket gets treated as first-class work rather than a trailing checkbox.

**Expected result.** Faff run favoured, for the same structural reason as quorum: the deciding artifact is the adversarial harness, not the editor. Expected to be closer than quorum because mature libraries can carry more of the correctness burden for the control — and if the control leans on a library well and passes, that's a legitimate, reportable path to parity, not a disqualification.

## 3. relay — durable workflow engine

**Why it's third.** Relay is the closest of any brief to the systems real teams actually pay for, and it is broad rather than deep: durability, exactly-once effect, time fidelity, fan-out/fan-in, recovery, and a scriptable-target harness all have to coexist in one codebase. Breadth is the axis the existing set under-tests past grocer, and it's the axis where session shape should matter most — one long context versus many scoped ones. Less decisive per-criterion than quorum or tandem, but the richest source of the by-phase economics evidence the control runbook cares about.

**What it tests in the one-shot control.** Endurance. No single criterion here is exotic; the test is whether the last subsystem built (usually cron fidelity or crash-resume) gets the same rigor as the first, deep into a long session. The kill-mid-run-at-any-instant criterion and idempotency-key stability across restart are the classic places where late-session code quietly regresses earlier guarantees.

**What it tests in the faff run.** Long dependency chains. Recovery semantics depend on the persistence model, which depends on the execution model — a poor early decomposition surfaces as rework across many tickets. Relay measures whether faff's planning layer sequences a deeply-coupled build well, and whether per-ticket verification composes into the whole-system guarantee the harness checks.

**Expected result.** Faff run favoured on final criteria pass rate; the one-shot control plausibly reaches an impressive-looking demo state on fewer tokens. The interesting measurement is exactly that gap — demo state versus harness-passing state — quantified by the economics wrapper. If the control converts demo state to harness-passing state without a flail phase, the breadth argument for process weakens measurably.

## 4. bookend — timezone-correct booking

**Why it's fourth — the fairness control.** Calendar and timezone logic is a well-trodden domain with strong library support, so this is a brief the one-shot control should be genuinely good at. A credible testbed needs briefs where the prediction favours the control or is uncertain; bookend is that brief by design. It also opens the deterministic-corpus axis (like gridlet) at higher difficulty: DST transitions, non-whole-hour offsets, nonexistent and ambiguous wall-clock times, plus one sharp concurrency race and an independent-parser round-trip.

**What it tests in the one-shot control.** Whether domain fluency extends to the edges: Lord Howe-class offsets, fall-back ambiguity, and the discipline of documenting a resolution rule and pinning it in a corpus rather than just behaving some way. The evaluator's extend-the-corpus check is the trap for memorised-looking correctness: an implementation that computes rather than pattern-matches passes zones its authors never wrote cases for.

**What it tests in the faff run.** Whether process pays when the domain is easy for models. If the faff run's overhead (spec, tickets, reviews) buys nothing here — same pass rate, more tokens — that bounds where the process premium applies, which is information the gallery needs to be honest about.

**Expected result.** Genuinely uncertain, leaning to the one-shot control on the corpus criteria; the faff run's edge, if it materialises, should come from the documented-rule discipline, the race check, and the round-trip — the parts that are process-shaped rather than knowledge-shaped. A control win here, published, is what makes the faff wins elsewhere credible.

## 5. sealed — zero-knowledge encrypted drops

**Why it's fifth.** It shares lifecycle machinery with stash, so its marginal evidence is the smallest — but the axis it opens is unique: the acceptance criteria are *negative* claims (nothing legible reaches the server, key material never transmitted), which can only be established by instrumenting traffic, database, and storage. It tests whether a build process can prove an absence, and it's the best cost-comparison brief: architecture-shaped, describable in one pass, with correctness carried substantially by standard crypto libraries.

**What it tests in the one-shot control.** Whether the architecture holds everywhere, not just on the happy path — one error log with a file name, one analytics beacon, one fragment leak into a request voids the claim. And whether the harness genuinely intercepts all traffic and inspects storage directly, versus asserting the app's own account of itself.

**What it tests in the faff run.** Whether process overhead is dead weight at this difficulty. Sealed is the brief most likely to land at criteria parity, which makes the comparison about cost, session economics, and the governed-codebase argument rather than pass rate — the second headline claim in the faff-lab PRD's goals.

**Expected result.** Near-parity on acceptance criteria is the honest expectation, with the control competitive or better on total tokens. The comparison's value is in what parity costs each side and what each leaves behind (test surface, docs, traceability). Both sides' crypto choices need the same human review regardless of who built it — the harness proves the architecture, not the cryptography, and the gallery should say so.

## Second wave — depth: keel

**keel — transactional storage engine.** Ranks with quorum at the top of the combined set, on a different depth axis: crash consistency rather than distribution. The engine forbids leaning on an existing store, so correctness lives between a write and an fsync — territory where nothing short of killing the process at every I/O boundary settles anything, which is exactly what the harness must do.

*What it tests in the one-shot control:* WAL designs are well-documented, so a plausible engine is likely; the exhaustive crash-point enumeration, the torn-write shim, and fresh-process recovery checks are the sustained-discipline artifacts a single session historically shortcuts. *What it tests in the faff run:* like quorum, the invariants cut across the whole engine and resist per-ticket verification — a decomposition-shaped process has to hold a global property through sliced work, and cheap build models have to land genuinely subtle systems code. *Expected result:* faff run favoured, decided by whether a real injection shim exists rather than by engine code quality; the stated counter-case — a control that ships exhaustive injection and passes it — would be the strongest single data point yet that process adds little, and gets reported as such.

## Third wave — decomposition briefs: stall, plinth, recall

Everything above tests verification on a monolithic goal: the deliverable is one thing, done or not. These three test the layer in front of that — planning. Each is an application-scale product whose value genuinely arrives in stages, and each makes incremental delivery a requirement of the brief itself: at least three releases, each deployed when made, each usable, recorded in a release log whose per-release passing-criteria sets must grow monotonically, all verified from repository and deploy history rather than narrative. That requirement is product-legitimate — real teams ship this way — but structurally it measures roadmap quality: how well the work was sliced, whether early slices were coherent products, and whether late work regressed early criteria. This is the layer faff explicitly claims (a decomposition pipeline from application-scale idea to dependency-linked slices), so these briefs test faff's actual pitch rather than only its verification discipline — and symmetrically, they test whether a single long session can sequence releases rather than front-load scaffolding toward one final assembly.

**1. stall — community marketplace.** The widest surface and the most natural increment ladder in the whole set (listings → search → messaging → offers → escrow → reviews), with a hard core — the escrowed credits ledger — that arrives mid-ladder, not at the start. *One-shot pressure:* sustaining release discipline is exactly what a single session has no structural reason to do; the monotone-criteria check catches the common failure of late escrow work breaking early listing behavior. *Faff pressure:* slicing is faff's product, but the ledger cuts across slices — a roadmap that treats escrow as one late epic risks the same big-bang it's meant to prevent. *Expected result:* faff run favoured on the release ladder and the ledger criteria; the control plausibly reaches wider demo-level breadth per token. The ladder evidence is the point: this is the brief most directly probative of the decomposition claim, which is why it leads the wave.

**2. plinth — headless CMS.** Production-shaped platform work: immutable versioning, cache staleness bounds, signed webhooks with honest retries — each a consumer-side promise verified from the consumer's seat, and each a clean release-ladder rung. *One-shot pressure:* breadth-with-guarantees deep into a session (webhook resumption across restart is the late-session regression magnet). *Faff pressure:* whether per-slice verification composes — the staleness bound spans editor, store, cache, and delivery, so no single ticket owns it. *Expected result:* faff run favoured on the guarantee criteria; closer on the ladder than stall because plinth's stages are more conventional and the control may sequence them adequately by convention alone.

**3. recall — spaced-repetition platform.** The fairness-leaning member of the wave: the engine (an established-family scheduler pinned by corpus) is knowledge-shaped, and the control should be genuinely strong on it. What remains process-shaped: replay determinism, statistics-vs-replay agreement, day-boundary correctness across DST and timezone changes, and the release ladder. *Expected result:* genuinely uncertain — control competitive or ahead on the corpus, faff's edge if any on the time-domain cases and ladder. Like bookend, a published control win here is part of what makes the rest of the gallery credible.

## Slotting into the control run order

The control runbook's ordering logic (calibrate cheap, then evidence density, home turf last) extends to the combined set: `bookend` slots early as the second calibration brief and the fairness control; `quorum`, `keel`, and `tandem` follow once burn rate is known — the highest-value depth captures; `stall` is the priority decomposition capture (one decomposition brief in the gallery outranks a third depth brief — it evidences a different claim), with `plinth` and `recall` behind it; `relay` is the longest, most flail-prone session and goes where grocer goes; `sealed` remains the first sacrifice to budget, since stash covers adjacent evidence. All inherit the runbook's protocol unchanged: one prompt, fixed wrapper, high effort held constant, full capture. Note the decomposition briefs are the most expensive controls in the set — three deploy cycles minimum inside one session — so they should be captured only after the depth spine exists.
