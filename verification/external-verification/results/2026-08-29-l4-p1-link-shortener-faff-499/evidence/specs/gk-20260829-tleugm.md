Epic gk-20260829-tleugm — the error-shape increment on the shipped link-shortener MVP
(gk-20260829-zr4n8l) with TTL expiry (gk-20260829-u9qzgx), both now on `main`. Delivers the roadmap's
structured-error criterion: the client-facing error responses of `POST /shorten` and `GET /{code}`
(bad request body, not-found, expired) return a structured JSON body rather than the bare
`text/plain` status text `http.Error` currently writes. Blocked-by gk-20260829-zr4n8l (shipped);
carries epic B's TTL changes. Inherits that architecture (Go 1.22, `net/http` ServeMux, pgx v5,
Postgres 16, docker-compose); no new architecture is proposed.

## What to build (changes to the shipped code)

Only `internal/httpapi/handlers.go` (plus its test coverage) changes. No store, migration, config, or
compose change.

- Add one unexported error-body type and one writer helper in `internal/httpapi/handlers.go`:
  - `type errorResponse struct { Error string `json:"error"`; Message string `json:"message"` }`
  - `func writeJSONError(w http.ResponseWriter, status int, code, message string)` — sets
    `Content-Type: application/json`, calls `w.WriteHeader(status)`, then JSON-encodes
    `errorResponse{code, message}`. `Error` is a stable machine-readable slug (snake_case); `Message`
    is a short human string. The helper is the single place error bodies are formed, so every error
    path is byte-consistent. The status header is written **before** the body is encoded, so a
    mid-write failure can never revert the response to `200` (the status line is already on the wire) —
    the path fails closed on the already-sent error status. Encoding an `errorResponse` (two plain Go
    strings, all slug/message values being ASCII literals in the handler) cannot fail in practice; the
    encoder's error return is ignored exactly as the shipped 201-encode path already ignores it.
    `writeJSONError` performs exactly two writes to `w` — `WriteHeader(status)` then one
    `json.Encoder.Encode` — and nothing else (no `fmt.Fprintf`, no prefix/suffix `w.Write`), so the
    control-byte-escaping guarantee below cannot be voided by an out-of-band write.
- Replace **every** `http.Error(...)` and `http.NotFound(...)` call in the two client-facing handlers
  (`shorten`, `resolve`) with a `writeJSONError` call carrying the same HTTP status it uses today and
  the slug from the table below. The status codes are unchanged — only the body shape and
  `Content-Type` change.
- The error slug/status table (the complete, exhaustive set of error responses these two handlers
  emit) is:

  | Handler   | Condition                                   | Status | `error` slug      | Code-blind inducible? |
  |-----------|---------------------------------------------|--------|-------------------|-----------------------|
  | `shorten` | request body over `maxBodyBytes`            | 413    | `body_too_large`  | yes (send >8 KiB)     |
  | `shorten` | body unreadable (non-`MaxBytesError` read)  | 400    | `invalid_request` | no (internal read error) |
  | `shorten` | body is not valid JSON / wrong `ttl_seconds` JSON type | 400 | `invalid_json` | yes           |
  | `shorten` | `url` fails validation (empty/scheme/host/control byte) | 400 | `invalid_url`  | yes          |
  | `shorten` | `ttl_seconds` above `maxTTLSeconds`         | 400    | `ttl_too_large`   | yes                   |
  | `shorten` | store write error                           | 500    | `internal`        | no (needs a datastore fault) |
  | `resolve` | code fails `codeShape`                       | 404    | `not_found`       | yes                   |
  | `resolve` | code unknown **or expired** (store `found=false`) | 404 | `not_found`   | yes                   |
  | `resolve` | stored value has a control byte (defence-in-depth) | 500 | `internal`   | no (unreachable on the normal path) |
  | `resolve` | store read error                            | 500    | `internal`        | no (needs a datastore fault) |

  The final column marks which rows a black-box HTTP client can force against a healthy running
  stack. The four `not code-blind inducible` rows (a mid-body read error, a store fault, and the
  defence-in-depth control-byte re-check) cannot be triggered by a well-formed request to a healthy
  service, so they are covered by build-time reasoning and the in-repo unit/handler tests rather than
  the code-blind holdout scenarios. In particular, the `invalid_request` mapping SHOULD be covered by
  a handler-level unit test that injects a failing `io.Reader` as the request body and asserts the
  400 + `{"error":"invalid_request"}` shape, since it has no code-blind path. Every row still routes
  through the one `writeJSONError` helper, so the JSON shape is identical across all of them by
  construction.

- The success paths are unchanged: `POST /shorten` still returns 201 with `{"code": "<7-char>"}` and
  `application/json`; a resolved `GET /{code}` still returns 302 with a byte-for-byte `Location` header
  and no body.
- Tests: extend `test/integration_test.go` with the error-shape scenarios below (Content-Type +
  `error` slug + status for each named error), and keep every epic-A / epic-B regression scenario
  green.

## How to build it

- **Chosen:** the error body shape is a flat object `{"error": "<slug>", "message": "<text>"}`.
  `error` is the stable, machine-assertable field a client (and the code-blind holdout) keys on.
  `message` is a **fixed** short human string per slug (a literal chosen at the call site, one constant
  per error condition) — its exact wording is not asserted, but it MUST be a non-empty string and MUST
  contain no control bytes. It is never derived from caller input. A flat two-field object is the least
  structure that satisfies "structured JSON rather than bare status text" and is trivially testable; a
  nested `{"error":{"code":...,"message":...}}` adds a level with no consumer that needs it.
- **Chosen:** `writeJSONError` writes its body via `json.NewEncoder(w).Encode(...)`, which escapes
  every control byte (including CR and LF) in any string it serialises. Combined with the rule that
  both `error` and `message` are static literals never interpolated from request data, this makes HTTP
  response splitting / header injection through the error body impossible by construction — there is no
  path for a raw CR/LF or caller-controlled byte to reach the wire. Introducing a dynamic (input-echoing)
  error `message` is explicitly out of scope for this epic; a future epic that wants one MUST add a
  control-byte guard at that point.
- **Chosen:** the HTTP status codes stay exactly as the shipped handlers set them (400/404/413/500).
  This epic changes only the response *body and Content-Type*, never the status semantics, so every
  existing status-only regression test stays green.
- **Chosen:** expired and unknown codes both map to the same `404` + `{"error":"not_found"}` body.
  The resolve path already collapses expired and unknown into `found=false` (epic B), and the roadmap
  groups "not-found, expired" as one shape. Emitting an identical body for both avoids leaking whether
  a code ever existed (an enumeration signal) and matches the shipped 404 semantics.
- **Chosen:** the `500` internal-error paths use a generic `{"error":"internal"}` body with a
  fixed `message` and never echo the underlying error, the submitted URL, or the stored value — no
  internal detail leaks to an unauthenticated caller. This preserves the shipped handlers' existing
  no-leak behaviour (`http.Error(w, "internal error", 500)`), now as JSON. Because a `500` cannot be
  induced code-blind against a healthy stack (it needs a datastore fault), this no-leak property is
  **not** a code-blind holdout assertion — it is enforced by the fixed `writeJSONError` call sites
  (the message strings are literals in the handler, never interpolated) and, where a fault can be
  simulated, by in-repo handler unit tests. The holdout verifies the shapes a black-box client can
  actually reach.
- **Chosen:** `GET /healthz` is **out of scope** and unchanged — it stays a plain-text liveness probe
  (`200 "OK"` / `503 "unhealthy"`). It is not one of the roadmap's named error surfaces (bad request
  body, not-found, expired), it is consumed by the compose healthcheck as text, and converting it
  would be unrequested scope. Its `503` body is therefore intentionally left as `text/plain`.
- **Chosen:** framework-emitted responses that the two handlers do not author — a `405` from the
  ServeMux for a wrong method, or a body that never reaches a handler — are **out of scope**. This
  epic converts only the error responses the `shorten` and `resolve` handlers emit themselves; it does
  not install a custom mux-level error writer. This bounds the change to the shipped handler bodies.
- **Chosen (declined review-expansions — recorded so they are not silently dropped):** the following
  are deliberately **out of scope** for this error-shape increment, each for a concrete reason, not
  omission:
  - *A global panic-recovery middleware that reformats panics as JSON.* This change adds no new panic
    surface — encoding a struct of two Go strings cannot panic — so there is no regression to guard.
    Cross-cutting panic handling is a separate concern with its own review, not part of converting
    existing `http.Error` calls to JSON.
  - *Rate limiting / output-throttling of the error path.* The input is already bounded by
    `maxBodyBytes` (epic A), and JSON-encoding a ~60-byte body is not a materially larger DoS surface
    than writing a plain-text string. Rate limiting is a separate, cross-endpoint concern (its own
    epic), not introduced or regressed here.
  - *An `X-Content-Type-Options: nosniff` header.* The error bodies are pure JSON with no
    caller-controlled content (the `message` is a fixed literal), so there is no sniff-to-XSS path to
    close. Adding security headers is a separate hardening pass, not this increment.
- **Assumes:** epics A and B are on `main` (shipped) — the `links` table, the store `Create`/`Resolve`
  signatures, the validation/handler structure, `maxBodyBytes`, `maxTTLSeconds`, `codeShape`, and the
  docker-compose stack all exist and are unchanged except for `internal/httpapi/handlers.go` and its
  tests.

## Scenarios

Born-verifiable Given/When/Then scenarios, each HTTP-exercisable code-blind against the running stack.
Every error scenario asserts three observables: the status, `Content-Type: application/json`, and the
JSON `error` slug.

```
Given a POST /shorten request whose body is not valid JSON (e.g. the bytes "this is not json")
When the client sends it
Then the response status is 400, the Content-Type is application/json, and the JSON body field error equals "invalid_json"
```

```
Given a POST /shorten request with a well-formed JSON body whose url is not an absolute http(s) URL (e.g. {"url":"/foo/bar"})
When the client sends it
Then the response status is 400, the Content-Type is application/json, and the JSON body field error equals "invalid_url"
```

```
Given a POST /shorten request with a valid url and ttl_seconds greater than ten years (e.g. 999999999999)
When the client sends it
Then the response status is 400, the Content-Type is application/json, and the JSON body field error equals "ttl_too_large"
```

```
Given a POST /shorten request with a well-formed JSON body whose ttl_seconds is the wrong JSON type (e.g. {"url":"https://example.com/x","ttl_seconds":"100"})
When the client sends it
Then the response status is 400, the Content-Type is application/json, and the JSON body field error equals "invalid_json"
```

```
Given a POST /shorten request whose body exceeds the 8 KiB cap (e.g. a 64 KiB body)
When the client sends it
Then the response status is 413, the Content-Type is application/json, and the JSON body field error equals "body_too_large"
```

```
Given a well-shaped but never-issued code (e.g. GET /ZZZ0000)
When the client sends GET for it without following redirects
Then the response status is 404, the Content-Type is application/json, and the JSON body field error equals "not_found"
```

```
Given a single-segment path that fails the 7-char base62 shape (e.g. GET /abc!123)
When the client sends GET for it without following redirects
Then the response status is 404, the Content-Type is application/json, and the JSON body field error equals "not_found"
```

```
Given a code created via POST /shorten with ttl_seconds 1
When the client sends GET /{code} at least 3 seconds later without following redirects
Then the response status is 404, the Content-Type is application/json, and the JSON body field error equals "not_found"
```

```
Given a valid absolute http(s) URL
When the client sends POST /shorten
Then the response status is 201, the Content-Type is application/json, and the JSON body field code matches ^[0-9A-Za-z]{7}$
```

```
Given a code created via POST /shorten with a valid URL
When the client sends GET /{code} without following redirects
Then the response status is 302, the Location header equals the submitted URL byte-for-byte, and the response body is zero-length
```

```
Given the running stack
When the client sends GET /healthz
Then the response status is 200 and the Content-Type is not application/json (the health probe stays a plain-text probe, unchanged)
```

## DONE

Externally-observable completion assertions, each checkable **code-blind** against the running stack
via HTTP (this is what the holdout evaluator verifies). The internal error rows that a black-box client
cannot reach are covered by the in-repo tests in the next section, not here.

- [ ] Both distinct `invalid_json` triggers MUST be verified independently: (a) a non-JSON body and (b) a well-formed body whose `ttl_seconds` is the wrong JSON type (e.g. a string) MUST **each** return 400 with `Content-Type: application/json` and `error` equal to `invalid_json`. A build passing only one of the two does not satisfy this item.
- [ ] `POST /shorten` with a non-absolute-http(s) `url` MUST return 400 with `Content-Type: application/json` and `error` equal to `invalid_url`.
- [ ] `POST /shorten` with `ttl_seconds` above ten years MUST return 400 with `Content-Type: application/json` and `error` equal to `ttl_too_large`.
- [ ] `POST /shorten` with a body over 8 KiB MUST return 413 with `Content-Type: application/json` and `error` equal to `body_too_large`.
- [ ] `GET /{code}` for a well-shaped but unknown code, for a shape-failing path segment, and for an expired code MUST each return 404 with `Content-Type: application/json` and `error` equal to `not_found`.
- [ ] No `2xx`/`3xx` success path is altered: a valid `POST /shorten` MUST still return 201 + `application/json` + a `^[0-9A-Za-z]{7}$` `code`, and a resolved `GET /{code}` MUST still return 302 with a byte-equal `Location`, a zero-length response body, and NO `Content-Type: application/json` header (the resolve handler writes no body and the JSON error helper MUST NOT touch the redirect path).
- [ ] `GET /healthz` is unchanged: it MUST still return 200 with a `text/plain` (non-`application/json`) body — the JSON error helper MUST NOT be applied to the health probe.

## Required in-repo tests (verified by `faff gates run` + code review — NOT the holdout)

These cover the `not code-blind inducible` rows of the error table using **only** faults injectable
without any codebase structural change (no `Store` interface, no dependency-injection refactor — the
`API` struct and its concrete `*store.Store` are unchanged). They are mandatory build deliverables (the
gate suite must include and pass them), but they are not holdout DONE items because a black-box HTTP
client cannot reach them. Each has a born-verifiable oracle over the handler, driven directly:

- A `shorten` handler whose request body is an `io.Reader` that returns a non-`MaxBytesError` error on
  `Read` (built with `httptest.NewRequest(..., failingReader)` — no interface refactor needed) MUST
  produce 400, `Content-Type: application/json`, and a body that decodes to
  `{"error":"invalid_request", "message": <non-empty>}`.
- `writeJSONError` called directly for every `(status, slug, message)` in the error table (writing to
  an `httptest.ResponseRecorder`) MUST always produce `Content-Type: application/json` and a body that
  decodes to an object with a non-empty control-byte-free `error` string and a non-empty
  control-byte-free `message` string, so no row can drift from the shape.

The two `500` store-fault rows and the `resolve` control-byte `500` row are deliberately **not**
unit-tested: inducing a store fault would need a `Store` interface / DI refactor beyond this single-file
increment. Their no-leak guarantee is **by construction and verified by code review** — the two `500`
call sites pass the fixed literals `"internal"` and a constant message and NEVER the underlying error,
the submitted URL, or the stored value (directly readable in the diff). The by-construction guarantee is
stated as a `**Chosen:**` marker above.
