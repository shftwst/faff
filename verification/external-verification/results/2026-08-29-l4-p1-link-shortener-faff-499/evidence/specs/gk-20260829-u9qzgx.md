Epic gk-20260829-u9qzgx — the TTL increment on the shipped link-shortener MVP
(gk-20260829-zr4n8l, now on `main`). Delivers the PRD's optional-TTL acceptance criterion:
`POST /shorten` accepts an optional `ttl_seconds`; an expired code stops resolving (404). Blocked-by
gk-20260829-zr4n8l (shipped). Inherits that epic's architecture (Go 1.22, pgx v5, Postgres 16,
docker-compose); no new architecture is proposed.

## What to build (changes to the shipped code)

- `internal/store/store.go` — extend the datastore layer to carry an optional TTL, computing the
  expiry **in SQL against the database clock** so write and read use the same clock (no app/db skew):
  - `Create(ctx, url string, ttlSeconds *int) (string, error)` — when `ttlSeconds` is nil, insert
    `expires_at = NULL`; when non-nil, insert `expires_at = now() + make_interval(secs => $3)` (the DB
    computes the absolute expiry from its own `now()`). The `expires_at` column already exists (epic A's
    migration).
  - `Resolve(ctx, code string) (url string, found bool, err error)` — resolve only a non-expired row:
    `SELECT url FROM links WHERE code = $1 AND (expires_at IS NULL OR expires_at > now())`. An expired
    (or unknown) code returns `found=false`, so the handler returns 404. Both the write and the read use
    the DB clock, so there is no mixed-clock seam.
- `internal/httpapi/handlers.go` — in `shorten`, derive the TTL from the already-parsed
  `req.TTLSeconds`: pass a positive value straight through to `Create`; a nil, zero, or negative
  `ttl_seconds` passes nil (no expiry). Reject a `ttl_seconds` greater than a sane maximum
  (`maxTTLSeconds = 315360000`, ten years) with 400, so an absurd value cannot overflow the interval
  arithmetic or mint an instantly-stale code. The wrong-JSON-type `ttl_seconds` 400 path from epic A is
  unchanged.
- No new migration is required (the `expires_at` column exists). No index is added: correctness does
  not need one, and adding one keeps the discovered-scope migration-transactionality concern
  (gk-20260829-nf8ug7) out of scope. Should a future epic add an `expires_at` index it MUST be a
  transaction-safe `CREATE INDEX` (never `CONCURRENTLY` inside the advisory-locked migration tx).
- Tests: extend the suite with the TTL scenarios below (expiry, non-expiry, indefinite) and keep the
  epic-A regression scenarios green.

## How to build it

- **Chosen:** expiry is computed and enforced entirely on the **database clock** — written as
  `expires_at = now() + make_interval(secs => $3)` at mint and read as `expires_at IS NULL OR
  expires_at > now()` at resolve. Both sides use the same DB `now()`, so there is no api/db clock-skew
  seam (the prior draft's rationale was wrong — an app-clock write against a DB-clock read is a mixed
  clock; this decision removes it).
- **Chosen:** `Create` gains a `ttlSeconds *int` parameter (nil = no expiry). This is the code seam
  epic A's spec named; the call site in `shorten` is the only caller.
- **Chosen:** a non-positive `ttl_seconds` (0 or negative) is treated as **no expiry** (NULL
  `expires_at`) — the same as omitting it. This resolves the semantics explicitly rather than leaving it
  to the build agent; a scenario and a DONE item cover it.
- **Chosen:** a `ttl_seconds` above `maxTTLSeconds` (315360000, ten years) → 400. This is plain input
  bounding — it rejects absurd/accidental values (an integer meant as milliseconds, a fuzzer value)
  rather than silently minting a link that outlives any sensible horizon. (`make_interval(secs => $3)`
  takes a double and does not overflow, so this is a sanity bound, not an overflow guard.)
- **Chosen:** an omitted `ttl_seconds` stores NULL `expires_at` → the code never expires (unchanged
  epic-A behaviour, now explicit).
- **Assumes:** epic A is on `main` (shipped) — the `expires_at` column, the `links` table, the
  validation/handler structure, and the docker-compose stack all exist and are unchanged except for
  the two files above.

## Scenarios

Born-verifiable Given/When/Then scenarios, each HTTP-exercisable code-blind against the running stack.

```
Given a code created via POST /shorten with ttl_seconds 1
When the client sends GET /{code} at least 3 seconds later without following redirects
Then the response status is 404
```

(This is deterministic, not a timing race: expiry is evaluated on the single database clock and a
404-after-expiry outcome is monotonic in the wait, so a wait strictly greater than the 1s TTL always
observes the expired state; over-waiting only strengthens it.)

```
Given a code created via POST /shorten with ttl_seconds -1
When the client sends GET /{code} without following redirects
Then the response status is 302 and the Location header equals the submitted URL (a negative ttl means no expiry)
```

```
Given a code created via POST /shorten with ttl_seconds 3600
When the client sends GET /{code} immediately without following redirects
Then the response status is 302 and the Location header equals the submitted URL
```

```
Given a code created via POST /shorten with no ttl_seconds field
When the client sends GET /{code} without following redirects
Then the response status is 302 and the Location header equals the submitted URL
```

```
Given a valid absolute http(s) URL
When the client sends POST /shorten
Then the response status is 201 and the body field code matches ^[0-9A-Za-z]{7}$
```

```
Given a code created via POST /shorten with ttl_seconds 0
When the client sends GET /{code} without following redirects
Then the response status is 302 and the Location header equals the submitted URL (non-positive ttl means no expiry)
```

```
Given a POST /shorten body with ttl_seconds greater than ten years (e.g. 999999999999)
When the client sends POST /shorten
Then the response status is 400
```

## DONE

Externally-observable completion assertions (each checkable code-blind against the running stack via HTTP).

- [ ] `POST /shorten` with `ttl_seconds: 1` MUST cause `GET /{code}` to return status 404 when requested at least 2 seconds later.
- [ ] `POST /shorten` with a large `ttl_seconds` (e.g. 3600) MUST return status 201 and the code MUST still resolve with status 302 immediately after minting.
- [ ] `POST /shorten` with no `ttl_seconds`, or a non-positive `ttl_seconds` (0 or negative), MUST return status 201 and the code MUST resolve with status 302 (never expires).
- [ ] `POST /shorten` with a `ttl_seconds` above ten years MUST return status 400.
- [ ] The epic-A behaviours are unbroken: a valid `POST /shorten` MUST return 201 with a `^[0-9A-Za-z]{7}$` code and `GET /{code}` MUST return 302 with a byte-equal Location.
